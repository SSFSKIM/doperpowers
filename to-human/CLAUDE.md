# to-human/

A path here is named from `to-human/` when it is the plugin's own file; `docs/`, `scripts/` and `to-human/…` paths are the repository's.

A third plugin in this marketplace (versioned on its own: `scripts/bump-version.sh --plugin to-human`), the report view of a session under the `to-human` output style. It is a plugin of its own because the engine runs none of a plugin's render hooks on a row that plugin submitted (the debug log's `ui.render skipped: re-entry (the plugin's own code raised it)`), and sminos submits prompts (the bridge's sminos deliveries, the ask's answers) as doperpowers does (the compact mod's resume prompt).

Its `plugin.json` lists sminos under `dependencies`, which installs and enables sminos with it; its place outside sminos and doperpowers comes from the owner's `prependPlugins` (first in the list, outermost), since a dependency alone puts the dependent outside its dependency only where both share a rank and pushes the depended-upon behind every plugin nobody depends on, so it sees the ask mod's rows before the ask draws them; its band above the prompt draws its line under what the ask's band draws there.

`hooks/mods/message.tsx` registers the message tool, `mcp__to-human__message` (input `{text, final}`: the message in Markdown, and `final: true` for one that ends the turn; result `sent`; its description only `Send the human a message.`, since when to use it is the style's rule): every message to the human under the style, a `<message>` tag being the form only where the tool is not registered; written as text before a tool call a message comes back from the API (claude-opus-5-5, claude-fable-5-1) as a progress note's paraphrase that reaches no one, while a tool's input is never summarized; registered at a session's start only under the `doperpowers:to-human` output style (read from `$.config.list()`'s `outputStyle` row, once), by `MAWS_NATIVE_TO_HUMAN`, the contract version MAWS advertises (`getsTool`): an interactive session gets it unless that is a number below 8 (that MAWS registers its own `mcp__maws__message`), and a headless one only where it is 8 or more. From 8 on MAWS offers no tool of its own and its sessions use this one (MAWS's Decision Log 92), so across the switch a session never has two message tools, or none. Every MAWS launch is headless (`claude -p`, stream-json both ways, permission requests over stdio) and MAWS reads its report, where nobody reads another headless session's (a script's, a sminos internal fork's). `tests/mods/live-maws-check.py` pins a launch made as MAWS makes one, with MAWS's flags and version 8 (haiku): the init frame lists the tool, its call raises no `can_use_tool` request in the `default` mode, a final message makes one request, and no notification is raised. On stdout the made-up response after a final message streams as any response does (`message_start` to `message_stop`, then an `assistant` frame), with a `msg_hook_` message id, zero usage and no `request_id`, but without the transcript row's `answeredWithoutRequest`, and the `result` frame's `result` is its text (live, 2.1.312). It is always loaded (`isDeferred: false`); a subagent's call is refused (#310 is the ticket for letting one message the human), and so is an empty one. Its name, input, result and the log event sminos writes for it are a contract MAWS and the desk build on (design `docs/doperpowers/specs/2026-10-20-to-human-message-tool-design.md`).

A final message ends the turn once it is sent, with no request after it. The engine asks the model again after every tool result, so a turn that ends on a message otherwise pays one more request over the whole context for a closing text that mostly restates it; told to write nothing after it, haiku answered an empty response, which drew the engine's "no visible output" nudge and a third request (live, 2.1.312). The module's `turn.step` hook answers the main loop's next step itself, never calling `next`: a made-up response, `Message sent to the human.` (`FINAL_ANSWER`) stopping `end_turn` with no usage, which the transcript keeps as the turn's last assistant row (no request id, the engine's `answeredWithoutRequest` flag, a `msg_hook_` message id) and the view draws as nothing, and the turn ends `answer`. It does so only when that request would carry nothing else for the model, which the main loop's rows kept since the step before tell (its `session.append` hook): calls of the message tool alone, one of them final, every result `sent`, and beside them only the engine's standing attachments (`STANDING_ATTACHMENTS`: the style's and the token budget's reminders, live, and the announcements of tools and skills; in the owner's transcripts, 672 responses of message calls alone, these were all that stood after the results but for a prompt queued mid-turn, 37 times). A final call beside another tool's, a refused call, a prompt typed mid-turn, a hook's context, a delivery or any other attachment lets the request go, and so does a subagent's step or a turn's first. Being outermost, the step it answers reaches no hook beneath, so sminos' bridge streams no step for it (a steer the turn left unread wakes the session at its end, as the bridge does for any turn, and a pending upload's wake likewise); the call's rows and the made-up row are kept and exported as any row is. `tests/mods/live-final-check.py` pins it live (haiku, an isolated config, a probe plugin outermost): the request count of a turn with and without `final`, the turn's reason, the rows, the terminal and the export.

`hooks/mods/to-human.tsx` is the consumer of the `to-human` output style on every surface (`<message>`, with old `<to-human>`, `<essential>`, `<need-input>` and `<insight>` marks read as aliases of it; tags in inline code or fenced blocks stay literal; a message-tool call draws as a message where it sits, in the full transcript as in the report (the engine's row there is its input as one dim, cut line), its input drawn as it streams and never as raw JSON, its result as nothing, a refused or errored call left in the working record, and the response the message mod makes up after a final message drawn as nothing too, in either view and in no run, so no `› working record` follows a final message (known by where it came from and by its exact text, `FINAL_ANSWER`: live by the mod's own record of the row it made up, or of the one streaming before it is kept; from the transcript file, read with the rows' places, by the engine's `answeredWithoutRequest` flag, which follows the row's id on its line; a model that writes the same sentence, and another hook's own response, are drawn as ever); an assistant message draws as its marked spans, each body a `Markdown` element on every surface (a render answer to a remote surface carries one props and only the first engine node draws there; on the terminal the engine's block carries its row margin between label and body), and the view's rows stand a line apart as the engine's do; a run of working record — unmarked messages, tool calls and their results — between two rows the human reads folds behind one `› working record` button (the view's controls, it, `‹ fold to report` and the band's `full transcript ›`, draw as the engine's rows that unfold do: dim text the pointer brightens anywhere on the control's row, a Button with `plain`, `dimColor` and a `hover` of `inverse: false, dimColor: false` inside a keyed Box, where a bare Button is a bracketed label the pointer inverts); a question asked through `AskUserQuestion` or the ask mod's tool stays in the report, and so do agent spawns through `Agent` or `Workflow` and the notification that one failed, and an API error in the main conversation, at the turn's end or mid-turn (sent and received agent messages, the other finish notifications, and a sminos delivery whose frame names a sender other than `human` fold into the working record); an API error is the row the engine writes in place of a response, known live by its append naming `<synthetic>` as its model (`No response requested.` excepted) and from the transcript file by its `isApiErrorMessage` flag, read with the rows' places, and a mid-turn error's row branches off the conversation's chain, so a resume draws none; buttons unfold a run, a message, or the whole transcript; while a run's last call runs under the engine's pill (`(ctrl+b to run in background)`), its `‹ fold to report` draws under the pill, where under the call's row it would stand between the two; a `‹ fold to report` press brings the folded run's button into view when that row's top is out of the window (each row's last `onScreen` says; a reveal, even one that moves nothing, stops the transcript following its bottom); a module that starts over (an update the reload applied, a `/reload-plugins`) reads, before its first answer, whether the conversation holds a mark and where the transcript's rows stand (its file found by the session's id, searched by rg where the machine has it, else grep), under the `session.start` each load raises, the rows waiting on it only while their own dispatch stands and at most 3 s (the engine holds a draw's budget at 10 s and unloads a plugin whose draws twice run past it deaf to their signal, which a 437 MB transcript's grep did on 2026-10-20), since the fullscreen transcript holds a row off its window at the height it last had and lets go of it at the window's top edge, so a row folded while off the window pulls the view down as it scrolls back in (the rest is the engine's, TECH-DEBT); on the terminal a span's link to a local file, `[name](/abs/path#L42)`, draws behind a file glyph as a `file:` link, and a plain click on it opens VS Code at the line, a cmd-click staying the terminal's).

`hooks/mods/edits.tsx` folds the rows of file changes on the terminal: a run of `Edit`, `Write` and `NotebookEdit` calls with no other row between them draws as one dim line in the engine's group style, `Edited build.py +3 -1, created notes.md +12 ›` (each file by name with its counts from the result's patch, a clash of names told by folder, past three files a count; a call still running `Editing x…`), where each call would draw with its whole diff; the pointer brightens the line as it does the engine's count lines (a Button's `hover` set to `inverse: false` inside a keyed Box, since the pointer otherwise inverts any Button); a press unfolds the run's rows as the engine draws them, on the grey card (`userMessageBackgroundHover`) the fullscreen transcript gives a row its click unfolded, headed by the line, and a press on the line folds them back. A click on the card itself cannot fold it: no Box takes a press and a Button holds only text, and the engine's own click-to-unfold covers groups and truncated results, not edits. The engine folds only reads, searches and commands into its count line (its own edit summary is drawn only in a mode a session does not run in, and a `ToolGroup` rewrite changes nothing but `isExpanded`), so the line is this plugin's, between the engine's. It registers from `registerToHuman`, beneath the view's hooks, so it draws wherever the view hands a row on (an unfolded run, the full transcript), reads the view's row order for its runs, and is off until the view is; an errored or cut call, the ctrl+o transcript and `--verbose` keep the engine's rows. The loader refuses a module that keeps the value of a function it hands `on`, which is why the view registers it rather than returning its state.

`hooks/mods/notify.tsx` tells the person when a message is sent: each main-conversation response row whose text carries a `<message>` span (read by the view's own `parse`, so a quoted mark stays quiet) raises `$.ui.notify` with the first message as one line, as the row is kept, mid-turn as at the turn's end, and the message tool's handler raises it for an accepted call (never from the call's row, kept before the call runs), except in a sminos internal fork (`SMNS_INTERNAL`) and in a MAWS session (`MAWS_NATIVE_TO_HUMAN` set to any non-empty value, as the view and the stream hook read it, an empty one being no MAWS: MAWS is the notification surface there, banners only for what it marks essential while the person is not viewing that session, and it never edits the person's hooks that would ring for every message; `isNotifying`); their `Notification` hooks read it as `plugin_notification`, then their `preferredNotifChannel` writes it.

`hooks/mods/reminder.tsx` puts the rule for sending back in front of the model. The style is attached once, at the head of each context window (the engine's `output_style_instructions` attachment, its whole body, at a session's start, a resume, a compaction and a `/clear`), so a long window leaves it far back. A transcript audit (2026-10-27, 186 sessions, 4,885 main-conversation turns) found that a turn a subagent's report, a notification, another session or a plugin prompt opened ended on unsent prose in 75% of cases, about half of it written for the human. 85% of those misses fell at 150k tokens or more. Rewording the style's body did not move them: a replay of 14 such turns on Opus 5.5 sent 3 to 5 of 28 under each of four wordings. The reminder (`REMINDER`: the human reads only what is sent with the message tool, and a message that ends the turn goes with `final: true`) rides `prompt.submit` as context, beside the first prompt past each of 150k, 300k and 450k tokens (`REMIND_AT`, the owner's points, set so it stays rare), and nowhere else: at the head of a window it would only repeat the style. The figure is `$.session.usage()`'s, which reads the last response. The module takes the point the figure stands at from the first prompt it meets, a slash command's included, without reminding, so a fresh session, a reload and a resume each start where the context stands; a figure the engine does not have (before the first response, or after a compaction until the next one) stands at no point. A main-conversation compaction re-arms the points, and so does a figure that fell below one without the event, as after a `/clear`. It is active only where the message tool registered under its contract name (`isMessageToolOn`), since it names the tool. A slash command's prompt carries none. A prompt dropped beneath passes the reminder to the next one, unless a newer prompt moved the point while it waited (dispatches overlap: a composer prompt can pass while a notification is still screened beneath).

System notices (`Prompt dropped by a hook: ...`, a plugin's `$.ui.log` line) draw through no render hook of any plugin, so neither view can hide one once drawn, and a resume draws each again; which is why the reload mod tells a reload that went through by a toast, not a line.
