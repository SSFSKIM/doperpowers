# to-human/

A path here is named from `to-human/` when it is the plugin's own file; `docs/`, `scripts/` and `to-human/…` paths are the repository's.

A third plugin in this marketplace (versioned on its own: `scripts/bump-version.sh --plugin to-human`), the report view of a session under the `to-human` output style. It is a plugin of its own because the engine runs none of a plugin's render hooks on a row that plugin submitted (the debug log's `ui.render skipped: re-entry (the plugin's own code raised it)`), and sminos submits prompts (the bridge's sminos deliveries, the ask's answers) as doperpowers does (the compact mod's resume prompt).

Its `plugin.json` lists sminos under `dependencies`, which installs and enables sminos with it; its place outside sminos and doperpowers comes from the owner's `prependPlugins` (first in the list, outermost), since a dependency alone puts the dependent outside its dependency only where both share a rank and pushes the depended-upon behind every plugin nobody depends on, so it sees the ask mod's rows before the ask draws them; its band above the prompt draws its line under what the ask's band draws there.

`hooks/mods/message.tsx` registers the message tool, `mcp__to-human__message` (input `{text, final}`: the message in Markdown, and `final: true` for one that ends the turn; result `sent`; its description only `Send the human a message.`, since when to use it is the style's rule): every message to the human under the style, a `<message>` tag being the form only where the tool is not registered; written as text before a tool call a message comes back from the API (claude-opus-5-5, claude-fable-5-1) as a progress note's paraphrase that reaches no one, while a tool's input is never summarized; registered at a session's start only under the `doperpowers:to-human` output style (read from `$.config.list()`'s `outputStyle` row, once), by `MAWS_NATIVE_TO_HUMAN`, the contract version MAWS advertises (`getsTool`): an interactive session gets it unless that is a number below 8 (that MAWS registers its own `mcp__maws__message`), and a headless one only where it is 8 or more. From 8 on MAWS offers no tool of its own and its sessions use this one (MAWS's Decision Log 92), so across the switch a session never has two message tools, or none. Every MAWS launch is headless (`claude -p`, stream-json both ways, permission requests over stdio) and MAWS reads its report, where nobody reads another headless session's (a script's, a sminos internal fork's). `tests/mods/live-maws-check.py` pins a launch made as MAWS makes one, with MAWS's flags and version 8 (haiku): the init frame lists the tool, its call raises no `can_use_tool` request in the `default` mode, a final message makes one request, and no notification is raised. On stdout the made-up response after a final message streams as any response does (`message_start` to `message_stop`, then an `assistant` frame), with a `msg_hook_` message id, zero usage and no `request_id`, but without the transcript row's `answeredWithoutRequest`, and the `result` frame's `result` is its text (live, 2.1.312). It is always loaded (`isDeferred: false`); a subagent's call is refused (#310 is the ticket for letting one message the human), and so is an empty one. Its name, input, result and the log event sminos writes for it are a contract MAWS and the desk build on (design `docs/doperpowers/specs/2026-10-20-to-human-message-tool-design.md`).

A final message ends the turn once it is sent, with no request after it. The engine asks the model again after every tool result, so a turn that ends on a message otherwise pays one more request over the whole context for a closing text that mostly restates it; told to write nothing after it, haiku answered an empty response, which drew the engine's "no visible output" nudge and a third request (live, 2.1.312). The module's `turn.step` hook answers the main loop's next step itself, never calling `next`: a made-up response, `Message sent to the human.` (`FINAL_ANSWER`) stopping `end_turn` with no usage, which the transcript keeps as the turn's last assistant row (no request id, the engine's `answeredWithoutRequest` flag, a `msg_hook_` message id) and the view draws as nothing, and the turn ends `answer`. It does so only when that request would carry nothing else for the model, which the main loop's rows kept since the step before tell (its `session.append` hook): calls of the message tool alone, one of them final, every result `sent`, and beside them only the engine's standing attachments (`STANDING_ATTACHMENTS`: the style's and the token budget's reminders, live, and the announcements of tools and skills; in the owner's transcripts, 672 responses of message calls alone, these were all that stood after the results but for a prompt queued mid-turn, 37 times). A final call beside another tool's, a refused call, a prompt typed mid-turn, a hook's context, a delivery or any other attachment lets the request go, and so does a subagent's step or a turn's first. Being outermost, the step it answers reaches no hook beneath, so sminos' bridge streams no step for it (a steer the turn left unread wakes the session at its end, as the bridge does for any turn, and a pending upload's wake likewise); the call's rows and the made-up row are kept and exported as any row is. `tests/mods/live-final-check.py` pins it live (haiku, an isolated config, a probe plugin outermost): the request count of a turn with and without `final`, the turn's reason, the rows, the terminal and the export.

`hooks/mods/present.tsx` registers the present tool, `mcp__to-human__present` (input `{brief}`; design and contracts `docs/doperpowers/specs/2026-11-13-present-panel-design.md`): the session's panel, one HTML page per session for what the human must read closely and plain text carries poorly, which the style's rule says when to use. It is offered where the message tool is and only in an interactive session (never under MAWS, in a headless session or in a sminos internal fork), and refuses a subagent's call, an empty brief and plan mode. The handler runs `panel/server.py open-panel`, which has the panel server copy the page (or the starter) to the panel's `draft.html`, spawns a fork of the session (`$.agent.spawn`, `fork`, description `panel`) with the standing prompt and the brief, and returns at once with the address (`STARTED`); the fork holds the conversation up to the call, so the brief only says what to present. A second call while a fork writes is refused (`BUSY`). At the fork's `turn.complete` with reason `answer` the server publishes the draft over the page in one rename; the call's row in the report turns from `writing…` to the address as a link, or to `not written` and why, a notification is raised where the session notifies, and the session reads `FINISHED` or `FAILED` as hook context beside its next tool result or prompt, never woken for it. The run's record and every fork id it spawned stay in `$.state` (`present`, `presented`, `presentForks`), so a module that starts over still guards the fork and hears its end. The guard is the module's own `tool.call` and `tool.check` hooks, registered apart from the handler, since a plugin's hooks run on its fork's calls except the registration whose frame made the spawn: `Read`, `Grep`, `Glob`, `Bash` the engine holds read-only, and `Write` or `Edit` of the draft's real path pass, the last only for the open run's own fork (a former fork's late write would land in the open run's draft, which that run's end publishes), a write holding a secret's handle is refused at `tool.call` (before devcloud's guard beneath restores the secret), everything else is refused with `GUARD_REFUSAL`, and no call of a fork reaches a permission prompt (unguarded, a write under the configuration directory asks in `default` and `acceptEdits`, and the fork blocks on the main pane's dialog). Its `tool.check` also allows the plugin's own spawn, which the engine checks as an `Agent` call that asked in `auto` and `plan`, and it fails closed while it cannot tell whose fork a call is. The hold is needed: a fork starts mid-turn with the session's task in its context and goes on with it when nothing stops it. **On haiku the panel is unreliable.** Haiku forks often re-enact the session's last steps instead of writing the page: across four haiku main runs 16 of 26 forks made a call off the panel (`present`, the message tool, the session's commands) and about 8 of 26 ended without writing, and notes went missing on a page the human had seen and appeared on one they had not. The guard refused every such call and nothing outside the draft changed; the session is told `FAILED` and calls again. Opus and fable forks held in every run (6 of 6 each, the session mid-task with steps of its own pending, and every acceptance run). `tests/mods/live-present-check.py` is its live check.

`panel/server.py` is the panel server, one process per machine (Python's standard library alone), on `127.0.0.1` at `PANEL_PORT` (4777 by default), started detached by the first command that needs it and outliving the session. One server serves a configuration directory: it holds the panels directory's `server.lock` for its life, a second one over the directory refuses to start whatever its port, and a command whose `PANEL_PORT` is not the running server's is refused with the port that one is on. Told to shut down (the version replacement), it takes no new request and lets those in flight answer, and no record transaction is cut; a publish records its time before it replaces the page, so one a crash cuts is published again by the next. It is the only writer of a panel's records (`to-human/panels/<short id>/` in the configuration directory: `panel.html`, `draft.html`, `meta.json`, `state.json`), serves each panel at `/<short id>/` and the base (`panel/base/`: `panel.css`, `panel.js`, `starter.html`, `GUIDE.md`, what every page links and the fork reads) at `/base/`, puts a content policy on every response so only the base's script and its own run, and cuts at publish every `meta http-equiv`, `base` and `link` but the base's stylesheet. The mod's whole interface to it is the command line (`open-panel`, `publish`, `ensure`, the last at every interactive session's start, so an old address opens again after a restart and an older server is replaced). The base is served from the running server's own plugin directory, so a server whose plugin cache directory was removed answers 404 for `/base/*` until a session on a newer version replaces it. With `PANEL_REACH=tailnet` it maps its port with `tailscale serve` (under `sudo -n` where the user may not, as on a devcloud host), so the MacBook opens every machine's panels; a forwarded request must carry the machine's own user's login, any login on a tagged host. `PANEL_LOCALE=ko` writes the page in Korean. Tests: `to-human/tests/panel/` (unittest, in the `to-human-mods` gate) and `live-base-check.sh` (the base in a browser, no model call).

`hooks/mods/to-human.tsx` is the consumer of the `to-human` output style on every surface (`<message>`, with old `<to-human>`, `<essential>`, `<need-input>` and `<insight>` marks read as aliases of it; tags in inline code or fenced blocks stay literal; a message-tool call draws as a message where it sits, in the full transcript as in the report (the engine's row there is its input as one dim, cut line), its input drawn as it streams and never as raw JSON, its result as nothing, a refused or errored call left in the working record, and the response the message mod makes up after a final message drawn as nothing too, in either view and in no run, so no fold's button follows a final message (known by where it came from and by its exact text, `FINAL_ANSWER`: live by the mod's own record of the row it made up, or of the one streaming before it is kept; from the transcript file, read with the rows' places, by the engine's `answeredWithoutRequest` flag, which follows the row's id on its line; a model that writes the same sentence, and another hook's own response, are drawn as ever); an assistant message draws as its marked spans, each body a `Markdown` element on every surface (a render answer to a remote surface carries one props and only the first engine node draws there; on the terminal the engine's block carries its row margin between label and body), and the view's rows stand a line apart as the engine's do; a run of working record — unmarked messages, tool calls and their results — between two rows the human reads folds behind one button, `› ` and the run's label (`folds.tsx`: its newest call's line while it is live, its summary once it has closed, `working record` where it has neither; the view's controls, it, `‹ fold to report` and the band's `full transcript ›`, draw as the engine's rows that unfold do: dim text the pointer brightens anywhere on the control's row, a Button with `plain`, `dimColor` and a `hover` of `inverse: false, dimColor: false` inside a keyed Box, where a bare Button is a bracketed label the pointer inverts); a subagent's row is known by its append (`agentId` set) at once, and any other drawn row with no place is judged at the main conversation's next step's end (a row kept through the `tool-result`, `delivery` or `prompt` door, or `turn.complete`, never another row of a response, whose blocks are kept one by one while the next streams), a prompt row as it draws, since one is kept before it draws (the person's own now and then after, which its append takes back, as it does any row judged so); none is judged until the transcript's list was read whole (`isWhole`: the search writes its list to a file, read back in pieces under the 4 MiB one run's output stops at); a queued delivery's preview draws nothing, as the delivery does, and any other such row as the engine draws it (a loop's own instructions, origin `coordinator`, among them, which the main conversation's queue never holds; `hooks/mods/edits.tsx` folds the rows of file changes on the terminal: a run of `Edit`, `Write` and `NotebookEdit` calls with no other row between them draws as one dim line in the engine's group style, `Edited build.py +3 -1, created notes.md +12 ›` (each file by name with its counts from the result's patch, a clash of names told by folder, past three files a count; a call still running `Editing x…`), where each call would draw with its whole diff; the pointer brightens the line as it does the engine's count lines (a Button's `hover` set to `inverse: false` inside a keyed Box, since the pointer otherwise inverts any Button); a press unfolds the run's rows as the engine draws them, on the grey card (`userMessageBackgroundHover`) the fullscreen transcript gives a row its click unfolded, headed by the line, and a press on the line folds them back. A click on the card itself cannot fold it: no Box takes a press and a Button holds only text, and the engine's own click-to-unfold covers groups and truncated results, not edits. The engine folds only reads, searches and commands into its count line (its own edit summary is drawn only in a mode a session does not run in, and a `ToolGroup` rewrite changes nothing but `isExpanded`), so the line is this plugin's, between the engine's. It registers from `registerToHuman`, beneath the view's hooks, so it draws wherever the view hands a row on (an unfolded run, the full transcript), reads the view's row order for its runs, and is off until the view is; an errored or cut call, the ctrl+o transcript and `--verbose` keep the engine's rows. The loader refuses a module that keeps the value of a function it hands `on`, which is why the view registers it rather than returning its state.

`hooks/mods/folds.tsx` is the run tracker, what a fold's button says before it is opened (design `docs/doperpowers/specs/2026-11-12-fold-summaries-design.md`). The view learns of a row only when it draws, and a fullscreen terminal never draws the rows outside its window, so the tracker follows the main conversation's rows as they are kept (`session.append`, a subagent's ignored) and each turn's end (`turn.complete`), sorts them into runs by the view's own exported rules, and publishes each run in `$.state` (`types/to-human.d.ts`: `folds` the closed runs, `fold` the open one, `foldLast` its newest row, which no drawing reads, so a result or a note redraws no button); the view finds the run of whichever row draws a button by its place. A live run reads its newest call's line (`lineOf`: a command's description, a file's name, `server: tool` for an MCP call). A run that closes at a row the person reads, once its calls' results are kept, and the open run at a turn's end if rows joined it since its last summary, is summarized: one `$.model.complete` call, never awaited by a hook, to `haiku` (`TO_HUMAN_FOLD_MODEL` names another for a launch) at high effort over the run's digest (its notes, calls, results cut to their ends and deliveries, each part cut as added, 60,000 characters at most) under `LABEL_SYSTEM`, the reply's first line cut at 120. A reply for a run that took a row since it was asked, or across a `clear`, `resume` or `fork`, is dropped; an unanswered, empty or thrown call leaves the run's summary as it was, so a spent quota leaves `working record`. Summaries are asked for only where a mark has been seen (drawn by the view, or kept: the message that closes a session's first run counts for that run before it draws), in an interactive session, not under MAWS nor in a sminos internal fork. The tracker's memory is the authority; `$.state` and the session's file, `to-human/folds/<session id>.json` in the configuration directory, are written from it whole through one chain each, and the file each time a summary settles, so a resume shows them (a new process publishes its file as closed runs and removes files older than 30 days). A reload loses the module's memory: the open run is taken up from `$.state` and is never summarized again, the next is.

`hooks/mods/notify.tsx` tells the person when a message is sent: each main-conversation response row whose text carries a `<message>` span (read by the view's own `parse`, so a quoted mark stays quiet) raises `$.ui.notify` with the first message as one line, as the row is kept, mid-turn as at the turn's end, and the message tool's handler raises it for an accepted call (never from the call's row, kept before the call runs), except in a sminos internal fork (`SMNS_INTERNAL`) and in a MAWS session (`MAWS_NATIVE_TO_HUMAN` set to any non-empty value, as the view and the stream hook read it, an empty one being no MAWS: MAWS is the notification surface there, banners only for what it marks essential while the person is not viewing that session, and it never edits the person's hooks that would ring for every message; `isNotifying`); their `Notification` hooks read it as `plugin_notification`, then their `preferredNotifChannel` writes it.

`hooks/mods/reminder.tsx` puts the rule for sending back in front of the model. The style is attached once, at the head of each context window (the engine's `output_style_instructions` attachment, its whole body, at a session's start, a resume, a compaction and a `/clear`), so a long window leaves it far back. A transcript audit (2026-10-27, 186 sessions, 4,885 main-conversation turns) found that a turn a subagent's report, a notification, another session or a plugin prompt opened ended on unsent prose in 75% of cases, about half of it written for the human. 85% of those misses fell at 150k tokens or more. Rewording the style's body did not move them: a replay of 14 such turns on Opus 5.5 sent 3 to 5 of 28 under each of four wordings. The reminder (`REMINDER`: the human reads only what is sent with the message tool, and a message that ends the turn goes with `final: true`) rides `prompt.submit` as context, beside the first prompt past each of 150k, 300k and 450k tokens (`REMIND_AT`, the owner's points, set so it stays rare), and nowhere else: at the head of a window it would only repeat the style. The figure is `$.session.usage()`'s, which reads the last response. The module takes the point the figure stands at from the first prompt it meets, a slash command's included, without reminding, so a fresh session, a reload and a resume each start where the context stands; a figure the engine does not have (before the first response, or after a compaction until the next one) stands at no point. A main-conversation compaction re-arms the points, and so does a figure that fell below one without the event, as after a `/clear`. It is active only where the message tool registered under its contract name (`isMessageToolOn`), since it names the tool. A slash command's prompt carries none. A prompt dropped beneath passes the reminder to the next one, unless a newer prompt moved the point while it waited (dispatches overlap: a composer prompt can pass while a notification is still screened beneath). The engine's own style reminder, `<style> output style is active. Remember to follow the specific guidelines for this style.` (the `output_style` attachment, beside every request of the main loop: the turn's prompt and each tool result), names no rule; the module's `prompt.attachment` hook appends one to it (`STYLE_FINAL`: a message that is the last thing done in a turn goes alone with `final: true`, which saves the request after it), wherever the message tool is registered. The answer does not depend on the loop: the engine caches an attachment's answer process-wide by its UUID and a fork inherits main's UUIDs, so a condition on `agentId` would be wrong for whichever loop did not ask first (the compact mod's `mcp_instructions_delta` hook keeps to the same rule). A subagent is not known to get this attachment, and a fork's message call is refused anyway. `tests/mods/live-final-check.py` reads, through its probe, what the model reads for each one.

System notices (`Prompt dropped by a hook: ...`, a plugin's `$.ui.log` line) draw through no render hook of any plugin, so neither view can hide one once drawn, and a resume draws each again; which is why the reload mod tells a reload that went through by a toast, not a line.

Tests `to-human/tests/mods/run.sh` (the `to-human-mods` gate). Beside them the live checks, each an isolated session in a tmux pane, run by hand since they spend model calls (haiku, through the gateway keys in the environment): `live-message-check.py` (the message tool), `live-final-check.py` (a final message), `live-maws-check.py` (a MAWS launch), `live-resume-check.py` (a resumed history), `live-reload-check.py` (a reload in a long session, no model call), `live-folds-check.py` (the live line and the summaries) and `live-present-check.py` (the present tool, its fork and its guard; `--model` runs it on the owner's models).
