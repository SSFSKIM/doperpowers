# sminos/hooks/mods/ — the sminos plugin's function hooks

A path here is named from `sminos/` when it is the plugin's own file; `docs/`, `sminos/…` and `to-human/…` paths are the repository's.

The function hooks, `hooks/mods/` (`register.tsx` registers the bridge, the ask, the address and the name, in that order; their manual is `hooks/mods/README.md`): `ask.tsx` registers `mcp__sminos__AskUserQuestion`, the model's one way to ask the human in an interactive session: the built-in's questions plus `async`, true unless the call says false, under the built-in's description less its plan-mode paragraph. Blocking (`async: false`), it opens the engine's own dialog (a `$.ui.ask` raised inside the tool's hook and widened to the full question set by the mod's own `tool.call` hook on `AskUserQuestion`, correlated by a token in the header) and returns the engine's text; async, it returns at once, the questions wait behind `[ answer ]` and `[ dismiss ]` in the call's row and in an `N open questions` band above the prompt (a dismissal closes the ask unanswered and tells the model so quietly, on the next route another opens, never waking the session), and the answer reaches the model as `context` on its next tool result, or as a plugin prompt when the session is idle, or with the human's next prompt after a stop. Each ask raises a notification of its first question as the model asks it (`$.ui.notify`, which the person's `Notification` hooks read as `plugin_notification`); the dialog the mod raises reaches the PreToolUse and PermissionRequest hooks marked `metadata.source: sminos-ask`, and while it stands the engine's `permission_prompt` reminder is kept from the `Notification` hooks, so a press to answer notifies nothing. The asks and the answers not yet delivered are kept in `$.state` (`sminos.ask`, typed in `types/sminos.d.ts`, the plugin's contract: doperpowers' appeal and reload read its `answered` count and `isDialogUp`), which the host holds for the session, so a reload of the module (a `/reload-plugins` or the autoreload bringing a new version) takes them up where the one before left them. A resumed session's asks are read back from its transcript; a copy's (a session the engine starts under a new id with the original's conversation, its transcript not yet written) from the conversation it holds, `$.session.messages()`, which starts at the last compaction. The built-in is deferred and refused while the tool exists; design in `docs/doperpowers/specs/2026-10-13-ask-async-design.md`.

`address.tsx` adds, on `attribution.text`, the session's sminos address — `Sminos-Session: <alias>#<short> (<project> on <machine>)`, composed by `sminos who --session <id>` and asked for again only for a new session id, after a compaction, or once the kept line is ten minutes old (a minute for no line: none yet, or a CLI that failed), a line it has served at once while it is asked in the background — to the text the engine tells the model to end every commit message (as a trailer) and PR body (as its last line) with, which reaches the model even with the settings' attribution empty and reads the parent's session in a subagent; nothing for a session in no project, an internal fork, or a non-member, and `sminos who <commit|PR>` reads it back.

`name.tsx` renames a session whose name the engine made up after what it is in charge of: `sminos derive` proposes the name with the in-charge line and leaves it pending in `$SMINOS_HOME/names/<session>.json`, and a 15 s timer runs the engine's own `/rename` (`$.command.run`, registered `user`, the engine telling the model) at the first tick that finds the session between turns with no ask's dialog up, once `sminos name-due` finds it still due, in every session but an internal fork (interactive, `--bg` and SDK sessions alike take the command, measured on 2.1.306); an alias a member held before keeps reaching it behind every current alias, with a `note:` naming it now (design `docs/doperpowers/specs/2026-10-20-sminos-charge-names-design.md`).

`bridge.tsx` (registered first, so its hooks are the plugin's outermost, and the plugin is seated outside every other but to-human) makes the session reachable from outside it on this machine: at `session.start` it spawns a session-lifetime child, `sminos bridge --session <id>`, which serves the session's endpoint at `$SMINOS_HOME/bridge/<id>.sock` (the socket answering is the session's bridge presence); the mod posts the session's events there from one poster loop (each chunk of the main loop and of every subagent, tool calls and results, turns, subagents, usage, a heartbeat, and a notice for every row the session keeps, as it is written, each loop's last notice the snapshot's cut, seeded, for a loop older than the module, from its transcript tail at the module's first hello; every post carries the hello's nonce, so a reloaded module's old instance is refused and stops) and reads commands from the child's stdout: steer (a user row the loop reads at its next request, the owner's words under its first line `[sminos steer from human]`, which tells the steer from the bridge's other rows), interrupt (the turn aborted, each Bash the abort moved to the background stopped, and user rows in before the turn can end: Esc's marker whole, the only text a transcript's reader knows an interrupt by, then a note telling the model where it came from and what was stopped, then, when the main turn streamed text no row kept (a plugin's abort drops it where Esc keeps it), a row carrying that cut-off reply under its first line, which starts `The interrupt cut off the reply you were writing.` and is how a reader knows the row; the turn's messages are taken before the abort, a row kept meanwhile settling its block in them even once the stream pairs it no more, and their text is read just before the cut-off row goes in, and the terminal's one-line mirror shows the reply's first 300 characters), model and effort (rewritten on the main loop's requests, never `$.config.set`), compact (at the turn's end when asked during one), the desk's `read` (`status`: the engine's version, where the session runs, its surfaces, the permission mode; `catalog`; and `usage`, `config`, `settings`, `mcp`, each cut to what the desk shows: no `env`, no hook's command, no MCP server's configuration, no plugin's text config value) and `command` (a slash command checked against the route table of the engine it runs on — a panel, a command that saves a default, one that needs the terminal, each refused with its reason, a non-built-in classed by its `source`; a table per measured engine, a session routing by the newest at or below its own — then run with `$.command.run`, answered `queued` at once, one desk command at a time, its run on the stream as `run` start and end with the line it printed read back from its row; a `/reload-plugins` is called only once its answer and its run's start have reached the child, and a desk command sent while one is queued or running is refused, since the module it would run in is going: the module the reload replaces says nothing more, the daemon finishing it by the bridge answering from another child than the one the start names; every resync carries the module's `capabilities`, which the child answers in its status, among them `controls`, every desk control's key with whether this bridge can do it and why not; design `docs/doperpowers/specs/2026-10-22-desk-control-surface-design.md` in MAWS), the desk's side question (`btw`: one `$.model.fork` over the session's own transcript under a frame that keeps it from the open task and from tools, answered `started` at once unless there is nothing to fork, its answer, cut to 64 KiB, and its cost following on the stream as `btw` start and end; nothing is written into the conversation; each open one is kept in `$.state` until the child took its end, so the module that loads after a reload ends those whose fork the reload aborted, `aborted`; a desk command's and a side question's end is posted again after every resync until a post the child answered carried it, and the child relays each end once), one subagent stopped or told (`stop-agent`, `tell`: the agent named by its id or its Agent call's name, checked running in `$.agent.list()`, else refused `unknown-agent` — or, when the caller resolved it (`resolvedAgentId`, the daemon), that agent alone, checked by its exact id in the list, no shape assumed (a teammate's id is `<name>@<team>`); a stop runs TaskStop on the resolved id, a hook's refusal of it being no stop, and leaves the parent's own loop (main, or the subagent that spawned it) a note that the person stopped it and it must not be started again or redone, what the stop hands the parent — a foreground agent's Agent call result, a background agent's task notification — held until the note is in so the parent's next request carries it, and a note not kept named in the answer (`noteError`); a tell sends through `$.session.send` under a line saying the person wrote it, since the engine's envelope credits the coordinator; both answer once the engine has, so no outcome follows on the stream), an upload from the desk (`media`: files the daemon saved under the session's working directory, answered `queued` once held in `$.state`, `{plugin: 'sminos', key: 'media'}`; at a main-loop step with one pending the step's `turn.step` hook claims it, keeping a generated tool-use id before it yields, and streams a prelude saying the Read is the bridge's, then a native Read of the pinned path, which the engine runs, never calling `next` for that step; each attachment `pending`, `claimed`, `read` (a media-bearing result for that id), `forwarded` (the next main-loop step went on through `next`, which a hook beneath may still answer without a request), `aborted` (its step cancelled, Esc or a turn's end; never retried) or `failed`, said as a `media` event the child relays once by `(upload, index, state)`, carrying the upload, which is the RPC's operation id (its `opId`, else its nonce), as `rpc`, its whole upload's states, and `phase: end` once every attachment ended, each said again after every resync until the child took it; an idle session gets one `[sminos bridge]` wake 2 s after an upload, and one when a turn ends with an attachment still pending; a reload reconciles each claim from the transcript, a claim with no result `aborted` as indeterminate), an owner's log event (kind `human`, written by `<machine>/human` or `hub/<member>`) delivered as the human's words once per `(project, writer, seq)` (a peer's event goes instead to the engine's inbox as a peer message, in the engine's envelope, closed by the reply line), and an answer from outside to a permission prompt or a question, settled once on the engine's own `tool_decision` record of who decided (a permission raised with the engine's `permission_suggestions` only when its input is exactly the call the bridge's `tool.call` hook saw, so nothing a guard beneath restored leaves the machine, and only within the hub's bound; an allow from outside may add one of them as `updatedPermissions`, never an input). It exports the main loop's `<message>` spans, message-tool calls once each has its result (what is kept after one waits, so the log keeps transcript order; a row holding several goes once all have theirs), async questions and their answers (the plugin's delivery, MAWS's `[MAWS ask]` steer) to the project's log as their rows are written, through the record path's own writer and `(kind, src)` keys, so the Stop hook's export finds them there. Never in `SMNS_INTERNAL`.

The permission mode: `read status`, `ping`, the heartbeat and every resync carry `permissionMode`, the main loop's mode in the engine's word as the engine last reported it, with `permissionModeAt` (when the bridge read the report) and `permissionModeFrom` (the event it came in), all three absent until a report. The reports: the engine's `permission_mode_changed` collector record at each switch its mode transition makes (Shift+Tab in the terminal included; a change is posted at once on a heartbeat of its own, a report of the same mode rides the next beat), and the classic UserPromptSubmit and PermissionRequest inputs' `permission_mode`; a subagent's is its own loop's and never taken, and nothing is inferred from the settings or the launch flags. A tool call's `tool_decision` record is no report: its `permission_mode` is the mode the check began under, so it can arrive after a newer switch's record still carrying the old mode. A change no record reports stays unseen until the next prompt or permission prompt, and the session's start reports none (the classic SessionStart input carries no mode), so a session that has neither switched nor taken a prompt has no mode yet. A reload keeps the last report in `$.state` (`{plugin: 'sminos', key: 'mode'}`). The child keeps the three fields as the last heartbeat or resync carried them and says them in its `GET /status`, which the daemon's probe reads for the session's presence (`mode`).

In a MAWS lane B session (O12 M3: MAWS's engine host launches each `claude -p` with `MAWS_LANE=B` beside `SMNS_MEMBER`, its own pid) the bridge only observes, since MAWS is that session's controller: the mod reads the marker at its session start and is a provisional observer until its child, which can read its parent's pid where the mod cannot, says in its hello (or on a later `{op: "lane"}` line of its own, which carries no command id: the child's `/command` refuses `hello` and `lane` from a client, retrying an `unresolved` one every 2 s for a minute, then every 30 s) whether sminos's parent check matches: `match` stays an observer, `mismatch` (positive evidence of another spawner: the host SMNS_MEMBER names running, not a zombie, started in an earlier whole second than the session and not its parent, as for a `claude` a lane B session's Bash started, both variables inherited) is a full controller, `unresolved` (a parent that is merely not the mark, as after the host exited and the engine was re-parented, included) stays an observer. A resolved verdict is the process's and stands, kept in `$.state` (`{plugin: 'sminos', key: 'lane'}`) for a reload and handed to every later child the module starts (`sminos bridge --session <id> --lane <verdict>`), which takes it as its own: a replacement child after the host exited would find the engine re-parented. The child's own verdict rests on one observation of the session's parent. An observer answers every control op (`steer`, `interrupt`, `stop`, `model`, `compact`, `deliver`, `answer`, `command`, `btw`, `stop-agent`, `tell`, `media`) `{ok: false, code: 'lane-b'}`, `ping` and `read` still answering; its capabilities have no `ops` and every `controls` key `{available: false, reason: 'MAWS controls this session'}`; it raises no permission or question to the desk (MAWS answers through `--permission-prompt-tool stdio`); its `turn.step` claims no upload and rewrites no model or effort, and it submits no upload's wake, its chunks and steps still posted, subagents' too; and its child refuses the decision route `409 lane-b`. A refused `deliver` goes, as any refused delivery, as an inbox frame.

The bridge names its process's launch (O12 M7): at its first session start the module mints one (16 random bytes, base64url), keeps it in `$.state` (`{plugin: 'sminos', key: 'launch'}`) so a reload names the same, and starts every child with it (`sminos bridge --session <id> --launch=<id>`, joined to the flag since the id may start with `-`); a `--resume` is a new process and mints its own. The child says it in its hello and `GET /status` (which the daemon's probe keeps, a cut-over machine's presence and `member` frames carrying it), and refuses a `POST /command` or a decision whose body names another launch (`409 {ok: false, code: 'launch'}`), posting nothing to the mod; a body naming none is a local caller's and runs as ever, and the child passes no `launch` on to the mod. A remote desk action names the launch it was sealed for, so one sealed before a relaunch is refused at the effect.

On a machine cut over to its endpoint (RL10; O12 M8), the export of a hub project's session goes to that project's host store in place of its log, through the same writer and `(kind, src)` keys, so the Stop hook's export still finds it there; the child's `_export_now` is unchanged, `append_host` choosing the store.

On every settled `tool.call` and `session.append` it checks its own place in `next.trace`: when the guard loaded now (devcloud's, its marker live, else cua's copy, `cua@cua` enabled in the user settings) is not beneath it, it turns off: it drops what was queued, stops the child, raises nothing, and says so once in a toast and a debug line naming `prependPlugins`; a later dispatch that began after the off and reads safe turns it back on with a new child, as a reload starts one. Until the first check, tool events wait and no permission's input is raised (a native question is).

`bridge.tsx` keeps the hooks and the code that takes `$` (the session start, the child, control, the wait for a decision, the reads of which guard is loaded); its other concerns sit beside it, none taking `$`, each importing only the ones listed before it: `bridge-routes.tsx` (the route table as data, written from `sminos/tests/routes-<engine>.json` by `routes_check.py --write`, which fails while the two differ: a mod loads no JSON), `bridge-commands.tsx` (the route check, `routeOf` — a command's forms first, then its class — and the refusals' words), `bridge-controls.tsx` (the desk's per-control capability map), `bridge-catalog.tsx` and `bridge-reads.tsx` (the catalog and the desk's reads, which take `$`), `bridge-place.tsx` (the rule that judges its place among the guards), `bridge-state.tsx` (the one state object, its types, `resetBridge`), `bridge-stream.tsx` (the live state every resync carries, and the poster), `bridge-requests.tsx` (requests from outside and their settlement), `bridge-rows.tsx` (each kept row's notice, and the export to the host), `bridge-agents.tsx` (the agent state seeded and refreshed from `$.agent.list()`, so agents that predate the module are known), `bridge-btw.tsx` (the side question: its frame, its bound, the op, which takes `$`), `bridge-agent-ops.tsx` (one subagent stopped or told, which takes `$`), `bridge-media.tsx` (a desk upload's intake: its state in `$.state`, the claim and the synthetic Read, its events, the wakes and the reload's reconciliation, which take `$`).

The protocol is DX5 in `docs/doperpowers/plans/2026-10-15-arkho-desk-c2-bridge.md`; tests `tests/mods/bridge.test.ts` and `tests/test-bridge*.sh`, live checks `tests/mods/live-*-check.py` (they spend model calls; run by hand).
