# sminos/hooks/mods/ — the sminos plugin's function hooks

A path here is named from `sminos/` when it is the plugin's own file; `docs/`, `sminos/…` and `to-human/…` paths are the repository's.

The function hooks, `hooks/mods/` (`register.tsx` registers the bridge, the ask, the address and the name, in that order; their manual is `hooks/mods/README.md`): `ask.tsx` registers `mcp__sminos__AskUserQuestion`, the model's one way to ask the human in an interactive session: the built-in's questions plus `async`, true unless the call says false, under the built-in's description less its plan-mode paragraph. Blocking (`async: false`), it opens the engine's own dialog (a `$.ui.ask` raised inside the tool's hook and widened to the full question set by the mod's own `tool.call` hook on `AskUserQuestion`, correlated by a token in the header) and returns the engine's text; async, it returns at once, the questions wait behind `[ answer ]` and `[ dismiss ]` in the call's row and in an `N open questions` band above the prompt (a dismissal closes the ask unanswered and tells the model so quietly, on the next route another opens, never waking the session), and the answer reaches the model as `context` on its next tool result, or as a plugin prompt when the session is idle, or with the human's next prompt after a stop. Each ask raises a notification of its first question as the model asks it (`$.ui.notify`, which the person's `Notification` hooks read as `plugin_notification`); the dialog the mod raises reaches the PreToolUse and PermissionRequest hooks marked `metadata.source: sminos-ask`, and while it stands the engine's `permission_prompt` reminder is kept from the `Notification` hooks, so a press to answer notifies nothing. The asks and the answers not yet delivered are kept in `$.state` (`sminos.ask`, typed in `types/sminos.d.ts`, the plugin's contract: doperpowers' appeal and reload read its `answered` count and `isDialogUp`), which the host holds for the session, so a reload of the module (a `/reload-plugins` or the autoreload bringing a new version) takes them up where the one before left them. A resumed session's asks are read back from its transcript; a copy's (a session the engine starts under a new id with the original's conversation, its transcript not yet written) from the conversation it holds, `$.session.messages()`, which starts at the last compaction. The built-in is deferred and refused while the tool exists; design in `docs/doperpowers/specs/2026-10-13-ask-async-design.md`.

`address.tsx` adds, on `attribution.text`, the session's sminos address — `Sminos-Session: <alias>#<short> (<project> on <machine>)`, composed by `sminos who --session <id>` and asked for again only for a new session id, after a compaction, or once the kept line is ten minutes old (a minute for no line: none yet, or a CLI that failed), a line it has served at once while it is asked in the background — to the text the engine tells the model to end every commit message (as a trailer) and PR body (as its last line) with, which reaches the model even with the settings' attribution empty and reads the parent's session in a subagent; nothing for a session in no project, an internal fork, or a non-member, and `sminos who <commit|PR>` reads it back.

`name.tsx` renames a session whose name the engine made up after what it is in charge of: `sminos derive` proposes the name with the in-charge line and leaves it pending in `$SMINOS_HOME/names/<session>.json`, and a 15 s timer runs the engine's own `/rename` (`$.command.run`, registered `user`, the engine telling the model) at the first tick that finds the session between turns with no ask's dialog up, once `sminos name-due` finds it still due, in every session but an internal fork (interactive, `--bg` and SDK sessions alike take the command, measured on 2.1.306); an alias a member held before keeps reaching it behind every current alias, with a `note:` naming it now (design `docs/doperpowers/specs/2026-10-20-sminos-charge-names-design.md`).

`bridge.tsx` (registered first, so its hooks are the plugin's outermost, and the plugin is seated outside every other but to-human) makes the session reachable from outside it on this machine: at `session.start` it spawns a session-lifetime child, `sminos bridge --session <id>`, which serves the session's endpoint at `$SMINOS_HOME/bridge/<id>.sock` (the socket answering is the session's bridge presence); the mod posts the session's events there from one poster loop (each chunk of the main loop and of every subagent, tool calls and results, turns, subagents, usage, a heartbeat, and a notice for every row the session keeps, as it is written, each loop's last notice the snapshot's cut, seeded, for a loop older than the module, from its transcript tail at the module's first hello; every post carries the hello's nonce, so a reloaded module's old instance is refused and stops) and reads commands from the child's stdout: steer (a user row the loop reads at its next request, the owner's words under its first line `[sminos steer from human]`, which tells the steer from the bridge's other rows), interrupt (the turn aborted, each Bash the abort moved to the background stopped, and two user rows in before the turn can end: Esc's marker whole, the only text a transcript's reader knows an interrupt by, then a note telling the model where it came from and what was stopped), model and effort (rewritten on the main loop's requests, never `$.config.set`), compact (at the turn's end when asked during one), the desk's `read` (`status`: the engine's version, where the session runs, its surfaces; `catalog`; and `usage`, `config`, `settings`, `mcp`, each cut to what the desk shows: no `env`, no hook's command, no MCP server's configuration, no plugin's text config value) and `command` (a slash command checked against the route table of the engine it runs on — a panel, a command that saves a default, one that needs the terminal, each refused with its reason, a non-built-in classed by its `source`; a table per measured engine, a session routing by the newest at or below its own — then run with `$.command.run`, answered `queued` at once, one desk command at a time, its run on the stream as `run` start and end with the line it printed read back from its row; a `/reload-plugins` is called only once its answer and its run's start have reached the child, and a desk command sent while one is queued or running is refused, since the module it would run in is going: the module the reload replaces says nothing more, the daemon finishing it by the bridge answering from another child than the one the start names; every resync carries the module's `capabilities`, which the child answers in its status, among them `controls`, every desk control's key with whether this bridge can do it and why not; design `docs/doperpowers/specs/2026-10-22-desk-control-surface-design.md` in MAWS), the desk's side question (`btw`: one `$.model.fork` over the session's own transcript under a frame that keeps it from the open task and from tools, answered `started` at once unless there is nothing to fork, its answer, cut to 64 KiB, and its cost following on the stream as `btw` start and end; nothing is written into the conversation; each open one is kept in `$.state` until the child took its end, so the module that loads after a reload ends those whose fork the reload aborted, `aborted`; a desk command's and a side question's end is posted again after every resync until a post the child answered carried it, and the child relays each end once), one subagent stopped or told (`stop-agent`, `tell`: the agent named by its id or its Agent call's name, checked running in `$.agent.list()`, else refused `unknown-agent`; a stop runs TaskStop on the resolved id and leaves the parent a note that the person stopped it and it must not be started again or redone, an Agent call's result held until the note is in so a foreground agent's parent reads it with the interruption; a tell sends through `$.session.send` under a line saying the person wrote it, since the engine's envelope credits the coordinator; both answer once the engine has, so no outcome follows on the stream), an owner's log event (kind `human`, written by `<machine>/human` or `hub/<member>`) delivered as the human's words once per `(project, writer, seq)` (a peer's event goes instead to the engine's inbox as a peer message, in the engine's envelope, closed by the reply line), and an answer from outside to a permission prompt or a question, settled once on the engine's own `tool_decision` record of who decided (a permission raised with the engine's `permission_suggestions` only when its input is exactly the call the bridge's `tool.call` hook saw, so nothing a guard beneath restored leaves the machine, and only within the hub's bound; an allow from outside may add one of them as `updatedPermissions`, never an input). It exports the main loop's `<message>` spans, message-tool calls once each has its result (what is kept after one waits, so the log keeps transcript order; a row holding several goes once all have theirs), async questions and their answers (the plugin's delivery, MAWS's `[MAWS ask]` steer) to the project's log as their rows are written, through the record path's own writer and `(kind, src)` keys, so the Stop hook's export finds them there. Never in `SMNS_INTERNAL`.

On every settled `tool.call` and `session.append` it checks its own place in `next.trace`: when the guard loaded now (devcloud's, its marker live, else cua's copy, `cua@cua` enabled in the user settings) is not beneath it, it turns off: it drops what was queued, stops the child, raises nothing, and says so once in a toast and a debug line naming `prependPlugins`; a later dispatch that began after the off and reads safe turns it back on with a new child, as a reload starts one. Until the first check, tool events wait and no permission's input is raised (a native question is).

`bridge.tsx` keeps the hooks and the code that takes `$` (the session start, the child, control, the wait for a decision, the reads of which guard is loaded); its other concerns sit beside it, none taking `$`, each importing only the ones listed before it: `bridge-routes.tsx` (the route table as data, written from `sminos/tests/routes-<engine>.json` by `routes_check.py --write`, which fails while the two differ: a mod loads no JSON), `bridge-commands.tsx` (the route check, `routeOf` — a command's forms first, then its class — and the refusals' words), `bridge-controls.tsx` (the desk's per-control capability map), `bridge-catalog.tsx` and `bridge-reads.tsx` (the catalog and the desk's reads, which take `$`), `bridge-place.tsx` (the rule that judges its place among the guards), `bridge-state.tsx` (the one state object, its types, `resetBridge`), `bridge-stream.tsx` (the live state every resync carries, and the poster), `bridge-requests.tsx` (requests from outside and their settlement), `bridge-rows.tsx` (each kept row's notice, and the export to the host), `bridge-agents.tsx` (the agent state seeded and refreshed from `$.agent.list()`, so agents that predate the module are known), `bridge-btw.tsx` (the side question: its frame, its bound, the op, which takes `$`), `bridge-agent-ops.tsx` (one subagent stopped or told, which takes `$`).

The protocol is DX5 in `docs/doperpowers/plans/2026-10-15-arkho-desk-c2-bridge.md`; tests `tests/mods/bridge.test.ts` and `tests/test-bridge*.sh`, live checks `tests/mods/live-*-check.py` (they spend model calls; run by hand).
