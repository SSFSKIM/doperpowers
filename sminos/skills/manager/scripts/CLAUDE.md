# skills/manager/scripts/

The session manager's command, `manager` (a launcher resolving its real path, then `manager.py`). Design: `docs/doperpowers/specs/2026-10-31-session-manager-design.md` (its Interfaces section holds the commands, JSON shapes, entry kinds and state file). It is the manager skill's alone: no sminos verb, nothing in `sminos help` or the sminos skill.

`manager.py` puts `../../sminos/scripts` (resolved) on `sys.path` and imports `sminos`, `sminos_bridge`, `sminos_fork` (for `query`), `manager_ledger.py` (the state file and the ledger) and, through `manager_window.py`, `sminos_jobs`, `sminos_marks` and `sminos_subagents`. It never calls `sminos.main()`; one resolution pass per process, so no `forget_caches()`.

**Read-only.** Nothing here appends to a session's conversation, interrupts it, or writes to a project log; it never calls the functions behind `say`, `send`, `steer`, `interrupt`, `answer`, `decide`, `compact`, `model`, `charge`, `status` or a cursor-advancing `chat`. The writes are the manager's own state file and its archive; `query` puts its question to a fork, which the session never sees (the fork agent shows in its agent strip while it runs). `find_target` and `members` may let sminos reconcile a project's membership (`joined`/`retired`), as any sminos read does.

**Members.** `resolve` follows the spec's order: `sminos.find_target` first; a bare alias it does not find (it looks only in the caller's project) is matched exactly among the local members of every known project, two or more exiting 4 as `<project>/<alias>`; a full uuid membership no longer holds (sminos retires a seat-less session once its process ends) resolves `historical`ly from disk: the project whose log holds its own events, its transcript, its `continued_in` chain. A subscription resolves by the session id it stored (`resolve_stored`), on to `sminos_bridge.successor`. A member on another machine is refused (`<alias> runs on <machine>; …`, exit 1).

**Windows** (`manager_window.py`). The start is `sminos_subagents.offset_since` over an mmap (to within 1 MiB), then rows before `--since` are skipped; request records (`api-request`, most of a large transcript) and attachments no entry reads are passed over unparsed; `sminos.transcript_rows` (the whole file) is never used. Each row becomes at most one kind of entry per block; a tool call is settled by its result later in the feed (a message tool's call is `→you` at the call, from its input, so a window edge between call and result cannot lose it, and an error result in the window withdraws it; a result whose call lies before the window is skipped, its message having belonged to the window of its call; an agent's line takes 600 characters of its result unless that is the launch text; a blocking question its answer, `answered` with `source: "blocking"`); the async ask's `asked`/`answered` come from `sminos._ask_events` over the rows that can hold them (`source: "async"`). A `you·desk` or `you·desk?` entry carries `via`: `composer` (a MAWS launch's composer) or `bridge` (a bridge delivery). The JSON alone carries `source` and `via`; the text output is unchanged. A blocking question asked before `--since` still has its answer recognized, for each envelope (native, the plugin's `async: false` ask, MAWS's blocking ask): the rows between the seek point and `--since` are read for their calls only (`Classifier.prior`, no entries); a result whose call lies further back is matched to it through the call its row names (`sourceToolAssistantUUID`), found by a byte search back from the seek point that parses only the line found (`_row_back`, request records passed over); a row that names none is an answer only when it says so itself (the native `toolUseResult` with `questions` and `answers`, or MAWS's `{"status": "answered", "askId": <this call>}`). `--max-chars` counts rendered text (each entry plus its newline); the text output then ends with a line naming where it stopped. A transcript that cannot be opened or mapped raises `Unreadable` and the command exits 1 naming it (an empty one is an empty window); a lineage session with no transcript here is named on stderr and in the JSON's `missing`, unless the records prove it ended before `--since` (`ended_before`: a later session of the lineage has a transcript whose first row is at or before it; the engine prunes old transcripts, so a long-lived lineage loses its oldest).

**Provenance**, the part most likely to be subtly wrong. `you` needs an origin that affirmatively says the owner typed it (`human`, `composer`, `bridge`), or a `queued_command` attachment so stamped; an unstamped row that matches no known frame is `you?`; a MAWS launch's (entrypoint `sdk-ts`) owner rows are `you·desk` (checked on 90 MAWS-launched transcripts: the `human` stamp there is only on composer submissions and MAWS ask steers, the latter `answered`). `<message>` tags are taken out of the prose by the tags the marks parse itself reads (`sminos_marks.tag_tokens`, shared with `_parse_marked`), so a literal tag in code stays prose. A row of the bridge's plugin (`sminos`, or `doperpowers` from before the move), submitted `asUser` or appended `isMeta`, is read by its text: `STEER_LINE` a steer, `INTERRUPT_MARKER` / an interrupt note / `CUT_OFF_LINE` interrupted, a stop note or `WAKE_LINE` a notice, anything else a delivery. A delivery of several frames is split, each frame its own entry: another sender's a peer, the owner's `you·desk` when `OwnerWords` finds it among the owner's events addressed to this lineage (`sminos.addressed_to`; a chat frame by its `writer:seq` ref and exact text, a message frame or a bare text — MAWS's RL10 send — by an event's whole text), else `you·desk?`. One frame's evidence never vouches for another's. Peer envelopes (origin `peer`) are `peer`; one carrying a `senderTaskId` is a subagent's message or hand-back, `agent`. Other plugins' rows and anything unplaced are left out.

**Pending.** Unanswered async questions are read from each lineage session's own writer files in the log and the host store, matched to answers by `src`; `--until` keeps only what was asked and answered before it. `waiting` is the member's state now, which no record reconstructs for a past moment: with `--until` it is empty, `waiting_known` is false, and the text says so. `seen` is one entry per subscription (its stored `session`, which `ledger apply` takes back): its window from `--since`, else its `covered`, to `--until` or now, read forward by the same window reader (`seen_window`, no character budget; ~0.35 s for ten hours of a 669 MB transcript, ~1 s for a day); `seen` is the newer of the subscription's stored mark and the newest entry `manager_window.owner_present` accepts (`you`, a `composer` `you·desk`, a `blocking` answer); `last_activity` the newest entry. A subscription that does not resolve, runs elsewhere, has a session in its lineage with no transcript here that the window could include (the window's `missing`: an incomplete read, never an inactive one), or a transcript that cannot be read is listed with `error`, so the update leaves its `covered` where it was.

**The ledger** (`manager_ledger.py`). `ledger` prints it per initiative (`view`, the shape `ledger --json` and the page serve; the text is one line per item with its id, done and overtaken ones from the last 7 days only); `ledger apply (--file PATH | -)` is `apply`: the whole change validated first, every item as it would stand after the merge (fields by lane, kinds, enumerations, what each status requires, `seen` never back to false, ids known, sessions subscribed; unknown fields refused), any problem exiting 2 naming each with the file unchanged. Every present value is checked against its kind before any emptiness test, lookup or set operation reads it (a blank string is no text, `seen` only a boolean, `items`/`sessions`/`briefs` empty only when absent, an id or session that is not text refused), so malformed input is a named problem, never a traceback. New items take the lane's next id (`next`, never lowered); `reported`/`changed` are apply's stamps (a caller's are ignored), `changed` moving only for a substantive field (yours: `type`, `blocking`, `need`, `status`, `evidence`; work: `title`, `meaning`, `status`, `waits_on`). A listed subscription's `covered` moves to the value given only when its `from` is at or before the held one, never back; its `seen` to the newer. An owner's item filed under any session of a subscription's lineage then turns `seen` once the subscription's mark has passed its `raised` (the digest that read the window may not mention an older item, and a done one is not in its open list); the command resolves each lineage as `pending` does (`lineages_of`), one that does not resolve standing for its stored session alone, never failing the apply. Done and overtaken items whose `changed` is past 30 days are appended to `<name>.archive.jsonl` (0600) before the state is written. It reports `new`, `changed` and `unchanged_open` (open: yours not done or overtaken, answered included; work not done); text `P5: 2 new · 3 changed · 5 still open · brief written`.

**Query.** `manager query <member> "<question>" [--timeout S]` asks a fork of the member's newest session, through `sminos_fork`: its fork agent (`ask_fork_agent`, the bridge's `ask`, the question as asked, the bridge adding `ASK_FRAME`) when `bridge_offers(session, "ask")`, sent with an `rpc` nonce of its own so an end a module reload delivered to a new child before the stream was back is read from that child's kept file; otherwise, and when `ask` is refused `no-guard` or `spawn-refused` (the engine refuses a session stopped by Esc a spawn until it gets input), the headless fork (`headless_fork`, `FORK_FRAME` and the question, `--permission-mode auto --tools Read,Grep,Glob,Bash`, caching on) from where the session runs (a stand-in member for a session membership no longer holds, at the project's root when no `joined` names its directory). `busy`, `nothing-to-fork`, any other refusal or failure of the fork agent, and a silence past `--timeout` (default 300 s, either path) exit 1 saying why, with no fallback; a session another config dir holds is refused for the headless path (`foreign_config`), as is one in no project. Text output is the answer, then `via fork agent|headless fork · cache read N · cache write N · input N · output N`; `--json` is `{member, via, text, truncated, usage}`.

**State.** `$SMINOS_HOME/managers/<name>.json`, version 2, mode 0600, written whole by `sminos.write_json` (temporary file, rename); every read-modify-write (`subscriptions add|remove`, `ledger apply`) holds an exclusive `flock` on `<name>.lock` beside it. Times are stored as UTC with milliseconds; any ISO-8601 time is accepted, one with no zone read as local. A version 1 file (M1's `carry`/`briefed`) migrates on read (carry entries become yours items of type `other`, `briefed` becomes `updated` and each subscription's `covered`) and is validated as `apply` validates; a file that does not hold exits 1 naming each problem. Each subscription stores `session`, `alias`, `project` (the project's id, which historical resolution needs), `project_name`, `added`, `covered` and `seen`. `subscriptions add` resolves every member before writing, refuses the manager's own session (`CLAUDE_CODE_SESSION_ID` anywhere in the member's lineage) and remote members, starts `covered` 24 hours before now, and moves a member already subscribed under another initiative keeping its `added`, `covered` and `seen`.

**The skill around it.** `../SKILL.md` (`disable-model-invocation: true`: in the slash menu as `/sminos:manager`, in no model's skill list) is what the manager model reads: the update's procedure, the ledger's terms, the read-only and owner-only rules, the digest dispatch (Sonnet at the effort the replay chose). `../references/digest-brief.md` is the brief each digest subagent reads first, by path; it returns its items in `ledger apply`'s shape. The replay that chose the effort and set the work-item cap is `docs/doperpowers/specs/2026-10-31-session-manager-replay.md`. A change to either file is a change of behavior: rerun the pressure scenarios and, for the brief, a replay update, before relying on it.

Tests: `sminos/tests/test_manager.py` (run from `run_suites()` in `sminos/tests/run-sminos-tests.sh`, the `sminos-suites` gate); `query` runs against the real bridge child with `sminos/tests/bridge_standin.py` as its mod, which derive's cases in `run-sminos-tests.sh` use too, and a fake `claude` for the headless fork. `sminos/tests/mods/live-manager-check.py` runs `manager query` and `sminos derive` against a throwaway live session (acceptance 1, 4–7, 9, 10; by hand, not a gate; `--model` picks the session's model, which its forks inherit).
