# A repository is a project by its remote; the desk shows the active ones

The owner's target: connecting a machine to the org is `sminos hub enroll` plus the plugin, and from then on the desk shows and controls that machine's projects with no per-repository step. The platform around that (accounts, several orgs, invites, a web finder) is MAWS #52's later phase; this is its first step, and it closes nothing there off.

Today (`docs/doperpowers/specs/2026-10-18-smns-org-directory-design.md`, §1) a session on an enrolled machine resolves to its join override, else the launch directory's `.smns`, else the machine's own project. Every `.smns`-less repository session on `macbook` or `mini` is therefore a stray in `@macbook` or `@mini`, and the grid lists every project the org ever registered. After this change:

1. a session in a git repository with a usable remote and no `.smns` is in a hub project whose id is a function of the org and the normalized remote, so the same repository on either Mac, in any clone or worktree, is one project with nothing committed; a `.smns` still wins;
2. the grid shows the projects that have a live member, the rest behind "Show all".

To see it: open Claude Code in `~/Developer/GitHub/cua` on the MacBook (no `.smns`); `sminos project show` prints `source   remote origin → github.com/ssfskim/cua`; within a daemon tick the desk has a `cua` tile with one live session, and `sminos list --project cua` on the mini lists it too; a linked worktree of `cua` resolves there as well. `sminos chat macbook` shows `retired (moved to cua)` for the session that was a stray. The grid's other tiles are only projects with live sessions; "Show all (12)" reveals the rest.

Terms are the org directory design's (project, `.smns`, member, stray, machine project, followed, held, move, launch directory, the `org` frame, `org.json`). New: **remote key** — the normalized form of a repository's remote URL (§1); **remote-derived project** — a hub project whose id is computed from the org and a remote key. Note the name clash to avoid: a `.smns`'s `remote` field is the *log's* git archive, not the repository's remote; this design never reads that field.

## 1. Identity: the remote key and the id

**Which remote.** The owning repository's `origin`; when there is no `origin` and exactly one remote, that one; with several remotes and no `origin`, none (the session stays a stray in the machine project, and `sminos project show` says why: "remotes `a`, `b`, none named origin — name one origin, or `sminos project init --hub`"). A repository with no remote, or whose remote is a local path (`/srv/x.git`, `../y`), is a stray too: a path names nothing another machine can agree on. *Alternative:* the current branch's upstream remote (`branch.<b>.remote`) — lost because it varies per branch and worktree, so one repository would split by branch. *Alternative:* no-remote repositories become `local-<repo>`-style per-machine projects — lost: §1 of the org directory design made every session on an enrolled machine a hub project's member, and the machine project is that project.

**Reading it.** From `<common git dir>/config`'s `[remote "origin"] url` (the first `url` line; `pushurl` ignored), the common dir found as `_owning_repo_fs` finds it, so a worktree reads its main checkout's config. No git process: `git_branch` already reads `HEAD` this way, and the org directory's F1 showed what a process per directory per tick costs. `url.*.insteadOf` rewrites are not applied; normalization makes the usual ones (https ↔ ssh) moot.

**The remote key.** Parse the URL in its three forms — `scheme://[user[:pass]@]host[:port]/path`, scp-like `[user@]host:path`, and nothing else — and build `host[:port]/path` where: scheme and userinfo are dropped; host is lower-cased; the port is dropped when it is the scheme's default (22, 443, 80, 9418) and kept otherwise; the path has its leading `/`, trailing `/` and one trailing `.git` removed, repeated `/` collapsed, and is **lower-cased**. `git@github.com:SSFSKIM/MAWS.git`, `https://github.com/ssfskim/maws`, `ssh://git@github.com/ssfskim/maws.git/` are all `github.com/ssfskim/maws`; `gitlab.com/group/sub/repo` keeps its subgroups; `https://user:token@git.example.org:8443/a/b.git` is `git.example.org:8443/a/b`. Lower-casing the path follows GitHub, GitLab, Bitbucket and Gitea, which all redirect case variants to one repository; the price is that two repositories differing only in case on a case-sensitive host would merge, which is no real host's layout. *Alternative:* case-preserving — lost: the owner's own remotes differ in case between machines (`SSFSKIM/MAWS` vs `ssfskim/maws`), the split this design exists to end.

**The id.** `uuid5(NAMESPACE_URL, "smns-repo:<org>:<remote key>")`, the machine project's construction with another prefix. It is computed on the machine only; the hub needs nothing but a UUID (`PROJECT_ID`). The org is in the string so a repository is a project *per org*, as a machine is — under #52's several orgs that is the shape wanted. *Alternative:* an org-less id — lost: a project row belongs to one Registry, and an id shared across orgs invites exactly the cross-org leak #52 will have to rule on.

**The name.** The last path segment of the remote key's path *as written in the remote* (`MAWS`, `ci-kit`), through `safe_name`; the hub keeps the name of the first `hello` that registers a project (`registerProject`), so it is fixed at first sight. Two remotes with one basename (`github.com/a/tools`, `github.com/b/tools`) are two projects with one name: the grid shows both, `sminos projects` prints both with their ids, and name-addressing (`find_project`'s hub tier) is refused "ambiguous" naming the ids, as today for any clash; the fix for a project that matters is a `.smns` with a chosen name (§3). *Alternative:* `owner-repo` names — lost: every project pays an ugly name for a rare clash the id already resolves.

## 2. Resolution and registration

`resolve_project(cwd)` becomes: the first `.smns` walking up (a linked worktree without one, its main checkout's) → **on an enrolled machine, the remote-derived project of `owning_repo(cwd)`** → the machine project → (unenrolled) `local-<repo>` → none. `session_project` keeps its override ahead. The new step sits between the file and the machine project, so every existing rule holds: a join override is untouched, a `.smns` wins, a worktree reads its main checkout, a stray stays a stray. Unenrolled machines are unchanged (no org, no id).

The project is `make_project(id, name, "", owning_repo, hub_from_enrollment)`, kind `hub` (`project_kind` unchanged; no new kind: the hub, the `org` frame, `join`, `known_checkouts`, the spawn RPC and the desk all treat it as a `.smns` project). `project.json` gets the five fields, `root` the main checkout; `project_path` keeps a registered root that still resolves to the project (today's `root_kept` generalized), so a second clone on one machine does not rewrite it each tick — both clones are offered by `known_checkouts` through their sessions' `joined.cwd`. `sminos project show` gains a `source` line: `.smns at <dir>` / `remote origin → <key>` / `machine project` / the refusal above.

**How the hub learns of it:** through the paths that exist. The daemon's `map_sessions` registers a live session's project locally, the uplink's scan lists it (`hub_projects`: its `project.json` names the org), `hello` registers it at the Registry under its name, the `org` frame carries it to every machine, which follows it. **No hub change and no storage change for identity.** A project registers only when a session resolves to it or a verb runs in it — an old transcript directory registers nothing, so the ~1,500 directories on each Mac do not become projects; repositories used from now on do.

**Strays that move.** On the first tick after the roll, every live session whose launch directory now derives a project is retired `moved` in its machine project and joined (`by: move`) in the new one — M4's path, one interval, each project's reconciliation under the session file's lock (F3's fix). History stays in `@macbook`/`@mini`; the `moved` event names the new id; `@macbook/<alias>` is refused `moved to <name>`, `@short` keeps working. The burst is bounded by the repositories of live sessions (a dozen on the MacBook), each one hello and a few events.

## 3. `.smns`: the explicit, global declaration

`.smns` is not a legacy override: it is how a project is *declared* rather than inferred, and it stays optional. Without it a repository is a project by its remote with zero steps. With it the file wins, and it gives what derivation cannot:

- **a name** the owner chooses (`--name`), and the only answer to a basename clash;
- **one project across several repositories** — the same id committed in each (MAWS and a plugin repository, a monorepo split in two);
- **an identity pinned against the remote** — rename, transfer, a swapped `origin` (§4);
- **a project for a repository derivation refuses** — no remote, a path remote, several remotes and no `origin`;
- **identity on an unenrolled machine** — the file names the org, so the machine learns which project it is looking at and says so once a day (§2 of the org directory design); a derived project is nothing there.

To make "pin what you have" the common case, `sminos project init --hub` in a repository that resolves by its remote writes **that** id and name into the new `.smns` (not a fresh uuid4), so committing the file moves no session and splits no history; `--name` changes the name only. The fresh uuid4 stays for a repository derivation refuses.

**The `hub` field stays as it is** (`{"org": "ssfskim"}`, no URL). It still does its one job — a `.smns` without `hub` is a git-mirrored project, and that path exists for fleets with no hub — and changing it now means re-deciding the mirror. Under #52, who sees a project becomes the machine owner's choice at the hub; that is a policy on a machine's hellos, not a field in the file, so nothing here constrains it. The three committed files (doperpowers `09e88d10…`, ci-kit `cc28919f…`, MAWS `ebb30c31…`) are untouched now and later: their ids predate derivation, and removing a file would move its sessions to the derived id and leave history behind — a split for nothing. The only step they want is the one the org directory's run left open: the mini's doperpowers checkout at `dd970773` predates its `.smns`, so **pull it before the roll**, or it derives a second `doperpowers` from its remote.

## 4. A remote that changes

A rename or transfer on GitHub changes no local remote (the old URL redirects); the id changes only when someone runs `git remote set-url`, or clones under the new name. Then a purely derived id splits the project: old clones and new clones disagree until every remote is updated, and when they are, every session has moved to the new id and the old project holds the history.

Options weighed. **Pin per clone on first sight** (the id in `git config smns.project` or in sminos state keyed by the checkout): the pinned clones keep the old id while fresh clones derive the new one, so the split happens anyway — between clones, silently, and for as long as the old clones live; and it writes into repositories sminos did not create. Lost. **Accept the split**: every machine re-derives the same new id as soon as its remote is updated, the move is visible (`moved to <name>` in the old log, the old tile goes quiet and behind "Show all"), and nothing is written anywhere. **Recommended**, with one addition: when a registered root's remote key changes under it, sminos says so once per project (stderr from the verb that sees it, a `daemon.log` line; marker `warned-remote` beside `warned-url`), naming the old and new project and `sminos project init --hub` as the pin. **`.smns` is the answer** when identity must outlive the remote: pin it *before* the rename with `init --hub` (which keeps the current id, §3), and the rename moves nothing. A hub-side alias table ("these two ids are one project") is #52's platform work (it needs a web finder and an owner's say), and the recomputable id loses nothing by waiting for it.

## 5. The desk's "active" rule

**The count.** `Project.reportSummary` (MAWS `apps/desk-hub/src/objects/project.ts`) gains `live`: the session presence rows whose `record` is not null, from machines that are not revoked, **online or offline**. `record: null` is what a machine publishes once it sees a session's process gone (the plane's leavers), and reconciliation retires such a session within a tick, so this is "a non-retired member with a process", the owner's "idle, busy, or not retired". Offline machines count because a sleeping MacBook's projects are still where its sessions are (the tile already reads "Offline"); a machine that is gone for good is revoked, which drops its presence from every count. *Alternative:* online machines only, as `working` is counted — lost: a laptop that sleeps nightly would make the grid flap, and the tile's "Offline" already says the rest.

**Carried:** `SummaryReport.live` → the Registry's `summaries` table → `ProjectSummary.live` on the grid socket. **This is one storage change**, the only one in this design: `summaries` gains a column `live INTEGER NOT NULL DEFAULT 0` through the existing `ADDED_COLUMNS` path (an older report without `live` leaves the stored value: `COALESCE(excluded.live, summaries.live)`). *Alternative with no hub change:* the grid acquires every project's socket as the org view does and groups sessions from the logs — lost: the grid is the home screen and the phone, drawn before any log loads, and its doctrine is counts the projects report.

**The filter lives in the web.** `GridView` shows by default the projects with `live > 0 || waiting > 0` (a waiting project with no live process — a stopped seat's open question — is still the owner's to answer); below the tiles, `Show all (N)` reveals the rest and becomes `Show active`; the choice is kept in `localStorage` (`desk.grid.all`, beside `desk.depth`). `sortForGrid`, the "All sessions" button, `orgWaiting` and the push badge read the whole list as today. Machine projects follow the same rule (a machine with no strays hides). *Alternative:* the hub filters the `grid` frame — lost: "Show all" would then need a second frame, for a rule that is a view preference. Optional, same count: the org view acquires sockets only for projects with `live > 0 || waiting > 0`, which cuts its cost by the hidden projects' backlogs; and a tile can say `3 idle` where it now says "Quiet".

## 6. Privacy in a one-person org

Today a private repository's sessions already upload through the machine project: their `<message>` spans, `joined.cwd` (a local path that contains the directory name), `repo` basename and `branch`. New: the basename becomes a **project name on the grid and in the `org` frame**, and a project row for it exists at the hub for good (hub projects are never retired today). Not disclosed: the remote URL, host, owner and path — the id is a hash of them, and the name is the basename alone. The id is computable by anyone who knows the org and the remote; it is not a secret, and the org key, not the id, protects the log. Nothing changes for an unenrolled machine.

## 11. Risks

- **Projects accumulate.** Every repository used from now on is a permanent hub row and a followed project on every machine (one hello and lease each). Bounded by use, not by history; the grid hides the quiet ones; retiring a hub project is #52's. Watch `sminos projects` and the uplink's CPU as the count grows (`bench_scale.py`).
- **Two tiles of one name**: a basename clash, or the mini's un-pulled doperpowers clone. Visible, not silent; the pull is a pre-roll step, the `.smns` name the fix.
- **A remote that differs between machines** (one Mac's `origin` on a mirror) is two projects until the remotes agree; the remote-change line names it when the key changes under a known root, not when it differed from the start.
- **The roll's first tick** moves every stray in a repository at once: a burst of events and hellos proportional to live sessions. The F1/F3 fixes bound it to one interval; it is the one observation the live acceptance should time.
- **The storage column** is the one change the owner must approve; without it, M2 falls to the lost alternative in §5.

Where the build departs from or adds to the text above, and why:

- **The name is the one the id already has.** §1 names a project after its remote's spelling, fixed at the hub at first sight. Locally that alone flipped `project.json`'s name between clones that spell one remote differently (`Widget`, `widget`), and `@Widget/<alias>` then failed whenever the other spelling registered last. A derived project's name is the org directory's entry for its id (the hub's), else this machine's registration, else the remote's spelling; every machine converges on the hub's name. Found by `test-remote.sh`'s two-clones case.
- **The old key is recorded.** §4's line needs to know a registered root's project was derived and from which key: a derived project's home keeps `remote.json` (`{"key"}`), beside `warned-remote`, and `project.json` keeps its five fields. The scan for an old project runs only while the new id has no rooted registration here (its first sight), so it costs one look per new key.
- **A kept root must resolve to the identical project**, name and hub included, not only the same id: a checkout whose `.smns` names no hub must not keep a root its converted twin should take (the rule `hub_elsewhere` guards). The generalization holds for `.smns` projects too, so `test-hub.sh`'s registration race now starts from a checkout at an older head that named the project otherwise: a registration identical but for its root is kept, never written over, and the race needs one that is.
- **Schemes.** `ssh`, `git+ssh`, `ssh+git`, `git`, `http`, `https`; `file://` is a local path; any other scheme and `<transport>::<address>` derive nothing. Refusal texts never quote a URL (it may carry a credential).
- **The guide's machine line** reads "no .smns or repository remote claims your launch directory" (the eval-validated "no .smns" kept); a derived project's reads "the project of your repository's remote, <key>".
