## Purpose

After T1 and T2 every member is a thread that keeps its identity and is woken. What is still wrong is the parent's first fault: the unit of coordination is the directory a session was launched in. CH adds the declared channel: a named set of threads that crosses repositories and machines, made with one command, in which threads are placed without acting, and in which they speak. It is the parent's Purpose, second bullet, and nothing wider: a channel owns nothing, leads nothing by default, bounds no one's reach, and has no surface but the CLI.

## Design

The parent's D3, D5 and D6 are the design. What follows is what its cut needs settled with both halves in view. Marked **[binding]** where a child may not reopen it; the rest is advisory, and a child overturns it with evidence and a dated line in this document's Decision Log.

### C1. A channel has two readings of "its members", and they never mix

**[binding — both children read the same set for opposite purposes, and the wrong reader publishes a member under a channel id, which MAWS refuses, or writes a thread's fact into the wrong log]**

- **The roster** of a channel is derived and never stored: the threads whose membership (C2), read from each thread's own project log as the reader may read it, names the channel (D3). A row of it is the member's row in its own project's view and names that project. Where a thread's rows stand in several projects' views at once (a move or a refill across projects, read before the source's retirement arrives), the roster keeps the row its newest `joined` in effect points to, and neither at a tie. So a thread that went private, ended, or whose machine was retired is absent by the rules that already build that row, and where those rules leave a row standing for a reader (a narrowing whose withdrawn audience could not be named sends no notice today), the roster shows it as the project's view does.
- **The roster is a read of its own. A channel's view has no members.** `view_of` of a channel id returns none, by construction and whatever an older copy wrote into the channel's log, so every existing path that asks for the members of a log (delivery, tags, `@all`, the plane, the verbs that find a target) finds nothing under a channel id unless a child changes that path on purpose. A path that addresses through a channel takes the roster explicitly and keeps two things apart: the log an event is in, and the project of the thread it found. As built, a channel's log is reconciled by a function of its own (`_reconcile_channel`, reached from the daemon's `channel_pass`; the plane's refresh of a channel reads no view), and an import into a channel's log runs no project reconciliation and no delivery (`HubLog.deliver`). CH2 leaves both so: what a channel owes is delivered by the daemon's channel pass, which an import nudges, and by a sender's own call, from this machine's thread records; the uplink only asks the endpoint about a channel's messages and keeps each answer in a file for that pass to carry out (the holder's ruling of 2026-11-22 on the consumer thread, Decision Log).
- **A fact about a thread is written to the thread's own project,** whatever log the thread was found through: its lifecycle events, its in-charge line, its statements, its words to its human.
- **Nothing is published under a channel id.** No `member` frame names one as `project`, and there is no session presence, no machine presence, no checkout, no `joined`, no `state`, no restated snapshot, no `pending` set, no host frame and no word to a human (`message`, `question`, `answered`). A thread is published once, in its project, as today, and its frame there carries its channels (X5). One event about a thread is written under a channel id by this code: the `retired` (`moved`) that undoes a `joined` an older copy wrote there (C4). A `snapshots?` for a channel is answered with one page, empty and done, and a `subscribe` for one with the `end` a project gives for a session it does not hold.
- **Whether this machine opens a channel's log without `follow`** is read from this machine's thread records and from nothing else: it does while a thread of this machine that has not ended names the channel in `channels`. That is one of the two things MAWS needs to list the channel as known; the other is that thread's `member` frame, which goes out by today's rules. sminos does not try to keep the two equal: while a thread's frame is withdrawn (its record unreadable, its lane changed), MAWS stops counting it and the hello stays as it is. A channel no thread of this machine is in is followed, and the leaving rule lets it go as it lets a followed project go, but not while it holds a request this machine wrote that is still outstanding (not answered, not withheld or refused upstream, not expired): the pass that asks the endpoint visits open channels alone. From CH2 on, nor while a message this machine wrote into it has not gone up, and a write into a channel that already left brings its log back: a thread that is no member writes from a machine that may hold none (C5). An answer written on another machine is known to this one only once its uplink imports it, so an uplink started after that import keeps the channel followed until the request expires.
- **Whether a request names a thread of this machine** is likewise read from this machine's thread records.

The cache that holds a view is keyed on one log's files; a roster depends on other logs, and is kept only while every project view it read is still the one `view_of` returns.

*Alternative: a `joined` in the channel's log.* The parent rejected it (`known_checkouts` would make every member's directory a checkout of the channel, and membership would have two writers). *Alternative: `view_of` of a channel returns the roster,* so that delivery and tags work unchanged. It lost to the review: a verb that finds a thread through a log writes to that log (`find_target` returns the project searched, and `charge` appends there), and every publishing path would need an exclusion of its own.

### C2. The events

**[binding — X4 gives CH the names and shapes, and both children and every older reader meet them]**

Four kinds are added. None names anyone in `to`, so no installed copy delivers one or wakes a thread for it.

- **The statement,** kind `channels`, in the thread's project log, written by the thread's machine under the thread's current writer, stamped with `thread` as every lifecycle event is. Fields: `session` (the writer's own, and no other), `thread`, and `op`, the journal entry's id, as every event a journaled operation owes; `channels`, the whole set of declared channel ids, in the order they were added, `[]` for none; and, when it answers a request, `answers` (`channel`, `id`), `result` (`applied` or `refused`) and, for a refusal, `reason` (`not-reachable`, `read-only` or `limit`). A statement that refuses carries the set unchanged. A reader takes an event as a statement only when it has a `channels` list, a `thread` and an `op`, and takes from the list the strings that are channel ids, in order, each once, the first 128.
- **What a reader takes as a thread's membership** is the latest statement under the thread's current writer that follows that writer's `joined` in effect, with no `retired` in effect for that writer after it. A writer that has stated nothing since its `joined` states no channel, and a statement written after its writer's `retired` (a move between the record's write and the statement) states nothing. So a writer a thread returns to (a `join` back to a project, a reach that returns to an audience it had) never speaks with an old statement, and a thread in no channel needs none. The kind joins `LIFECYCLE`, so a view's row carries the set as the log states it (`Member.channels`); what the record holds, on the thread's own machine, is read apart (`channels_of`).
- **The request,** kind `channel-request`, in the channel's log, one event per target, written under the requester's writer there. Fields: `op` (`add` or `remove`); `session`, a session id the target thread has had, which is where the hub and the endpoint read whom an event addresses; `thread`, the target's thread id; and `id`, a value the requester mints for this request: 32 lower-case hex digits, and an event whose `id` is anything else is no request. As written, `session` is the target's current session as the requester reads it. A person at a terminal asks by a request under the machine's human writer. A request is signed and presented under the channel's id on every path: the append, the upload, the import and the endpoint's `reach?`. A request that names a private thread is written under the stream of the two audiences' meet, by the split a message's recipients get today, and is refused by the endpoint or withheld by the hub otherwise; the requester reads either as withheld, the first as not sent and the second as not reachable (C3). A thread that adds or removes itself writes no request, only a statement.
- **A machine added to the pool by hand,** kind `channel-env`, in the channel's log: `op` (`add` or `remove`), `machine` (a machine's name as the org's directory lists it) and `thread`, its writer's thread id, written by a member under its own stream in the channel's log. `channel env` is refused from a terminal, from a thread not in the channel, and for a machine the directory does not list. Honoured when the roster, as it is read, holds that thread and its row lists the writer's session among those the thread has had; the last by merge order holds, a machine's name compared without regard to case.
- **The lead,** kind `channel-lead`, in the channel's log, honoured only under a machine's plain human writer (never a phone's `hub/<member>` writer, never a session's). Fields: `thread`, the lead's thread id, or `null` for none; and, when it names a thread, a top-level `session`, that thread's current session as the writer's machine reads it. The `session` is there for the endpoint, which takes an event's audience from the sessions it names: the event that names a lead takes the audience of the thread it names, as a request does, and is written under the human writer's audience stream when that thread is private; `thread: null` carries no `session` and is plain, for the org. The last such event a reader may read decides, by merge order, and a lead that is not in effect (it ended, or it left the channel) leaves the channel with no lead: nothing falls back to an earlier one. A reader cannot know of an event it may not read, so the command writes a plain `thread: null` event before one that names a private thread: a reader that may not read the second reads no lead, and learns that the lead changed and not to whom. The endpoint uses only an audience it knows (a local session's from its member frame, one on another machine from its policy cache; while that cache rebuilds an unknown one is held, and after it a session the cache does not know counts as listed), which is today's rule for any reference across projects (MAWS's architect, 2026-11-22).

A statement names the request it answers by the channel and the request's `id`, never by the request's writer: the writer holds the requester's session id, the statement is read by everyone who may read the target, and a private requester would be disclosed to them (the parent's reason for a thread id that is no session's id). A request whose `id` an earlier request of another writer in that channel already carries is a duplicate: it is not carried out, and `channel show` says so. The first child built the first three kinds (CH1, sminos 1.54.0); the second builds the lead.

### C3. Carrying out a request

- **Where.** On the target's machine, by one function (`carry_out`, reached through the pass `carry_due`), under the thread's own transition lock, called from three places: the daemon's tick, over every channel registered on the machine, after that channel's reconciliation; the command that wrote a request for a thread of its own machine; and the uplink's pass that asks the endpoint about what the others left pending for its word. The uplink's pass tries every lock of a request's carrying out with a bound and finishes no other operation's open entry; finishing its own can still wait on a registration's lock without one (a row in TECH-DEBT): what it cannot do at once stays pending for the daemon. A request is carried out only for a channel registered on the machine. A machine carries out a request from elsewhere only while its endpoint advertises `channels`; without it the request stays pending. "From elsewhere" is told by what this machine appended, never by a writer's name (below).
- **Whom it names.** The thread whose id is the request's `thread`, if it is a thread of this machine that has not ended and has had the request's `session`, and if that session is not now another thread's current one: the hub judged the request against the session it names, and a session that has since become another thread's would lend that thread's reach. The session's owner is looked up over every record of the machine, ended and set-aside ones included, in the order a session's thread is resolved (`thread_of`). Such a request is carried out for neither and expires. So does one whose target's current session is lane B, for as long as it is: every pass judges afresh, and it is carried out once that session is lane A again.
- **Who may ask** **[binding — the parent's rule, in the one form a check exists for; agreed with MAWS's architect]**. A request is honoured when its writer may message the thread: the endpoint answers `deliver` to `reach?` for the request and sminos holds the request's sender as verified, or the request is this machine's own and its writer shares the thread's owners. A request is this machine's own when this machine appended it: it is one of the machine's queued appends, or the machine holds its receipt, a line written beside the log, under the writer file's lock, before the event, which nothing imported has (`appended_here`). A writer's machine name decides nothing, since a retired machine's reused name and a rebuilt home carry it too: a request under this machine's name with neither is an outside event, held to the endpoint's word, to the read-only policy and to its signer. A session's writer shares the thread's owners only where this machine holds a thread or seat record that has had that session; the machine's human writer does when the target's record, read then, names the machine's owners, never by the owners the endpoint last resolved. The rule is for requests: a message's path still reads the writer's machine name. An unverified sender is refused, though the endpoint delivers such a sender's words to a thread that is not private: a word is shown marked unverified, and an act has no such mark. The question is put for the thread's current session, about the request's own event (its channel, writer, position and hash, not its `id` alone), and its answer is used only if, under the lock, that is still the thread's current session and its reach has not changed since the question (the session's record's owners, access, shares and policy revision, compared as one value: `reach_token`); otherwise it is asked again. While the endpoint gives no answer (it holds no record of the thread yet) the request stays pending, as it does while the revocation set cannot be read. A refusal is read as refused whatever its reason word, and is not asked again. A reply that names no verdict, and a word that could not be committed, wait for the ordinary interval: nothing is asked again at the reply's speed. As MAWS's endpoint reads the question (its master `5346ff6d3`, `decideReach`; MAWS's architect, 2026-11-22, with no change to the endpoint): it finds the recipient by the question's own `session` alone, which sminos sets to the target thread's current session (`ask_of`), and not by the `session` inside the signed request, which may be one the thread has left; the sender needs no member row under the channel, whose id is the scope the event is signed over; and it answers `deliver` on a shared owner or a reach of `list` or wider, else `refuse` with `not-reachable`, or with `unverified` for an unverified sender to a private recipient. So two frames go up first, each under its thread's own project: the target's `member` frame before the question, and the requester's before its request is uploaded. One gap is accepted: sminos holds a sender as verified from when the request was imported, and the endpoint's answer does not say whether it delivered for a verified sender, so a sender removed from the org between the import and the answer is still honoured; closing it needs the answer to say which, a change in MAWS. The parent said "may converse with"; in MAWS `converse` is a rank above the one a message needs, and no check asks for it. A request that is not honoured gets a refusing statement with one reason: `not-reachable`, `read-only` (the machine admits nothing from outside) or `limit` (it would be the 129th channel).
- **One at a time, in order.** For one thread and one channel, requests are carried out in the order this machine reads them (the merged log's requests, then this machine's queued appends in the queue's order), and a request waits behind an earlier one for the same channel that still waits for its verdict. While a writer file or the queue of a channel is there and cannot be read, nothing of that channel is carried out: a later request must not pass an earlier one this machine could not see. A request also waits while the thread's record has an open journal entry. The new set is computed from the record under the lock, never from an earlier read, and the judgment made before the lock is made again under it, on files read as they then are and not as the process cached them. Last before the record's write, after the positions (below), one read checks that the session is still no other record's current one, is lane A (a record that is there and cannot be read defers the write), has the reach the endpoint's word was given for, and is a member of the project the statement goes to; a change in any of them writes nothing and gives the outcome the same change would have given a moment earlier. No lock is added: a move after that read is the reconciliation's to repair. Requests for different channels are not ordered against each other, so when two adds contend for a thread's last place under the limit, the first that can be carried out takes it. Across writers the order read is the merged log's, which is by timestamp: an add and a later remove by two machines whose clocks disagree by more than the time between them are carried out in the stamped order. The command says for each target what happened: applied, refused with the reason, pending and why, or not carried out and why (expired, a duplicate, naming no thread the machine can place). A thread's own add or remove that could not be recorded is a failure, said with its reason and exit 1, never pending: no request exists for a later pass to carry out.
- **Once.** The thread's record keeps the requests it has answered (`answered`: the channel, the request's id and its timestamp) for as long as a request can be pending, and a request it holds is not carried out again, whatever writer, project or absorbed record the answer was written under.
- **The record and the statement are one transition.** The record's `channels`, the answered request and the statement are written through the thread store's journal (X1: the record first, the event owed in `pending`, a replay finishing exactly that), not through `update`, whose contract is a change that owes no event. `set_channels` is the journal's operation, `channels`: the one writer of the record's set, of where its memberships began, of its answered requests and of the statement. Its entry owes the statement and nothing else, so a finisher of 1.51.0 or 1.52.0 carries it to the same end.
- **The log is kept equal to the record.** Whenever the membership a reader would take from the log (C2) differs from the record's set, the thread's machine states the set. Noticing the difference is a reconciliation, run where the machine already reconciles a project; writing the statement is always the same journaled operation, under the thread's lock and, as every transition of a thread does, its wake lock (a wake in flight is one more wait, said as pending), which reads the record, the thread's current session, project and writer there and writes nothing if any of them moved or the record has an open entry. So a reconciliation that read an older set never states it. It is not a step attached to a `joined`: it holds after a continuation, a refill, a `join`, a return, a change of reach, a renamed machine, a `joined` an older copy wrote, and a stop between two writes. Between a `joined` and the statement that follows it, other machines read the thread as in no channel. Two limits, as built: the comparison runs only on a machine where a channel is registered, so a set made only of channels not registered there is not restated; and where the newest membership events name two projects at the same moment, no project is current and nothing is stated until a later event decides.
- **A provisional thread that is absorbed** gives its channels to the thread it continues: the continuing thread's set, then the job's additions, up to the limit; an addition past the limit is dropped and said in the daemon's log. Where each brought membership began comes with it, and the two records' answered requests are united, one entry a request.
- **What the requester is told,** then and in `channel show`: *applied* or *refused* with the reason, from the statement that names its request; *refused: not reachable*, when the hub withheld the request at its own position; *refused: not sent*, when the requester's own endpoint refused the audience the request went under, the target's reach having changed before it was signed (both read `withheld` in `channel show --json`, with the reason `not-reachable` or `audience`); *not carried out*, for a duplicate (C2); *pending*, with the machine the target was last seen on and since when, which covers a machine that is off, one whose sminos or MAWS predates channels, and an answer the requester may not read; and nothing, once the request is seven days old by its own timestamp, when it is expired and no longer carried out. A clock wrong by days misjudges that (a request stamped eight days behind is never carried out); it is accepted.
- **What is refused before anything is written.** `channel add` of a session that is no lane A thread, or of a thread that has ended or holds no session, where the requester's machine can see that; an add or a `create` that would be a 129th channel, where it can see the set; a target the stream choice refuses; `create` of a name that is no valid name, or that a log known on the machine already answers to; and `add`, `env` and `create`'s revival of a channel the machine's current enrollment does not carry (a channel that left this machine aside, since placing a member is what brings it back; `remove` is never refused for it). The plan's Interfaces §8 holds the whole list and its sentences. One exception: where a first member's reach narrows while `create` registers the channel, nothing is appended and the registration is left with no member, which the same command run again brings back.
- **The record keeps where each membership began.** For each channel in a thread's set the record holds the positions of the channel's log, as this machine held it, when the thread entered: written in the same record write that puts the thread in the channel, written anew when an ended thread returns (a channel whose log cannot be read then aside, below), and carried unchanged to a session that continues the thread and to the thread that absorbs a provisional one. The positions are read just before that write and no lock holds the channel's log still meanwhile, so an event imported between the read and the write counts as gained after it; the same holds for the order of requests, where a request that arrives after the last read is carried out as one that arrived later. A thread is owed only what this machine's copy of the channel's log gained after that, so a message the machine held before a removal, or received between a removal and an add, is never pushed to a later membership. The positions are the machine's own when the membership began, not the sender's time of sending: a message written elsewhere during an earlier membership and imported only after a later add lies past them and is owed, as a message to a thread that is a member when it arrives (accepted, 2026-11-22). An empty boundary stands for a log that held nothing and also for a channel not registered on the machine then. The boundary belongs to the thread, not to a session: a session id that comes to be another thread's does not carry it, and nothing of it is written into a log, since the positions name other members' writers. An add over a channel's log that is there and cannot be read writes nothing and fails: it has no earlier positions to keep. A return over one keeps that channel's positions from before the end, writes the others anew, commits and says so in the daemon's log (one line, which a stop between the write and the line can lose); so does every return an older copy makes, which writes none. What the channel gained while the thread was ended then counts as gained after its membership began, and CH2 may push it once at the return, in those cases alone. A return must not wait on a log the thread only reads; an unknown-boundary marker, a third state every older finisher would have to read, was weighed and not taken (the holder's ruling, 2026-11-21). CH1 keeps the boundary though nothing is delivered yet: a later release cannot reconstruct one that was not kept. The field is `began`, `{channel id: {writer: seq}}`, read through `began_of`; an empty object means the log held nothing then. *Alternative: marking the thread's delivery records at each change* (this document's second form). It lost to the review of CH1's plan: a delivery record is keyed by session, so a mark could settle another thread's mail, and an older copy that finishes a journaled entry skips a step it does not know, where it leaves a record's fields alone.
- **Adding wakes no one.** A request for a stopped thread is carried out by its machine's daemon while the thread stays stopped.

### C4. The wire

**[binding — the parent's X5 and D6, with what the code adds]**

- `is_channel_id` is MAWS's predicate, tested against the shared vectors' `ids`.
