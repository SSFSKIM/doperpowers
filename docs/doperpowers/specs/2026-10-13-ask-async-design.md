# AskUserQuestion with `async` — one way to ask the human, waiting or not

In a doperpowers session with function hooks on, the model asks the human
through one tool, `mcp__doperpowers__AskUserQuestion`: the built-in
AskUserQuestion's input exactly, plus `async`. With `async` false (the
default) it is AskUserQuestion: Claude Code's own dialog opens at once —
the tab bar across the questions, ←/→/Tab between them, ↑/↓ and Enter,
previews beside the options, notes with `n`, "Type something", "Chat about
this", the review page before Submit — and the call returns the engine's own
answer text. With `async` true the call returns at once and the model works
on; the questions wait in the human's view behind an `[ answer ]` button,
and pressing it opens that same dialog. Submit sends the answer to the
model: beside its next tool result while it is working, or as a new prompt
when the session is idle. The built-in AskUserQuestion is withdrawn from the
model while this tool exists, and the to-human style's `<need-input>` mark,
which served the waiting-free case with a text grammar and inline buttons,
is retired.

What the human can do after this that they could not before: answer a
question the agent asked without stopping it, in the full dialog — several
questions at once, previews, notes — instead of one-question text marks with
one-click choice buttons; and the agent can ask without parking itself when
it has other work. To see it: start a session with the plugin
(`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir <repo>`), ask the
model to ask you two questions asynchronously and then run a long command;
press `[ answer ]` while the command runs, answer in the dialog, and watch
the model quote your answer after the command's result.

The human's conditions, stated when they chose this design (2026-10-13):
the tool works exactly as AskUserQuestion does and differs only by the
`async` parameter; it is AskUserQuestion's superset and replaces
`<need-input>`; and everything the dialog offers — the key bindings
(←, →, Enter, Esc), the floating tab bar, what an agent can draw in each
question (descriptions, previews), notes with `n` — is the same. Where this
spec falls short of that, it says so: a tool already running beside a
declined blocking ask (Design → Blocking); a blocking refusal's text,
which the model reads wrapped in `<tool_use_error>` (every hook deny is,
and a hook cannot mark a result as an error otherwise); and a picture pasted into an
async ask's "Type something", which reaches the model as a file path it
reads rather than as an image block (Design → Blocking → Images).

## Terms

- **The engine dialog** — the form Claude Code draws for an AskUserQuestion
  call. A plugin cannot draw it from scratch; it reaches it through
  `$.ui.ask` (below).
- **Function hooks / the mod** — TypeScript modules the engine loads from
  `hooks/hooks.json` → `modules` under `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`
  (`hooks/mods/register.tsx` registers each mod). `$` is the engine
  interface every hook receives; its types are in `.claude/types/claude-code.d.ts`
  (regenerated by `/plugin-types`, gitignored). This feature is a new mod,
  `hooks/mods/ask.tsx`.
- **A hook dispatch** — the engine running one of the plugin's hooks for an
  event (`tool.call`, `ui.press`, …). Code running in a timer callback or a
  detached promise after the hook returned is outside any dispatch.
- **Widening** — replacing the one question `$.ui.ask` sends with the full
  question set (previews and all) in the mod's own `tool.call` hook on
  `AskUserQuestion`, before the engine draws the dialog.
- **An ask** — one call of the new tool. **Blocking** when `async` is false
  or absent, **async** when true. An async ask is **open** until its answer
  is delivered.
- **Delivery** — handing an async ask's answer to the model (two routes,
  below).

## How the engine is reached (probed 2026-10-13, Claude Code 2.1.296)

Each fact below was observed in a live session with a probe plugin
(`/tmp/askprobe`, not kept); the evidence lines are in Surprises &
Discoveries.

1. A plugin cannot call the AskUserQuestion tool itself:
   `$.tool.call({ tool: 'AskUserQuestion', … })` is refused with
   `runs the AskUserQuestion tool: that is $.ui.ask (host check)`.
2. `$.ui.ask(question, { options, header, multiSelect })` opens the engine
   dialog with that one question (option labels only), idle or mid-turn —
   the model's turn runs on underneath — and raises a `tool.call` of
   AskUserQuestion. It resolves to the chosen label and rejects on Esc and
   on "Chat about this" alike (`$.ui.ask: no answer (The user doesn't want to
   proceed with this tool use. …)`).
3. When `$.ui.ask` is raised inside one of the plugin's hook dispatches, the
   engine leaves out only the calling hook (`hooks 4 left out for re-entry
   (origin askprobe#4)`); the plugin's other hooks see the AskUserQuestion
   call. So the mod's own `tool.call` hook on `AskUserQuestion` can pass
   `next({ ...e, questions: fullSet })`, and the engine draws the whole set —
   tab bar, previews, notes, review page — exactly as for a model's call, and
   resolves `next` with the full record (`answers`, `annotations` with notes)
   and `text`, the result text the model would read. Raised outside any
   dispatch (a `$.clock.after` callback), the whole plugin is left out
   (`skipped: re-entry (the plugin's own code raised it; origin askprobe)`):
   **every ask must be opened from inside a hook dispatch** — the tool's own
   `tool.call` hook (blocking) or a `ui.press` hook (async).
4. Widening at render time is refused: a `ui.render` rewrite of the
   AskUserQuestion dialog `may relabel the questions but not change how many
   questions there are`, nor add previews. Descriptions may be added there,
   but widening at `tool.call` makes that moot.
5. A `$` call's time never counts against the calling hook's budget (the
   types say so; observed: a blocking ask answered after 120 s returned
   normally).
6. A `tool.describe` hook answering `isDeferred: true` for `AskUserQuestion`
   moves the built-in to the deferred list (`tool.describe AskUserQuestion: a
   hook set isDeferred false -> true`; the transcript's `deferred_tools_delta`
   lists it). Only the name stays in the model's view.
7. Delivery mid-turn: a `tool.call` hook (no matcher) that returns
   `{ ...result, context: [text] }` for the next main-loop tool call puts
   `text` in front of the model right after that result; the transcript
   stores it as an `attachment` of type `hook_additional_context`. The model
   quoted it.
8. Delivery while idle: `$.prompt.submit({ text })` starts a turn; the
   model reads `The doperpowers plugin sent a message:\n<text>\n\nThis is how
   Claude Code surfaces a prompt a plugin submits between turns — …`. A
   submit while a turn runs waits for the session to go idle (types:
   "a turn of its own, once the session is idle").
9. `$.prompt.fill` + the human's Enter delivers mid-turn as the human's own
   words (`queued_command`, `origin: human`) — the route `<need-input>` used.

What the built-in does, read from the extracted bundle
(`~/claude-code-bundle/2.1.292/cli.pretty.js`, diffed against 2.1.296's
binary: the dialog and result code are identical but for identifiers; the
full study is `docs/doperpowers/specs/2026-10-13-ask-async-engine-reference.md`,
background only — this section carries what binds):

10. **Result text** (`mapToolResultToToolResultBlockParam`, L838029): per
    answered question `"<question>"="<answer>"` (or `=(no option selected)`),
    then ` selected preview:\n<preview>` and ` notes: <notes>` when present,
    joined with `", "`. All answers plain option labels and no notes →
    `Your questions have been answered: <summary>. You can now continue with
    these answers in mind.`; free text or any notes → `The user answered:
    <summary>. Read the answers carefully — they may request clarification,
    changes, or that you not proceed — and follow what they actually say.`;
    nothing answered → `The user did not answer the questions.`
11. **Esc** (and Cancel on the review page, and Enter on an empty "Type
    something") refuses the call: the model's tool result is `The user
    doesn't want to proceed with this tool use. The tool use was rejected (eg.
    if it was a file edit, the new_string was NOT written to the file). STOP
    what you are doing and wait for the user to tell you how to proceed.`
    and **the turn is aborted** (`cancelAndAbort`, L205856).
12. **"Chat about this"** refuses with feedback: the result is the same
    first two sentences, then `To tell you how to proceed, the user said:\n`
    and a block beginning `The user wants to clarify these questions.` that
    lists each question with the answer recorded so far. **The turn
    continues.**
13. **Validation** (zod, L837822): 1–4 questions; 2–4 options; `question`,
    `header`, `label` and `description` required strings; question texts
    unique and option labels unique within a question (`Question texts must
    be unique, option labels must be unique within each question`); the
    top-level object strict. The header's "max 12 chars" is description
    only — never checked. Errors read `InputValidationError: …AskUserQuestion
    failed due to the following issue(s):` with one line per issue
    (`<tool_use_error>InputValidationError: [<steer>\n\n]AskUserQuestion
    failed due to the following issue[s]:\n<issue lines></tool_use_error>`),
    and a question with fewer than two options prepends this steer,
    verbatim: `This call included a question with fewer than 2 options, so
    it was rejected and the person never saw it. A question with a single
    option has no decision in it. Do not retry this call and do not invent a
    filler second option. Instead, state the one path you were going to
    offer as the approach you are taking, then continue with the task. If
    this call also contained questions with 2 to 4 options (each with
    distinct labels), you may re-ask those questions alone in a new call. Ask
    a question only when the person has at least two genuinely distinct
    choices.`
14. **Subagents never have it**: the subagent tool filter (`xl`, L6052)
    drops every tool in a set that includes AskUserQuestion (`I(e)`,
    L689962).
15. **Transcript rows**: none while the dialog is open; answered →
    `⏺ User answered Claude's questions:` then, under `⎿`, one dim row per
    answer, `· <question> → <answer>`; refused → `⏺ User declined to answer
    questions` then `· <question> (<opt> / <opt>)` per question.
16. **A refusal of the mod's own ask** (probed): Esc on a dialog opened
    from a `ui.press` hook while the model ran a 40-second command did not
    abort the model's turn — the command finished and the model went on.
    The widening hook's `next` resolved with an errored result whose
    `result` read `Error: The user doesn't want to proceed with this tool
    use. … STOP what you are doing and wait for the user to tell you how to
    proceed.` (the engine's cancel-and-abort applies to the model's own
    call, not to a plugin's).
17. **Concurrent asks queue in the engine** (probed): an async ask's dialog
    open, the model raised a blocking ask; the second `$.ui.ask`'s
    AskUserQuestion call reached the mod's hook at once (`origin
    {"plugin":"askprobe","tier":"user"}`), was widened there, and its dialog
    appeared when the first was answered. The mod needs no dialog queue of
    its own. (A hook's own time is bounded — 10 s, paused only during its
    `$` calls and `next` — so a hook must never wait on anything else.)
18. **A held answer attached to a plugin-raised call is lost** (probed, the
    failure the reviews predicted): with answer A held, the second ask's
    nested AskUserQuestion result took it as `context`
    (`answer attached to AskUserQuestion result`), and the model reported
    that no answer arrived. `context` reaches the model only on the model's
    own calls; a dispatch's `next.origin` tells them apart (`{ plugin:
    "engine", tier: "core" }` for the model's).

## Design

### The tool

`mcp__doperpowers__AskUserQuestion`, registered at `session.start` of an
interactive session (`{ isInteractive: true }`), as `compact.tsx` registers
its tools, and kept inline with a `tool.describe` answer of
`isDeferred: false` so the model reads its schema and description in every
request. Named after the built-in so the model's prior about AskUserQuestion
carries over; the plugin prefix is the engine's (`mcp__<plugin>__<name>`).
Rejected: a new name (`ask`, `ask_async`): the human's condition is that it
*is* AskUserQuestion plus one parameter.

**Input schema**: the built-in's model-facing schema verbatim (Interfaces),
minus `answers` and `annotations` — those are the permission component's
channel for collected answers, never the model's — plus:

```json
"async": {
  "type": "boolean",
  "default": false,
  "description": "<the async paragraph, below>"
}
```

**Description**: the built-in's own description, captured from the
built-in's `tool.describe` input as the engine raises it while the session
starts (`$.tool.list()` cuts descriptions at 300 characters — M1 found it),
followed by one paragraph on `async`. Reading it at runtime keeps the guidance the engine
ships for its own tool (when to ask, the preview format) in step with the
running engine. If `$.tool.list()` has no `AskUserQuestion` (a session that
disallowed it), the mod registers nothing and withdraws nothing: the
dialog's tool is not there to be reached. The async paragraph (copy is a
decision; M3's eval measures it):

> `async`: set it to true when you can go on with other work while the human
> decides. The call then returns at once; the questions wait in the human's
> view until they answer, and their answer reaches you in a later message
> that quotes each question. Leave it false when the work is blocked by the
> answer, nothing useful can proceed without the answer, or the answer is the
> last thing left in your turn.

**Validation**: an async ask has no engine call at the moment it is made,
so the mod validates every ask at once, before any dialog, against the
built-in's rules (fact 13) — and not the header length, which the built-in
never checks — and returns the built-in's error form: the
`InputValidationError` head naming `AskUserQuestion`, one line per issue,
the uniqueness message verbatim, and the fewer-than-two-options steer
verbatim. The wording of zod's own per-field messages is not pinned (the
engine reference marks it inferred); the shape and the two verbatim texts
are. If the engine validates a plugin tool's input against its
`inputSchema` before the mod's hook runs, its message stands for the cases
it catches; record which form the model sees in Surprises & Discoveries.

### Blocking (`async` false or absent)

The tool's `tool.call` hook adds a pending entry (the question set and a
token unique in the session, `ask-<n>`) to the mod's list, calls `$.ui.ask`
with the first question's text and option labels and the token as the
header, and awaits it. The mod's `tool.call` hook on `AskUserQuestion` sees
that call and claims the entry whose token is the call's one header — only
when the dispatch's `next.origin.plugin` is this plugin (`doperpowers`), so
a model's own call of the built-in can never claim an entry (fact 18's
identity). The token, not the question text, is the correlation: two
concurrent asks with the same first question still each claim their own.
It widens the call to the entry's set (the real headers with it), and
binds what `next` resolved to that entry; the tool reads its outcome from
there. (Should widening ever not happen, the human sees the token where
the header goes — visible, harmless, and a sign to look in the debug log.)
The tool returns:

- answered: `{ result: <next's text> }` — the engine's own result text,
  verbatim (observed: `Your questions have been answered: "Which
  backend?"="SQLite" selected preview: … , "Which layout?"="Stacked". You can
  now continue with these answers in mind.`);
- refused at the dialog: the refusal's text from `next`, verbatim, as the
  tool's error result (fact 11 or 12). A refusal without the user's
  feedback (Esc, Cancel, an empty "Type something": fact 11) also ends the
  model's turn, as the engine ends it for the built-in — the engine does not
  do it for a plugin's ask (fact 16), so the mod does, at the boundary
  after the tool batch has resolved and before the turn's next model
  request: either a `classic.PostToolBatch` hook answering
  `{ preventContinuation: true }`, or a main-loop `turn.step` hook that
  ends the turn without sending (`$.turn.abort({ turnId })` with the id
  `turn.start` handed the mod). M1 picks by a live probe of both, on these
  criteria in order: the refusal text is the call's recorded result; no
  model request follows in that turn; nothing is drawn beyond the declined
  row (a stop-reason line, an `Interrupted` marker). Ending it inside the
  tool's own hook is out: the result is recorded after the hook returns,
  and an abort there would replace it with an interruption. Until that
  boundary the refusal sets a **turn latch**: every later model-made
  main-loop tool call of the same turn — one queued behind the ask in its
  batch, a second ask — is refused before it runs with `Not run: the human
  declined the question asked in this turn.`, where the built-in's abort
  would have cancelled it; and a turn that ends with the latch set counts
  as stopped by the human for delivery (Async → Delivery), whatever
  `reason` its `turn.complete` carries — `preventContinuation` does not
  abort, so the engine may report it as `answer`. The latch clears at the
  next `turn.start`. One accepted difference: a tool already running in
  parallel with the ask when the refusal lands finishes, where the
  built-in's abort would cut it. A refusal with
  feedback ("Chat about this": fact 12) returns its text and the turn
  continues. Told apart by the text: fact 12's carries `To tell you how to
  proceed, the user said:`.

The principle: the model cannot tell this tool's blocking call from the
built-in's — same dialog, same result text, same turn outcome.

The entry leaves the list in a `finally` when its `$.ui.ask` settles, so a
stale set never widens a later ask. Every ask raises its dialog at once,
whatever else is open: the engine queues the dialogs (fact 17), so no hook
of the mod waits on anything but `$.ui.ask` itself.

**Images.** A picture pasted into "Type something" reaches the built-in's
model as a content block beside the result (engine reference §8.1). The
widened call's `next` carries no bytes — its answer reads `(Image
attached)` — but at paste time the engine writes each pasted image into the
session's pasted-image store, the one prompt pastes use (`[Image #N]` is
`N.png`; debug log `Stored image 1 to <temp root>/<project slug>/<session
id>/images/1.png`). So the mod lists the store before `$.ui.ask` and again
when it settles; the files that appeared are that dialog's pastes, in
number order. They are not what the human kept: removing a paste in the
dialog drops only the dialog's entry, and the file stays. Nothing a hook
can reach names the kept ones; the only signal is the engine's `(Image
attached)` mark, one per answer that kept at least one. So the pastes go
to the model only when the count of marked answers equals the count of new
files; otherwise none go, and a debug line says so. A removed picture is
not sent, at the cost of dropping two pictures kept in one answer or one
on a multi-select question (whose answer is never marked). One case the
mark cannot tell apart: the mark is not reserved, so a human who removes a
paste and then types an answer ending in `(Image attached)` themselves is
read as having kept it — recorded as a known limit; only an engine signal
for the kept attachments would close it.

- **Blocking (parity)**: each new file is read with `$.fs.read(path, { as:
  'bytes' })`, its `media_type` taken from the extension, and the tool
  returns an array of API content blocks — the engine's text block, then one
  `{ type: 'image', source: { type: 'base64', media_type, data } }` per file
  (probed: the model described the image). The built-in puts its images
  beside the tool result; these sit inside it, which reads the same to the
  model. No new files → the plain string, as before. Two result forms fail
  and are not used: an object `{ content: [...] }` (the output-shape check
  allows string | array | undefined), and the MCP image form `{ type:
  'image', data, mimeType }` (the API rejects it, `image.source: Field
  required`, and the engine strips it).
- **"Chat about this"**: the built-in sends kept images with the feedback
  refusal; a hook deny is text only, so the refusal text is followed by one
  `[Image source: <path>]` line per kept paste, which the model Reads.
- **Async**: no delivery route carries image bytes (`context` and a
  plugin's prompt are text, and a plugin prompt's images are not expanded),
  so the delivery text appends one line per kept paste (the rule above),
  `[Image source: <path>]` — the engine's own line for an image's source
  file — and the model opens it with Read.
- **Locating the store**: derived from what the engine gives the mod (the
  session id, the project slug, the temp root) or found by the store's own
  layout, never a hard-coded `/private/tmp/claude-<uid>`. Not found → the
  text-only outcome, and a debug-log line saying so.

Known limits, in `hooks/mods/README.md`: an async image arrives as a path
the model has to Read; the store is the engine's temp directory, cleaned
with old sessions, so a path delivered long after can be gone.

### Async (`async` true)

The tool's `tool.call` hook validates, records the ask as open (its
`tool_use_id`, the question set), redraws, and returns at once:

> Your questions are waiting for the human; this call does not wait for
> them. Their answer will reach you in a later message that quotes each
> question. Go on with work that does not depend on it.

**Where the human sees it.** The call's transcript row (every ask, blocking
or async; drawn by M2) draws what the engine draws for the built-in (fact 15): nothing while a
blocking dialog is open; `⏺ User answered Claude's questions:` with its
`· <question> → <answer>` rows once answered; `⏺ User declined to answer
questions` with its rows once refused. First try rewriting the `ToolUse`
props to the built-in's (`tool: 'AskUserQuestion'`, the input, the result
record) so the engine draws its own row; if the component refuses the
rewrite, draw the same lines with the mod's own elements. An open async ask
is the one state the built-in has no row for: it draws `⏺ Claude asked
(answer when ready):` with one dim `· <header> — <question>` row per
question and `[ answer ]`. In the to-human view the row stays in the
report, as the built-in's does (`isRead` in `hooks/mods/to-human.tsx`).
Above the prompt, while any ask is open: `N open question(s) · [ answer ]` (drawn pluralized: `1 open question`, `2 open questions`),
the button opening the oldest — an async question scrolls away while the
model works, and this keeps it reachable.

**Composing with to-human.** Both mods draw in the same places, and
`register.tsx` loads every mod into one hooks module, where `$` may only be
passed to functions of the same file (the engine refuses a module that
passes it across an import: "`$` is followed only into a function declared
in this same file, never across an import"). So the mods compose by
registration order, as `agents.tsx` wraps what `kairos.tsx` draws in the
footer (the hook registered first is the outer one, and reaches the inner
one through `next`): `to-human.tsx`'s `AbovePrompt` hook draws its band
without calling `next`, so the ask's `AbovePrompt` hook must be outer — it
draws its line above `await next(e)`; `to-human.tsx`'s `ToolUse` and
`ToolResult` hooks pass a read row (`isRead`) through `next`, so the ask's
row hooks must be inner. `hooks/mods/ask.tsx` therefore exports two
registration functions, `registerAskBand(on)` (the `AbovePrompt` hook) and
`registerAsk(on)` (everything else), and `register.tsx` calls
`registerAskBand` before `registerToHuman` and `registerAsk` after it.
`to-human.tsx` imports only the constant `ASK_TOOL`.

**Answering.** A press on either button runs the ask through the same path
as a blocking ask, from inside the `ui.press` dispatch (fact 3): a pending
entry, `$.ui.ask` with the first question, the mod's AskUserQuestion hook
claims, widens, and binds `next`'s outcome to the entry. A press on an ask
whose dialog is already raised (open or queued) does nothing. Then:

- answered → delivered (below); the ask turns answered and every row and
  the above-prompt line redraw.
- Esc → nothing is delivered; the ask stays open and can be answered later.
  This is the one place async differs from blocking, by meaning: in a
  blocking ask Esc refuses the call the model is waiting on; in an async ask
  nothing waits, and Esc means "not now".
- "Chat about this" → its refusal text (fact 12: the user wants to clarify,
  with the answers recorded so far) is delivered exactly as a blocking call
  would have returned it, and the ask turns answered: the model learns the
  human wants to talk these questions over, which is the button's meaning.

**Delivery** carries exactly what the blocking call would have returned,
headed by which ask it answers:

> The human responded to your async AskUserQuestion (call `<tool_use_id>`):
> `<the engine's result text>`

("responded", not "answered": a "Chat about this" delivery is a refusal
with the human's feedback, and the head is true of both.)

The call id is for the mod (finding answered asks on resume); the model
matches the answer to its questions by the question texts the engine's text
quotes. Route:

- the session is idle when the dialog is submitted → `$.prompt.submit` at
  once (fact 8): the human's Submit is the act that starts the turn.
- a main-conversation turn is running → the answer is held. Held answers
  form a queue, and every held answer goes out together, one `context`
  entry each, at the first of:
  - the result of the next **model-made** main-loop tool call: a `tool.call`
    dispatch whose `next.origin.plugin` is `engine`, with `e.agentId`
    undefined, whose result is not a `deny` (fact 7). Never a plugin's own
    call — the mod's nested AskUserQuestion, another plugin's `$.tool.call`
    — whose `context` the model never reads (fact 18). The queue is taken
    and emptied in the same synchronous step that builds the context, so two
    results resolving together cannot both take it or both miss it.
  - the turn's `turn.complete` with `reason: 'answer'` → one
    `$.prompt.submit` carrying them all.
  - a turn that ends otherwise — the human interrupted it, the turn latch
    was set by a blocking refusal, an error — leaves them held: a stop the
    human made is not undone by a prompt the mod submits. They ride with
    the human's next prompt, as `context` added by a `prompt.submit` hook,
    or go out by the first two routes if the model runs again first.

  Every route takes the held answers by one reservation: the queue's
  current contents are moved out in one synchronous step, so no other
  route can take them too. A route that cannot fail (a tool result's
  `context`) is done when it returns. A route that can — `$.prompt.submit`
  resolving `{ drop }` or rejecting, the human's prompt dropped by a later
  hook (its `next` resolving `{ drop }`) — on failure puts its answers back
  at the front of the queue, ahead of any answered meanwhile, keeps their
  asks reading answered-but-undelivered (the row says `not delivered yet`),
  toasts why, and lets the next route try again. An ask's row reads
  delivered only after its route succeeded.

Rejected: filling the prompt box for the human's Enter (fact 9, the
`<need-input>` route). It delivers as the human's own words, mid-turn, but
it takes a second Enter after the dialog's Submit — the built-in's Submit
delivers, and the human's condition is parity with it. The cost of the
route taken is the framing: the model reads the answer as relayed by the
doperpowers plugin, which is what it is.

**Resume.** At `session.start` of a resumed session the mod rebuilds its
open asks from the transcript. An ask is one the tool accepted: a
`tool_use` of the tool with `async` true whose paired `tool_result` is
`ASYNC_RESULT` exactly and not an error, and whose input still passes
`validateQuestions`. A call the tool refused (validation, a subagent), one
the permission layer denied, and one interrupted before its result are not
asks and are never rebuilt. Of the accepted asks, one whose id a later
delivery names (`(call <id>)`, in any of the forms a delivery is stored
in: a `hook_additional_context` attachment's `content`, a plugin-submitted
user row's text, and whatever row a `prompt.submit` hook's `context` is
stored as — M2 confirms that form live) is answered, its answer read from
that delivery; the rest are open.
The transcript path comes from the classic `SessionStart` payload's
`transcript_path`, as `hooks/mods/agents.tsx` takes it. An answer held for
delivery when the session ended is lost with the process; the ask then reads
open on resume and can be answered again.

### The built-in withdrawn

While the tool is registered: a `tool.describe` hook on `AskUserQuestion`
answers `isDeferred: true` with the description
`Withdrawn in this session: ask through mcp__doperpowers__AskUserQuestion,
which takes this tool's input plus async.`; and the mod's `tool.call` hook
on `AskUserQuestion` refuses, with that sentence, every call from the
model (origin `engine`) or from this plugin that does not claim a pending
entry (Design → Blocking: this plugin's origin, an unclaimed entry, the
entry's token as the call's one header). Another plugin's `$.ui.ask` is
that plugin's own dialog and passes. The withdrawal applies from the moment
an interactive session starts — the engine describes the built-in once,
before registration resolves, and caches it — and is lifted if registration
fails. Rejected: a permission deny rule or
`disallowedTools` — `$.ui.ask` is a `tool.call` of AskUserQuestion through
the permission check, so a rule that removed the built-in would remove the
dialog with it; and a plugin cannot write a session's rules.

The mod's own ask is told from a model's call by the dispatch's origin,
which the host sets and no plugin can write (fact 18): a model's call of
the built-in, even with a question text equal to a pending entry's, is
refused and claims nothing.

### Subagents

Subagents never have the built-in (fact 14). The engine hands every
subagent every MCP tool and a hook cannot filter the list per agent
(CLAUDE.md, `hooks/` row), so a subagent's call of the new tool is refused
in its `tool.call` hook (`e.agentId` set) with `AskUserQuestion is for the
main conversation: report what you need to the agent that dispatched
you.`, as `compact.tsx` refuses its tools. The agent
definitions that withhold `AskUserQuestion` (`agents/plan-executor.md`,
`agents/task-executor.md`) withhold `mcp__doperpowers__AskUserQuestion` too,
and the definitions that withhold the compact tools (every agent under
`agents/`) withhold it as well, so its schema does not ride in their
context.

### `<need-input>` retired

- `output-styles/to-human.md`: the paragraph from "Input you need from the
  human" through "it is AskUserQuestion, not the mark." and its example are
  replaced by one paragraph: input you need from the human you ask for with
  AskUserQuestion; when you can go on with other work while they decide, ask
  with `async: true`. The frontmatter `description` drops `<need-input>`;
  `maws-to-human-contract` goes from 2 to 3, the grammar MAWS reads having

## Outcomes & Retrospective

2026-10-13, at finish. `mcp__doperpowers__AskUserQuestion` shipped as
designed. A blocking ask opens the engine's own dialog, widened inside the
mod, and returns the built-in's result text byte for byte (acceptance 1:
the recorded results compared `IDENTICAL`). An async ask returns at once.
Its questions wait in the human's view, in their row and in the band above
the prompt. The answer reaches the model beside the next model-made tool
result, or as a plugin prompt when the session is idle, or with the
human's next prompt after a stop. The built-in is withdrawn, and
`<need-input>` is retired to a read-alias of `<message>`. Acceptance 1–13
passed live on the finished branch. The eval met its bar on the second
style round: S1 async 3/3, S2 blocking 3/3, S3 3/3, with zero marks and
zero built-in calls. In the before arm, the model produced a usable S1
question in only one run of three.

What moved during the build:
- Images came into scope mid-build. Blocking asks carry kept pastes as
  image blocks; async deliveries and "Chat about this" carry them as
  `[Image source: <path>]` lines.
- The engine facts the spec did not have were found by live probes and
  recorded in Surprises & Discoveries:
  - `$.tool.list()` truncates descriptions at 300 characters;
  - `tool.describe` fires before registration settles;
  - plugin tool input is not schema-checked;
  - every hook deny is wrapped in `<tool_use_error>`;
  - `context` on a cut call is dropped;
  - a plugin tool's `tool_use` row is written only once the call resolves.
- The turn-end boundary stayed `$.turn.abort` plus an empty step. The
  probe showed the abort spares running work, and the no-abort variant
  would run Stop hooks.
- Reviews caught real losses at every frontier:
  - removed pastes that would have been sent;
  - answers lost on a rejected prompt pass;
  - a human quote read as a delivery;
  - a truncated search rebuilding silently;
  - an abandoned rewind branch resurrected on resume;
  - a same-response sibling result dropped by the first ancestry fix.

Known limits, each recorded in `hooks/mods/README.md`:
- a blocking refusal reads wrapped in `<tool_use_error>`;
- a removed paste is sent if the human ends their own answer with the
  engine's literal `(Image attached)`;
- an async image arrives as a path the model Reads, and the path can
  expire with the engine's temp store;
- the over-4-MiB resume search has no ancestry and a 4 MiB output ceiling;
- an in-session rewind leaves the abandoned branch's asks in view until
  resume;
- a hot reload drops the asks until the next start or resume.

Lesson: the spec's style summary, written before any run, missed twice in
round 1. The old style's guard sentence, dropped in the summary, was what
the model needed. Behavior-shaping copy should be carried over from the
validated text and trimmed, not re-summarized.
