# The sminos org directory: every session in the org can find, judge, and reach every other

The owner runs many Claude Code sessions that collaborate across three repositories (doperpowers, ci-kit, MAWS) on three kinds of machine (the MacBook `macbook`, the Mac mini `mini`, the devcloud hosts), all enrolled in one desk-hub org, `ssfskim`. Today a session finds a peer in another repository only when the owner pastes its name; the harness's own `ListAgents` sees one machine; a bare sminos `@alias` never leaves the sender's project; and a session in a directory that is no project (the home directory, `~/claude-code-bundle`, a one-off clone) is invisible to every other session and to the desk.

After this change every session on every enrolled machine is in a project the hub syncs, so any session can run `sminos list --org`, `sminos find <words>`, `sminos projects` or `sminos machines`, read who works on what anywhere in the org — alias, kind, state, machine, project, repository and branch, in-charge line, activity — judge for itself whom to talk to, and reach that session with `sminos say "@short …"` or `"@<project>/<alias> …"`, the message recorded in both projects' logs and delivered through the receiver's own machine. A session whose directory misfiles it declares its own project with `sminos join`. The owner sees every live session of every project on one desk screen, those waiting on them first. sminos replaces the harness's `ListAgents` (board ticket #93 is absorbed here, and where this design supersedes #93 it says so), and once the evals hold the owner denies `ListAgents` in their settings.

To see it working: on an enrolled machine, in any directory, `sminos list --here` prints every session the harness's `ListAgents` would, each with its kind and a state that agrees with the engine's record; `sminos find ci-kit` prints the ci-kit sessions on every machine; `sminos say "@mini/mini-7c did the devcloud image build?"` from a doperpowers session arrives in the `mini-7c` session (a home-directory session on the mini) as a peer message with a reply line, and `sminos chat` in both the doperpowers project and the mini's machine project shows it; the desk's org view lists that session among every other, with the ones waiting on the owner at the top.

## Terms

Terms from `docs/doperpowers/specs/2026-10-13-smns-project-log-design.md` ("the log design") keep their meaning: project, `.smns`, member, alias, short, writer, event, log, projection, daemon, frame, internal fork. Terms from the desk's design (`docs/doperpowers/plans/2026-10-15-desk-dc4-uplink.md`, DX2/DX3/DX4) too: the hub (the Cloudflare Worker at `apps/desk-hub` in MAWS and its Durable Objects — the `Registry`, one per org; a `Project` per project; a `Machine` per enrolled machine), the uplink (`skills/sminos/scripts/sminos_uplink.py`, the daemon's child holding the machine's one stream to the hub), the plane (`sminos_plane.py`, the uplink's session plane: this machine's sessions' presence and the desk's subscriptions to their transcripts), `hello` (the frame that opens a project on a stream), the lease (a machine is online in a project while its lease is fresh), presence (DX4's session and machine messages). `board:<n>` names an entry of #93's board audit trail (its answers at board:643, the live comparison at board:646). New here:

- **Org** — the desk-hub org a machine is enrolled in (`$SMINOS_HOME/daemon/hub.json`'s `org`, written by `sminos hub enroll`); `ssfskim` for the owner. Every project whose `.smns` names the org, every enrolled machine, and every machine project together are **the org's directory**.
- **Enrolled machine** — one whose `daemon/hub.json` names a hub, an org and a machine name (`sminos_hub.held()` reads the file without exiting when it is absent; `sminos.machine_identity()` gives the name). Every other machine is **unenrolled**.
- **Machine project** — a hub project the hub creates for each enrolled machine, with no checkout anywhere: the project of every session on that machine that no `.smns` claims. Its id is a UUID v5 of the org and the machine's name (Interfaces and Dependencies), its name is the machine's name as enrolled, and in a tag it is `@<machine>/<alias>`. Written `@mini` in prose.
- **Stray** — a session on an enrolled machine whose working directory resolves to no committed `.smns`: a home-directory session, one in `~/claude-code-bundle`, a one-off repository. A stray's project is its machine project.
- **Followed project** — a hub project of the org that a machine opens on its stream only to read and deliver (it has no checkout of it and no session in it). A **held project** is one the machine has a checkout of or a session in. Which a project is on a machine can change.
- **Join override** — a session's declaration that it works in another project than its directory says (`sminos join <project>`), kept at `$SMINOS_HOME/sessions/<session-uuid>.json`.
- **Move** — a session's resolved project changing while it runs (a `.smns` committed or removed under it, a join override): recorded as `retired` with reason `moved` in the old project and `joined` in the new one.
- **Copy** — the record of a cross-project message in the sender's own log, marked `copy`, which delivers nothing.
- **Engine record** — `~/.claude/sessions/<pid>.json`, what the harness writes for each running session (`name`, `sessionId`, `cwd`, `kind`, `status`, `pid`, `entrypoint`, `nameSource`, `updatedAt`); the same records the harness's `ListAgents` reads. `sminos.peer_records()` reads them.

## 1. Every session on an enrolled machine is in a synced project

A session's project is resolved in this order, by one resolver, `session_project(session, launch_cwd)` in `skills/sminos/scripts/sminos.py` (§7), where `launch_cwd` is the session's **launch directory** (§1c), never the directory it happens to be in now:

1. its join override, when the file exists and names a project known here;
2. the launch directory's `.smns`, walking up (`resolve_project` as today), with the worktree rule of §1a;
3. on an enrolled machine, the machine's own machine project;
4. on an unenrolled machine, the local project of the owning git repository, `local-<repo>`, as today; a directory in no repository is no project, as today.

Consequences, each a decision:

- **One project per session, and every session on an enrolled machine is in a hub project**, so every one is synced to the hub and visible on the desk. The alternative, keeping strays out of every project and listing them from engine records alone (#93's "(no project)" group), lost because a stray could then be reached only from its own machine and only unrecorded, and the owner's scope revision made every session a directory entry.
- **`@all` is refused in a machine project** with "a machine project is not a team: tag who you mean". Its members share nothing but a machine.
- **`local-*` logs are not migrated.** On an enrolled machine step 3 comes before step 4, so no `local-<repo>` project is resolved again: every `.smns`-less repository session is a stray. The `local-*` logs stay under `$SMINOS_HOME/projects/local-*/`, readable with `sminos chat local-<id>` (by id: §4's name rule gives the name to the hub project), and the first reconciliation after this change retires each live session in one `moved` to its machine project (§1a); history stays where it was written, because migrating it into a hub project would upload every stray's past to the hub, which no one asked for.
- **Seats keep their group namespace** (`derive_group`, the seat key `group/alias`): the alias namespace and lifecycle lock stay per owning repository. Two same-named seats spawned in two non-hub repositories on one machine are both members of `@<machine>` and make a bare alias ambiguous there; a tag's refusal names each as `alias#short` (`resolve_tags`), a verb's as `group/alias` (`find_target`), and either resolves.
- **doperpowers and ci-kit get a committed hub `.smns`**, in the same milestone that switches the fallback to the machine project (M3), so a machine project only ever holds strays: home-directory sessions, `~/claude-code-bundle`, one-off repositories. Landing the files after the switch would put every doperpowers and ci-kit session of the fleet into machine projects for a while and move them later (§1a); landing them together costs nothing. **Both files are org-only, `{"hub": {"org": "ssfskim"}}`, with no `url`**, as the design decided: both repositories are public and their history is never rewritten here, so a URL committed there is disclosed for good. The cost is a window: the plugin installed on the fleet until this release reads a `hub` without `url` as malformed (`read_smns` warns on every verb and files the project as a hub project nothing feeds), so between the merge that lands the files and the roll of the new plugin every doperpowers and ci-kit session warns and syncs nowhere. The roll follows that merge directly — every enrolled machine at once, the Macs and the devcloud hosts (Constraints) — so the window is minutes. The alternative, carrying the `url` through the transition and dropping it later, lost: a permanent public disclosure set against a window of minutes.

### 1a. A repository that gains or loses a `.smns`; linked worktrees

- New sessions in the repository resolve to the new project.
- Live sessions move. A session whose resolved project changed — a `.smns` committed or removed under its directory, or a join override written (§7) — is retired in the old project with `reason` `moved` and `project` the new project's id, and joined in the new one with `by` `move` and its real `cwd`, by the same path `sminos join` takes (§7). Reconciliation does it, in every reading verb as today; the daemon's tick bounds it to one interval: each tick first maps every running engine session to its project through `session_project`, which registers a project not yet known here (`project_path` writes its `project.json`), so a project that appeared this tick is ticked this tick; then each project's reconciliation retires its local members whose session now resolves elsewhere and joins the sessions that resolve to it. One tick may join before it retires: a dual membership of one interval, accepted. This replaces the critic's "transient dual membership" as the steady state with a one-tick one.
- **A checkout that loses its `.smns`** (the file removed, or changed to another project) does not take the project off this machine: the project stays registered and eligible by its `project.json` (§3), becomes followed rather than held (`known_checkouts` offers a root only while the root's `.smns` still names the project), and its `moved` retirements upload like any event. Today `hub_projects` drops a project whose root's `.smns` stops naming the hub, and `Link.tick` then ends the stream (`gone = opened − known`); the drop goes — the org's directory, not a checkout's file, says which projects exist, and a `.smns` edit on one checkout must not strand the retirements it causes — while `Link.tick`'s path stays for what still leaves `hub_projects` (a retired project, §3).
- History stays in the old project's log; the `moved` event names the new project, and a tag that names the old project (`@mini/<name>` for a session that moved into a repository's new project) is refused with `<name> moved to <project>`; `@short` keeps working, since it resolves org-wide (§5). The desk's transcript view of a session does not depend on its project.
- An explicit join override is untouched by a `.smns` appearing: the override is step 1.
- **A linked worktree at a head that predates the `.smns`** resolves it from its main checkout: when the walk from the directory finds no `.smns` and `owning_repo(cwd)` (the main checkout, by the common git dir) differs from the directory's toplevel, `<main checkout>/.smns` is read if it exists. `skills/issue-tracker/scripts/_binding.sh` already resolves `board.json` this way ("a linked worktree reads the main checkout's file when it has none of its own"), for the same reason: a board worker checks out the head it was dispatched for, and an old branch must not split the repository into two projects. The alternative, requiring every branch to carry the file, lost there and loses here.
- Other machines move their sessions when they pull the commit, or at once through the main-checkout rule once the main checkout has it.

### 1b. The scope widening, stated

Before this change a stray recorded nothing: `hooks/smns-record.sh` exits, before Python starts, where no `.smns` or `.git` lies above the directory; the bridge's export (`sminos.export_live`) appends nothing where `resolve_project` finds no project; and `derive --all` covers members only. After it a stray on an enrolled machine is a member of its machine project, so its `<message>` spans and async asks are exported to that project's log and uploaded to the hub (the owner approved this on 2026-10-18), its presence is published to the hub, and `derive` covers it. The hook's cheap look stays and admits every directory when the enrollment file exists (`${SMINOS_HOME:-~/.claude/sminos}/daemon/hub.json`), since on an enrolled machine every directory is a project. `SMNS_INTERNAL` forks stay excluded everywhere (`sminos.internal_pids`, the hook's first line), as do headless and SDK runs (`HEADLESS_ENTRYPOINT`). On an unenrolled machine nothing widens.

### 1c. A session's directory is where it was launched

A session's project is resolved from its **launch directory** — the directory the engine started it in, which also keys its transcript directory (`~/.claude/projects/<encoded launch directory>/`) and which `claude --resume` needs to find the transcript — and never from the directory it is in now. An agent's `cd` moves no session: not when it shows in the hook payload's `cwd`, in the engine record's `cwd`, or in the transcript rows' `cwd`, all of which follow the shell. Only a `.smns` change that resolves the launch directory differently (§1a), `sminos join` (§7), or the engine's own relocation of the session — a human's `/cd` or `EnterWorktree`, which move the transcript to the new directory's folder and stamp a `relocated` row — moves a session; the launch directory is the engine's own reading of the session's directory, the latest `relocated` row's `relocatedCwd`, else the transcript's first row's `cwd` (M4).

- `session_project` takes the launch directory for every consumer §7 names: the record hook (`cmd_record`), the bridge export (`export_live`), and `_local_sessions` (through it the plane's presence). The engine record's `cwd` cannot serve here (it follows the shell); the launch directory is read once per session and cached (the transcript's first row's `cwd`, or `CLAUDE_PROJECT_DIR` where a command hook's environment carries it — M4 verifies which sources hold it and how a worktree entered with `EnterWorktree` records it).
- `joined` carries the launch directory as its `cwd`: Resume (the RPC) and `known_checkouts` read it, and a `joined` written while the session was `cd`'d elsewhere would otherwise record a directory Resume cannot use.
- `list` shows the launch directory as a row's `cwd` (the `joined` one; M1's row rule) — the directory that names the session's project and resumes it.
- A worktree the engine moves a session into (`EnterWorktree`) resolves to the same project through §1a's main-checkout rule whichever directory the transcript records.
- Rejected: following the current directory — today's behavior, which split one session's exports across two projects (Surprises & Discoveries, 2026-10-18), and which once doperpowers' `.smns` lands (M3) would write a `moved`/`joined` pair on every `cd`. Rejected: sticking to the first project a session joined, an accident of where its first export ran.

## 2. `.smns` names the org; the enrollment knows the URL

- The shape for a new hub project is `{"project": "<uuid>", "name": "<name>", "remote": "", "hub": {"org": "ssfskim"}}`. The hub's URL comes from the machine's enrollment (`sminos_hub.enrolled_hub()`), so moving the hub never means editing committed files in three repositories. `sminos project init --hub` writes this shape from now on. `read_smns` and `hub_wellformed` accept a `hub` with `org` and no `url`; `resolve_project` fills the `url` from the enrollment on an enrolled machine, and the `Project.hub` every reader sees is `{url, org}` as before.
- A present `url` is tolerated (MAWS's `.smns` has one today). When it differs from the enrollment's, sminos warns once per project on this machine — a stderr line from the verb that first sees it and a `daemon.log` line, remembered by a marker file `$SMINOS_HOME/projects/<id>/warned-url` (its own file: `uplink.json` is written whole by the uplink from its own read, so a verb's key there would race) — and never refuses: the enrollment's URL is used. Refusing would make a committed file an outage.
- On a machine not enrolled in the org the `.smns` names (no enrollment, or another org), the project is a **local project with a hub marker**: `Project.hub` is `{"url": "", "org": "<org>"}`, so `mirrored()` stays false and git never syncs it (a `remote` it names is the log's archive, as today), the uplink never opens it (`hub_projects` matches the org), and a reading verb prints once a day `project <name> syncs through the desk hub of org <org>; this machine is not enrolled (sminos hub enroll)`, remembered in the project's `daemon.json`. No sync at all for a hub project outside a hub: two transports were worse than none in the log design, and remain so.

## 3. Every enrolled machine follows every org project

- **The `org` frame** (Interfaces): the hub sends the org's directory down each machine's stream — every project the Registry holds, with its kind (`hub` or `machine`) and whether it is retired, and every enrolled machine with whether it is online and when its online state last changed (`seen`). It goes out on `welcome` (the `Machine` object asks the `Registry` for it as it opens the stream), again whenever the `Registry` registers a project, and whenever a machine's online state or enrollment changes. The uplink keeps the latest at `$SMINOS_HOME/daemon/org.json` with the time it arrived; `sminos projects`, `sminos machines`, and the filter layer read it. A frame pushed on the stream rather than a `GET /machine/org` the uplink would poll, because the stream is already open and a poll adds a second clock; rather than per-project `machines` frames from every followed project, because those name a project's machines, not the org's, and carry no project list.
- **Follow-only hellos.** For each project in the frame that this machine does not hold, the uplink writes a `project.json` with `root` `""` and the frame's name and hub, and opens it with `hello` carrying `follow: true`. A follow-only hello starts the machine's lease as any hello does (so the stream's heartbeats keep it and a half-open stream lapses), but the `Project` records `follow` on the lease, excludes such leases from `reportSummary`'s `machines` and `machines_online`, and a follower posts no `machine` presence and no session presence (it has none), so it is out of the project's `machines` frame. When a followed project gains a local member (a `join`, §7), the uplink's next scan sends `hello` again with `follow: false` and the machine's presence, and the hub updates the lease; when the last local member leaves, the next hello says `follow: true` again. The alternative, counting followers as machines of the project, lost because the grid's "2 machines" would then read "every enrolled machine" for every project and say nothing.
- **Eligibility** becomes "the project's `project.json` names this org's hub, and `org.json` does not mark it retired", whether or not it has a root (`sminos_uplink.hub_projects`); the root's `.smns` decides held versus followed (§1a), never eligibility. **`org.json` is the one local source of a project's kind and retirement** — `hub_projects`, `sminos projects`, `find_project`'s name rule and `join`'s eligibility read it, and this machine's own project is known by `machine_project`'s id; `project.json` keeps its five fields (`project`, `name`, `remote`, `root`, `hub`) and nothing else, because `project_path` rewrites it from those five whenever the file differs, on every verb and every tick, so any other key there would be erased within an interval. With no `org.json` yet (a daemon that never connected) nothing is retired. RPCs, Resume included, therefore work on rootless projects: a Resume names the session's real `cwd` from its `joined`, which the plane already uses. A project the frame marks retired leaves `hub_projects`, which ends the stream and reopens it without that project (`Link.tick`'s existing path; there is no close-one-project frame, and a revocation is rare enough that a reconnect is accepted).
- **`known_checkouts` returns `[]` for a machine project**, explicitly: a stray's working directory resolves to the machine project and would otherwise be offered as a checkout. So a desk spawn into `@<machine>` is refused `unknown-checkout`; a scratch-session spawn can come later.
- **Machine projects at the Registry.** The `Registry` registers a machine's project (`kind` `machine`, the machine's name) when the machine's enrollment is confirmed (its first authenticated request), computing the id as the Terms define it, so the project is on the grid and in the `org` frame before the machine's first hello; the machine's own uplink hellos it as a held project (its strays are its members). When a machine is revoked, its machine project is marked `retired` at the `Registry`: the `org` frame says so, every uplink stops following it (and removes it from its `hub_projects`), `sminos projects` hides it (shown with `--all`), and its `Project` object keeps the log for history. **A machine enrolled again under the same name** (DX7 releases the name on revocation; MAWS's `test/enrollment.test.ts` covers re-enrollment) computes the same project id: its confirmation reactivates the project (`retired` cleared; the `org` frame and the grid say so), every uplink that kept the registration follows it again on the frame that says `retired: false`, and the new machine's strays join the old log, which stays the machine's history. The alternative, a fresh id per enrollment, lost because a machine project's id must be computable from the org and the name alone: the uplink hellos it before any frame arrives (the held-project rule above).
- **Machines' online state at the Registry**, for `sminos machines` and the `org` frame: each `Project` already reports a summary to the `Registry` when its counts change (`reportSummary`); the report gains the project's machines with whether each is online (follow leases included, since a machine that only follows is still online), and the `Registry` keeps per machine whether any project reports it online and `seen` (Interfaces). Half-open streams lapse through the `Project`'s lease alarm as today, which changes the report. A retired machine project is removed from every open grid at once: the `Registry` sends the whole `grid` again without it (the frame exists; `GridClient` replaces its list on a `grid`), since a summary upsert cannot remove a row. The alternative, the `Machine` object telling the `Registry` on stream open and end, lost because the `Machine` object knows only TCP open and close: a half-open stream (a suspended daemon) is detected by the lease, which lives in `Project`, and duplicating the lease and its alarm in `Machine` is a second state machine for the same fact.
- **Measured cost** (the critic's reading, 2026-10-18): the MAWS hub log is 364 KB (about 235 events), desk-walk 240 KB, local-doperpowers 1.5 MB; every project on the MacBook totals 3,195 events. After the backlog, live traffic grows only with message volume.

## 4. One list with filters, plus project and machine lists

Every list prints the same row:

    alias [short]  kind  state  @machine  project  repo@branch  in charge: … (age)  · active <age>

- `alias [short]`: the alias and the session's eight-hex short, always (today `#short` appears only on a collision; the short is how a session is reached org-wide, §5, so every row carries it).
- `kind`: `interactive`, `bg`, or `seat` (sminos spawned it); from the engine record locally, from `joined`'s `session_kind` remotely (it travels on `joined` from M1 on; an older `joined` shows `?`). The log field is `session_kind`, never `kind`: `kind` is every event's discriminator (`joined` itself), and `lifecycle(project, session, kind, **fields)` takes it positionally.
- `state`: the word as today (`busy`, `idle`, `waiting`, `stopped`, `gone`, `vacant`, `retired`); for a remote member its last published word. **Liveness and the live word come from the engine records, for a seat as for a seat-less member**: a member is live when an engine record names its session and its process runs (`session_running`: pid alive and the same process), and its word is the record's `status`; only when no running record exists does the word fall to `stopped`/`gone` by the transcript. Today a seat-less member already reads so (`_member`, from `_local_sessions`), while a seat's word probes its inbox socket (`state(seat)` → `peer_for_session` → `peer_live`) and falls to `stopped` when the socket is quiet: that path moves to the record. The socket's answer decides delivery, never the word. Today the only guard against resuming a running process whose socket is quiet is the harness's copy banner after the launch (`push_member` falls to `seat_state(fresh, None)` → `stopped` → `resume_session`, and `copy_started` stops the copy): M1 makes `seat_state(seat, None)` consult `session_running`, so delivery's stopped fallback never launches a resume of a running process. This is the fix for #93's finding (board:646): `devcloud setup` read `stopped` in sminos while the engine's record said `interactive`/`idle` — M1 reproduces that case against the record first, since a seat-less session's word could also come from `same_process` disagreeing with the record's `procStart`.
- `@machine`, `project`: as the log says.
- `repo@branch`: the owning repository's basename and the branch of the session's working directory; read live for a local row (`sminos_policy.git_branch`), from `joined`'s `repo` and `branch` for a remote one (as at join; a branch change is not republished — it is a detail, not a fact worth an event).
- `in charge: … (age)`: the in-charge line with the age of its event; `· active <age>`: the engine record's `updatedAt` locally, the last `state` event's `ts` remotely.

Verbs and filters:

- `sminos list` with no filters shows the caller's project, as today. `--json` carries the new fields (`kind`, `cwd`, `repo`, `branch`, `charge_age`, `active_age`, `project`, `project_id`, `project_kind`).
- Filters combine, each takes a comma list, and **any filter widens the scope to the whole org before narrowing it** (the org here is every project known on this machine, which on an enrolled machine is every org project, §3, and on an unenrolled one every local project):
  - `--project MAWS,doperpowers` (name or id; a machine project by its machine's name);
  - `--machine mini,devcloud`, where a name matches a machine by prefix, so `devcloud` matches every devcloud host;
  - `--state waiting,busy`;
  - trailing `<words>` match, case-insensitively, the alias, the short, the project, the repository, the branch, the in-charge line, the status ("now") line and the title.
- `--org` means no narrowing at all. `--here` is shorthand for `--machine <this machine>`, and also lists, under `(no project)`, every running engine session on this machine whose directory resolves to no project — the sessions `ListAgents` shows and nothing else does; after M3 that set is empty on an enrolled machine, and the group is the unenrolled machine's. `sminos find <words>` is shorthand for `list --org <words>`. `--all` keeps its meaning (nothing folded).
- Rows are grouped under a project heading when one project is shown, and flat with the project column when several are.
- **A project's name resolves once, in `find_project`, for every verb and tag that takes one** (`list <project>`, `--project`, `chat`, `--in`, `join`, `@<project>/<alias>`): an exact id first; then by name among hub projects, then machine projects, then `local-*` projects — a `local-*` project answers to its name only when no hub or machine project has it, and always to its id. Without this, doperpowers' committed `.smns` makes every name-addressed verb die "ambiguous" on the owner's machines, where `local-doperpowers` (named `doperpowers`) already has a `project.json`.
- `sminos projects` lists every project known here: name, kind (`hub`, `machine`, `local`), its live and waiting counts, and the machines with sessions in it; a retired machine project only with `--all`. `sminos machines` lists every enrolled machine from `org.json`: `online` or `last seen <age>`, its live session count, and the projects it has sessions in; on an unenrolled machine it says so and lists this machine alone. Both read the logs this machine holds and `org.json`; the age of `org.json` is printed when it is older than a minute.
- **Inside a session, `sminos list` ends with the caller's subagent tree** (#93 item 4): the session's current subagents nested under their parents — agent id, type, status — the ids `SendMessage` takes. Live ones (running, or waiting on their own background work) are listed, as `ListAgents` lists them; finished ones fold into `+N finished`, and `--all` shows them with their ids, since `SendMessage` to a finished agent's id resumes it from its transcript. Read from the session's bridge when it answers (the child keeps every agent's spawn and whether it runs, `sminos_bridge.py`), else derived from the transcript as DX4's jobs ledger does (`sminos_jobs.py`).

Where this supersedes #93: #93's machine view `sminos list --here` is a filter shorthand here, not a view of its own; #93's "(no project)" group is empty on an enrolled machine once M3 lands (every session has a project) and stays the unenrolled machine's.

## 5. Addressing: bare names stay in the project

- `@alias` searches the sender's project only. When no member answers there, the refusal lists the org's candidates — every member of every project known here whose alias matches — as `@<project>/<alias>#<short>` and, for a stray, `@<machine>/<alias>#<short>`, with the line `a bare name reaches only your project; @short reaches anyone`. Today's refusal says only "no member".
- `@short` and `@alias#short` resolve org-wide: an eight-hex prefix of a session uuid is unique enough across the org that the message goes where it points. A short matching two sessions is refused naming both with their projects. A bare tag of exactly eight hex characters is read as an alias when a member of the sender's project has that alias, else as a short (today `match_members` matches a bare name against alias and short in one scope; with the two scopes apart, the alias in the project wins).
- `@<project>/<alias>` resolves the project among every project known here by §4's name rule, so a stray is `@mini/<name>`. **When an ordinary project and a machine share a name**, the ordinary project is read first, and the machine project only when the ordinary project has no member of that alias — the rule `find_target` already applies to a qualifier that is both a project and a seat group. A team names its project deliberately and a machine is named after a host, so the team is the likelier meaning; `@short` reaches the stray regardless. The hub refuses no such collision: a committed `.smns` must never fail to sync because a host shares its name, and a refusal at enrollment cannot be complete since projects register later. The alternative, refusing the tag as ambiguous, lost because it makes a whole project unaddressable by name for the sake of a case `@short` already covers.
- `@all` reaches the sender's project only, and is refused in a machine project (§1).
- There is no silent org fallback for a bare name: the board spawns the same seat names (architect, executor, reviewer) in every repository, so `@executor` from a repository without one would wake another repository's executor.

Where this supersedes #93: `send --session <name|short>` (#93 item 5) is not built; `@short`, `@alias#short` and `@<machine>/<alias>` reach a stray through the tag rules, recorded in both logs (§6). `sminos send`'s unrecorded raw-harness-name route (from no project, to a session in no project) is left for unenrolled machines, where it is still the only route to such a session; on an enrolled machine no session is in no project, so the route is never taken there.

Where this supersedes the log design: §2's "from a directory that is no project a name resolves across every project known locally" is dead letter on an enrolled machine (no such directory exists) and stands on an unenrolled one; `@project/name` crosses to any project known here, the followed ones included.

## 6. Recorded in both logs

- A cross-project `say` (or `send`) writes the **destination** event first, in the destination project's log under the sender's writer, with `from_project` the sender's project id (as today): that event delivers.
- Then it writes a **copy** in the sender's own log: the same `say` with `to` each recipient as `{session, alias, project}` and `copy` `"<destination project id>:<writer>:<seq>"` naming the delivering event. `_owed` skips any event carrying `copy`, so the copy delivers nothing and no one is woken twice. A copy that cannot be written (the destination's append succeeded, the sender's failed) is a stderr warning, not a failure: the message was delivered.
- Both are ordinary local appends, uploaded by the ordinary uploader; both machines' daemons and the hub see them as any event. A reply works the same way in reverse: the frame's reply line already names the sender as `@<from_project>/<short>`, so the recipient's `say` is a cross-project message too.
- This holds for strays, since every session has a synced project (§1): a stray recipient reads what it received with `sminos chat` in its machine project.

## 7. `sminos join <project>`

- `sminos join <project>` (a project name or id known here) declares the calling session's project. It writes `retired` with `reason` `moved` and `project` the new project's id in the old project's log, and `joined` with `by` `join` and the session's real `cwd` in the new one's; the machine's presence follows (the plane reads the log). `sminos join --cwd` removes the override and moves the session back to what its directory says, by the same path. `sminos join` with no argument prints the session's project and whether an override holds.
- **A join's target must be a project the session can sync in.** On an enrolled machine that is an active hub project of its org — not a `local-*` project (kept only as history, §1) and not a project `org.json` marks retired (§3); the refusal says which it was. On an unenrolled machine any project known here will do. Without this a `join local-doperpowers` would silently take a session off the desk and out of every other machine's reach, against §1's one invariant.
- The override is `$SMINOS_HOME/sessions/<session-uuid>.json`: `{"project": "<id>", "at": "<ts>"}`. It is removed only by `join --cwd` or another `join`; the daemon sweeps overrides whose session's transcript has not changed for 30 days or is gone. An override whose target has become ineligible (its machine project retired, the project no longer known) is read as absent — `session_project` falls through to the directory, so the session moves (§1a) — and is removed by the sweep, with a `daemon.log` line naming the session and the target.
- Hand-off (the log design §2) copies the override to the successor session, as it copies the cursor.
- Seats cannot join: a seat's project is its record's `cwd` (its spawner chose it), so `join` from a seat is refused with "a seat's project is where it was spawned".
- **One resolver, `session_project(session, launch_cwd)`** (§1c), serves the record hook (`cmd_record`), the bridge export (`export_live`), `_local_sessions` (and through it the plane's presence, which reads `view_of`), `seat_project`, `caller_project` and `caller_scope`. It does not serve `known_checkouts`, which must keep reading each `joined`'s `cwd` through `resolve_project` so a joined-by-override session's directory is never offered as a checkout of the project it joined.
- Resume (the RPC) uses the `cwd` carried on `joined`, which is the launch directory (§1c).

## 8. Desk

- Machine projects appear on the grid like any project, labelled by kind (`ProjectSummary.kind`), and open to the same project view; a retired one is not drawn.
- A cross-project message is drawn in both timelines: the destination's event as today, with its origin (`from_project`) named; the sender's copy marked with its destination (`→ <project>`), never as a message to the sender's own group.
- **The org view**: every live session of every project on one screen, waiting on the owner first, then working, then idle; ended sessions are not drawn. It is built on desk-web's existing projection — `apps/desk-web/src/log/projection.ts` and `shell/sessions.ts` — **lifted over all project sockets**: the view acquires a `ProjectConnection` for every project on the grid (`project/registry.ts` already shares one connection per project per tab), runs `useDeskSessions` on each, and merges the groups. A row is the session's name (`sessionName`: title, else alias) with its alias, project, machine, and in-charge line; a click opens the project view on that session. The alternative, an org-wide session table built by the `Registry` and streamed on the grid socket, lost on the desk's own doctrine: a browser draws only what it has verified with the org key (the push notice carries "only what points to a card, since the service worker holds no org key and so cannot check anything it would draw"), and a `Registry`-built table would be either an unverified directory of names and in-charge lines or a second copy of every project's events; it would also duplicate the lease and presence state the `Project` objects own. The cost is one socket per project (a handful) and each log's first load, which the IndexedDB log record already caches.

## 10. Channels: later

A channel will be its own log; whoever is tagged in it is a participant; it never limits reach. Deferred, and the reach rule is fixed now: in the prior art (a research pass of 2026-10-18 over Slack's shared-channels engineering posts, Matrix MSC1772/MSC3083, Zulip's topics, and the agent frameworks), Slack's shared channels made reach a two-sided approval and spent years undoing it with standing auto-approval; Matrix's spaces grant eligibility at join time and leave a known gap on leaving; Zulip's topics are a reading label that never drives delivery; among agent systems, Teams bots wake only on mention and no system scopes addressing to a channel. The directory therefore comes first, waking stays a tag's doing, and a channel, when it comes, is a place to read, not a wall.

## 11. What this revises in the log design

`docs/doperpowers/specs/2026-10-13-smns-project-log-design.md` stays the doctrine of the log; this spec supersedes these parts of it:

- **Terms, "Project"**: "a directory in no git repository is no project" holds only on an unenrolled machine; on an enrolled one such a directory's session is in the machine project (§1).
- **§1, resolution**: `resolve_project`'s outcomes gain the worktree rule (§1a) and, on an enrolled machine, the machine-project fallback in place of "no project"; `session_project` adds the join override ahead of the directory (§7). `spawn --cwd` into a project-less directory still registers a local project on an unenrolled machine; on an enrolled one the seats land in the machine project.
- **§2, addressing**: "from a directory that is no project a name resolves across every project known locally" is dead letter on an enrolled machine; `@project/name` reaches any project known here, followed ones included; a bare name's refusal lists the org's candidates; `@short` and `@alias#short` resolve org-wide (§5).
- **§3, the event table**: `joined` gains `session_kind`, `repo`, `branch` and the `by` values `join`/`move`; `retired` gains `reason` `moved` with `project`; `say`/`human` gain `copy` and `to[].project` (Interfaces and Dependencies).
- **§4, `send`**: its unrecorded raw-name route is never taken on an enrolled machine (§5).
- **§7, views**: `list`'s row and flags are §4's; `--all` keeps its meaning.

And in the desk design (`docs/doperpowers/plans/2026-10-15-desk-dc4-uplink.md`): the hub `.smns` shape `hub: {url, org}` becomes `hub: {org}` for new projects, `url` tolerated (§2); an opened project whose root stops naming the hub no longer ends the stream (§1a); a machine's `hello` may be follow-only (§3).

Nothing else moves: the writer model, delivery, the mirror, the daemon's duties, the hub's log plane and RPCs stand.

### M1 — Rows from the engine's records, the filter layer, `--here`, the subagent tree

What exists at its end: `sminos list` prints §4's row for every member — `[short]` always, `kind`, a state read from the engine records, `repo@branch`, the in-charge age, `· active <age>` — and takes `--project`, `--machine`, `--state` (comma lists), `--org`, `--here` and trailing words, any filter widening to every project known here; `sminos find <words>`; `session_kind`, `repo` and `branch` on every `joined` this machine writes from now on; inside a session the list ends with the caller's subagent tree, live agents nested, finished folded behind `+N finished` and shown by `--all`. `--here` lists under `(no project)` every running engine session whose directory resolves to no project, wherever it runs.

Touches: `skills/sminos/scripts/sminos.py` (`cmd_list`, `view_projects`, `list_row`, `state_column`, `member_json`, `joined_fields`, `_member`, `seat_state`/`state` for the engine-record liveness, the argparse of `list`, a new `find`), `sminos_jobs.py` (the subagent tree from a transcript), `sminos_bridge.py` (the bridge serves the agents it keeps), `tests/sminos/run-sminos-tests.sh`.

Interfaces: produces the row and its JSON fields (Interfaces and Dependencies, `sminos list --json`) and the `session_kind`, `repo`, `branch` fields of `joined`. Consumes nothing new.

Decisions: liveness is the engine record (`session_running`), and the word is `peer_state(rec)`, for a seat's word (`seat_state`, today by the socket probe) as for a seat-less member's (already so); the socket probe stays delivery's (`peer_for_session`), and `seat_state(seat, None)` — delivery's stopped fallback in `push_member` — consults `session_running` before it says `stopped`, so a running seat with a quiet socket is `recorded`, never resumed (§4). Before changing anything, reproduce board:646's case (a session the engine records as `idle` that `list` prints as `stopped`) to confirm which path produced it — the seat's probe, or `same_process` against the record's `procStart` — and pin that path. `--machine` matches by prefix on the member's `machine`; `--project` by name or id; words match a lower-cased concatenation of the fields §4 names. `--org` on an unenrolled machine is every local project. `--state` with several words keeps today's folding rule: a named word is shown even when `HIDDEN`. `--json` adds fields and removes none. ### Interfaces and Dependencies

**The `org` frame** (hub → machine, `apps/desk-hub/src/protocol/machine.ts`, `DownFrame`):

```ts
| { t: 'org'; projects: Array<{ id: string; name: string; kind: 'hub' | 'machine'; machine?: string; retired: boolean }>;
    machines: Array<{ name: string; online: boolean; seen: string | null }> }
```

Sent after `welcome` on every stream, on every project registration, on every change of a machine's `online` or enrollment. `seen`: ISO 8601 UTC with milliseconds, when the machine's `online` last changed at the `Registry` — for an online machine, when it came online; for an offline one, when it went offline (null: never reported online). Every other mention of `seen` points here.

**`hello`** gains an optional flag (`UpFrame`):

```ts
| { t: 'hello'; project: string; name: string; have: Vector; follow?: boolean }
```

`follow: true`: the machine holds no checkout and no session of the project; its lease counts toward no machine count and it posts no presence. Absent or false: as today.

**The summary report** (`Project` → `Registry`, `Registry.summary`): `counts` gains `machines_state: Array<{ name: string; online: boolean }>` — every leased machine, followers included, with whether its lease is fresh. `ProjectSummary` (`protocol/browser.ts`) gains `kind: 'hub' | 'machine'`.

**The machine project id**, in both implementations (the machine's name lower-cased, as the hub compares names, `machineNameKey`):

    Python: uuid.uuid5(uuid.NAMESPACE_URL, "smns-machine:%s:%s" % (org, machine.lower()))
    TS:     uuid v5 over the URL namespace of the same string (a small implementation in protocol/identity.ts; pinned by protocol/vectors/machine-project.json and its generator, M2, with a committed copy at tests/sminos/machine-project-id.json read by the Python parity test, M3 — the pattern of dx1-codes.json)

**`org.json`** (`$SMINOS_HOME/daemon/org.json`): the latest `org` frame's `projects` and `machines` plus `at` (when it arrived, ISO 8601 UTC).

**`project.json`** of a followed project: `{"project", "name", "remote": "", "root": "", "hub": {"url", "org"}}` — the five fields `project_path` writes and nothing else. A project's kind and whether it is retired are read from `org.json` (§3); whether this machine holds or follows it is decided at each scan (M3).

**`session_project(session: str, launch_cwd: str) -> Project | None`** in `sminos.py`: §1's order, from the session's launch directory (§1c). `machine_project(org: str, machine: str) -> Project`: the machine project of this machine (`Project` with `root` `""`, `hub` from the enrollment). `resolve_project(cwd)` keeps its signature and gains the worktree rule and the machine-project fallback; `session_project` adds the override.

**The join override** (`$SMINOS_HOME/sessions/<session-uuid>.json`): `{"project": "<project id>", "at": "<ts>"}`. An eligible target on an enrolled machine is a project whose `project.json` names the org's hub and that `org.json` does not mark retired; an override naming an ineligible project is read as absent (§7).

**Log events** (additions to the log design §3's table):

| kind | new fields |
| --- | --- |
| `joined` | `cwd` is the session's launch directory (§1c); `relocated: true` marks a repeated `joined` that only refreshes `cwd`/`repo`/`branch` after the engine relocated the session within the same project (M4); `session_kind` `interactive`/`bg`/`seat` (never `kind`, the event's own discriminator); `repo` the owning repository's basename (`""` outside one); `branch` (`""` when detached or none); `by` may be `join` or `move` |
| `retired` | `reason` `moved` with `project` the new project's id |
| `say`, `human` | `to[]` entries may carry `project` (the recipient's project id); `copy` `"<project id>:<writer>:<seq>"` marks the sender's copy of a cross-project message; `from_project` as today |
