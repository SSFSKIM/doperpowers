Today a session on a Mac that wants work done on a cloud machine runs `devcloud vm up`, then `devcloud vm ssh <name> -- sminos spawn …` by hand. The session it gets there is "spawned by the operator", is invisible to every other machine unless the VM happened to be made with the MAWS project, and cannot tell its spawner anything unless it was given a tag in its task. The VM belongs to the session that made it for as long as that session lives, and nobody else can take it over. Its idle and lease notices go to that session's short id as a person's words.

After this child:

- **One command opens a thread on a VM.** `sminos spawn --on <vm> <alias> <task>` opens it on a VM that exists, and `sminos spawn --on new <alias> <task>` makes the VM first, with the spawner's repository at its pushed branch, enrolled in the org and kept. The new thread knows who spawned it and how to reach it.
- **A VM can be handed on.** `devcloud vm owner <vm> <thread>` gives a VM to another thread of the same Mac. The thread that gave it up can then be retired; the one that took it cannot until it downs the VM or hands it on.
- **A VM's notice is a machine's notice.** It reaches the current session of the thread that owns the VM, wakes that thread if it is stopped, and arrives framed as coming from `devcloud@<vm>`, never as the person's words. Where the VM's own `say` reports that the owning thread is held and will not be woken with it, the notice goes on to the live members of that thread's project.

How to see it working is the acceptance below, proved by suites that run a real sminos and a real devcloud driver against stand-ins, and at the end by one check on the owner's fleet (M5).

## Acceptance

G1 of the composite's EN section, as observable items. "A Mac" is a machine where devcloud's driver runs; "a VM" is a devcloud host, an adopted machine included. Each item is proved where Concrete Steps' proof map says.

1. **One command, a new VM.** From a session on a Mac, in a worktree whose current branch origin holds at the worktree's commit, `sminos spawn --on new <alias> - <<'EOF' … EOF` prints devcloud's own lines while the VM is made, then one line `seat spawned on <vm>: …`. devcloud was called as `vm up --enroll --keep --expect-creator <the spawner's short id> --label <alias> --project <owner>/<repo>@<branch>`, and with `--confirmed` only when `--vm-confirmed` was passed. devcloud makes nothing, and calls no provider, when the creating session it reads is another, or none. The VM clones the branch as origin holds it when it boots; where that is another commit than the one checked, the Mac says which. `devcloud vm ls` shows the VM kept, its owner the spawning session's short id, and its descriptor names the spawner's project by its id.
2. **One command, a VM that exists.** `sminos spawn --on <vm> <alias> <task>` opens a session on that VM, an adopted machine included, in the VM's checkout of the spawner's repository, or in the directory `--cwd` names there. The task travels on standard input, and a task holding quotes, backticks, `$` and several lines arrives as written. The Mac prints the spawn's line only on one whole outcome line from the VM (Interfaces §8); on none, two, one outside the shape or one the exit status contradicts, it says that the outcome is not known, exits non-zero and names the command that shows what is on the VM. That holds for a name devcloud has no VM for: devcloud's own line is shown, with the Mac's reason added when the org lists the name as a machine, and nothing is claimed.
3. **The spawner travels with the spawn.** The new session's first message names its spawner's alias, short id, project and machine and the tag that reaches it, and `sminos say "@<that short> …"` run on the VM reaches the spawner's current session. Spawned from a terminal with `--on <vm>`, it says "the operator" as today.
4. **Refusals, each saying why, with nothing made and nothing spawned:** `--on` run on a devcloud host; `--on` from a machine that is not enrolled; `--on` naming this machine; `--on` from a session that is no member of a project, or whose project this machine's enrollment does not carry (a `.smns` naming another org among them), before devcloud is called; `--on` from a session whose reach could not be read (no record, an unreadable one, one not settled) or is not its machine's default, read again before each call to the VM, so that a reach narrowed while a VM is made refuses the spawn, saying that the VM is kept; `--on <vm>` whose machine is not enrolled in the org, or is enrolled in another org; a VM whose checkout, where the directory was inferred, is another repository's; `--on new` under a profile that cannot enroll a VM (devcloud's refusal, before any VM exists); `--on new` from a terminal; `--on new` from a worktree on no branch, on a branch origin lacks, or whose commit origin's branch is not at, each with the two ways out; `--on` with `--wait` or `--settings`. A cap refusal of devcloud passes through with devcloud's exit 4 and its line.
5. **Waiting for enrollment.** `--on new` whose VM is up and not enrolled yet says what it waits for, tries again for up to eleven minutes, and spawns when the VM enrolls. Past the bound it exits 1 saying that the VM is kept, who owns it, and the command that spawns on it later.
6. **The handover.** `devcloud vm owner <vm> <thread>` takes any name sminos resolves to a thread (an alias, `alias#short`, a tag, a short id, a thread id, a former session's id), accepts a thread of the machine it is run on that has not ended, a stopped one included, and prints who owned the VM and who owns it now. It refuses a thread of another machine, an ended one, a vacant seat and a name that is no thread, changing nothing. It works for an adopted machine and for a host made before this change. It reports a handover only after reading both of its writes back, the host's by the host's own parser: the tag, and the thread's project by its id where that parser takes the key. Stopped between its writes, crossed by another handover, or left without a reply by the host or the provider, it says what each side holds and what it could not read, exits non-zero where they differ, and run again it settles. A `vm lease` or a resumed `vm adopt` running at the same time on the same Mac does not write the old owner back, nor the handover an old lease.
7. **Who a retire refuses.** After a handover, `sminos retire` of the thread that gave the VM up succeeds, and `sminos retire` of the thread that took it exits 1 naming the VM and both ways on (`devcloud vm down <vm>`, `devcloud vm owner <vm> <thread>`).
8. **A notice follows the thread.** A VM's notice reaches the current session of the thread that owns the VM after that thread changed session id (a hand-off to a background job, a refill), once the VM has read that change, and wakes that thread when it is stopped. This holds for a host made before this change, whose descriptor names a former session's short id and whose boot library is unchanged. A notice written before the VM has read the change names the session the thread left: it is in the project's log and counted unread for the current session, and is not pushed (accepted; Decision Log, "The lagging view").
9. **A notice is a machine's.** From a host made with this change, read by a sminos of this change, the notice reaches the session as `[sminos chat <project> <ref> from devcloud@<vm>… → @you]` in the peer envelope with no reply line, and never through the bridge or a background job's supervisor, whichever verdict the endpoint gave, nor inside a payload routed by another event. `sminos chat` and the TUI show the same sender. The manager's reading of what the owner said leaves it out.
10. **A notice goes on.** When the VM's `say` reports that the owning thread is held and not woken (for any reason its machine published), has ended, or is no member, the notice goes to the live members of that thread's project; when none is live, into that project's log as an untagged note, whatever the first step recorded; then to the host's journal and `wall`.
11. **Nothing else changed** (parent acceptance line 8 for this surface). A `say` without the two new flags, a `spawn` without `--on`, a `who` without `--thread` and a `retire` of a thread that owns nothing print and exit as before; the retire refusal's words are the one visible change. Every suite that passed before passes.
12. **On the fleet.** On the merged versions, M5's check runs and each of its expectations is observed, or it is reported as not run with what is missing. This plan claims item 12 only when it ran.

## Words this document adds

The composite's Terms define the owner (the person, and only the person), thread, project, log, writer, member, seat, deliver, wake, the daemon, the hub, the endpoint, reach, lane B and devcloud. T2's plan defines held and woken. Added here:

- **A host** is a machine devcloud manages: a VM it made, or a machine it adopted. **The driver** is `devcloud vm`, the part of devcloud that runs on a Mac (`devcloud/driver/`). **The boot library** is what a host itself runs (`devcloud/boot/`), installed when the host is built and never updated afterwards.
- **The descriptor** is a host's `/etc/devcloud/boot.env`: `KEY="value"` lines the driver composed, which the host reads again at every tick of its lease service (five minutes). `DEVCLOUD_CREATOR` holds a sminos tag and `DEVCLOUD_CREATOR_PROJECT` a project's name or id.
- **The owning thread** of a host is the thread one of whose sessions the host names. A host names a session by its **short id**, the first eight characters of the session id, in up to three places: the provider's label `devcloud-creator` (a VM) or the Mac's adoption record (an adopted machine), and the descriptor. The stored names keep the word "creator"; after a handover what they hold is the owning thread's session.
- **Enrolled** is said of a machine whose sminos has an identity from MAWS's endpoint (`daemon/identity.json` under sminos's home, read by `enrollment()`). Only an enrolled machine's sessions are seen by other machines.
- **A marked event**, or **a machine's notice**, is an event that X8 (Interfaces §1) says is one. **The notice sender** is the string `<program>@<machine>` it is shown under.
- **The Mac side** and **the VM side** of `spawn --on` are the `sminos spawn --on …` a session runs, and the `sminos spawn … --asked-from …` it causes on the VM over ssh. **The outcome line** is the one line the VM side prints for the Mac side (Interfaces §8).
- **The recipe hash** is devcloud's hash of `devcloud/image/` and `devcloud/boot/` (`compose.recipe_hash`). An image is used by `vm up` only while its hash is the current one.
- **The stand-ins**: `sminos/tests/devcloud_standin.py` plays devcloud's CLI for sminos's suites; `devcloud/tests/unit/driver_fixtures.py`'s `FakeRemote` plays ssh to a host for the driver's tests, and `devcloud/tests/fixtures/sminos.py` plays sminos for the host's integration tests; the boot library's tests inject `call` and `say`.
- **`S/`** is `sminos/skills/sminos/scripts/`, **`T/`** is `sminos/tests/`, **`D/`** is `devcloud/`.

### M1 — A machine's notice: the marker, the exit that lets it go on, and the host that sends both

**At its end:** a `say` run from a shell with `--notice devcloud` writes `human` events that carry `notice: "devcloud"`, and a session that runs it is refused. Such an event is nobody's words: it reaches a session as a peer's frame whose sender is `devcloud@<machine>`, by the inbox and never by the bridge or a supervisor, whatever the endpoint answered, and never inside another event's payload; `sminos chat` and the TUI show that sender; the manager's reading of the owner's words leaves it out; and it wakes a stopped thread it is addressed to as any addressed message does. `say --exit-held` exits 3 where a tagged recipient's own line says it is held and not woken. A host's notices pass both flags, go on to the project's live members at exit 3 as at any other failure and to the project's log when none is live, and fall back to today's call where the host's sminos does not know the flags.

**Touches:** `S/sminos.py` (`EXIT_HELD`, new `notice_of` and `notice_sender` beside `owner_event`; `owner_event`; `cmd_say`, `say_scoped`, `deliver_say`; `frame_of`, `holder_wake`, `chat_line`; `SendDelivery`, its new `runs`, and the two places a `SendDelivery` is pushed and settled; `build_parser`'s `say`; the module docstring that is `sminos help`), `S/sminos_control.py` (`_routes`), `S/sminos_tui.py` (the two places that draw a chat event's sender), `T/test_notice.py` (new), `T/test-notice-machines.sh` (new), `T/run-sminos-tests.sh` (`run_suites_c`), `D/boot/devcloudlib/notices.py`, the docstrings and comments in `D/boot/devcloudlib/lease.py`, `services.py` and `descriptor.py` that say whom a notice goes to, `D/tests/unit/test_idle.py` and `D/tests/unit/test_lease.py` (each pins the argv of a notice's `say`: the idle notice's three steps, and the lease warning's first), `D/tests/fixtures/sminos.py`, `D/README.md` (the paragraph on notices), `S/CLAUDE.md`, and the files `scripts/bump-version.sh` writes for both plugins.

**Interfaces:** exposes §1 (the marker and its readers), §2 (`say`'s two flags and exit 3), §3 (the host's order). Consumes T2's `remote_line`, `held_line` and `HOLD_WORDS`, T1's `former_ids`, and the endpoint stand-in.

**Decisions:**

- **The verdict authorizes; the marker presents** (R8). The words gate's question and its `refuse`, the revocation set, the read-only policy and the reach gate are untouched: under `words` the reach gate still does not apply, under `peer` it applies as today. **The order.**

**The owner program** is a Python text the driver sends on standard input to `python3 -P - write <tag> <project>` or `python3 -P - read` on the host, as root. To read, it takes the lifecycle lock shared, parses the descriptor with the host's own `descriptor.parse` (`allow_http` as the host's CLI sets it), and prints one line, `{"tag": …, "project": …, "takes_project": true | false}`, exit 0.

To write, it:

1. takes the host's send lock, the file `notices.lock` beside the lifecycle lock, which the lease service holds while it sends a notice: `lease.locked(path=…, timeout=20)`, one acquisition through the host's own helper. Not had in twenty seconds: exit 4, nothing written. On a host built before the send lock (2026-10-28) no service takes that file, and the step excludes nothing;
2. takes the lifecycle lock, exclusively (`lease.locked()`), the send lock before it as the lease service takes the two;
3. exits 3 when the host's departure has started, writing nothing;
4. reads the descriptor and builds its new text: the first assignment of `DEVCLOUD_CREATOR` replaced, any later one dropped, the line appended when there was none; and, where the host takes the project key, the same for `DEVCLOUD_CREATOR_PROJECT`; every other line as it was;
5. parses the new text with the host's own `descriptor.parse`, and exits 1 with the parser's line, writing nothing, when it is refused;
6. writes it through `proc.write_file` with the file's own mode, reads it back as the read mode does, and prints that line, exit 0.

Its paths (the descriptor, the two locks, the status file) and its wait are parameters with the host's defaults, so a unit test runs the very text against a temporary host.

**What a handover redirects.** The notices of every tick of the host's lease service that starts after it. **A route back.** A session opened elsewhere answers its spawner through the org's hub. **The reach rule** is `reach_refusal`, read at (e) and again immediately before every run of the VM side, the tries of the wait included, since a reach narrowed while a VM is being made must not be outrun. It reads the session's record as it stands (`sminos_records.read`) and rebuilds nothing. ### §8. `spawn --asked-from`, the VM side, and the outcome line

The new session's record is what a spawn from this machine's terminal gives (`spawn_provenance`'s last case): the origin names no spawner's session, and nothing of `by` is a grant;
6. prints no `seat spawned:` line; its last line on standard output, for every way it ends after the value was read, is the outcome line, `sminos-spawn <nonce> <one JSON object>` on one line. A spawn that launched a job and cannot print a success whole by the shape below (its own outcome not whole, no usable session id, a refill whose stop of the new job failed) prints no outcome line, as step 8 says, so the Mac takes row 29 (the holder's ruling F6 of 2026-11-21, which replaced the first build's `ok` false here).
7. takes the task `-` reads as sent: decoded with `surrogateescape`, as the Mac encodes it, with nothing stripped; the Mac has already applied `spawn`'s local rules to it. An empty one is refused as `spawn` refuses one (`why` `other`, exit 2), since the Mac never sends one.
8. a launcher that was started and gave no usable acknowledgement (it timed out, it exited 0 with no job named, it was killed before naming one) is an outcome not known, never a refusal: no outcome line, and on standard error `spawn: the launcher (claude --bg) was started here and named no job (%s): a session may have started all the same; no outcome is reported for it, so the machine that asked says it is not known: sminos list here shows whether one runs`, exit 1 (`%s` one of `it gave no answer within %d s, and was stopped`, `it was ended by signal %d`, `it exited 0 without naming a job`) (the holder's ruling of 2026-11-21 after the second reading); a launcher that refused in its own words (a non-zero exit with its output), or could not be started at all, is a refusal as before. And after the launcher returned a job, nothing is a refusal, an exception or a deliberate exit alike: it prints no outcome line, names the job on standard error (`spawn: session %(job)s was launched here, and then this failed: %(error)s; no outcome is reported for it, so the machine that asked says it is not known: sminos list here shows whether it runs, and claude stop %(job)s stops it`) and exits 1, so the Mac takes row 29; a deliberate refusal after the launch keeps its outcome line (the holder's ruling of 2026-11-21 after the frontier review).

**The outcome line's shape,** which the VM side prints and the Mac side accepts, the same on both: a line outside it is no outcome.

    {"ok": true, "refilled": <true | false>, "group": "<group>", "alias": "<alias>",
     "short": "<the engine's job id>", "seat": "<seat id>", "session": "<session id>",
     "status": "<status>", "project": {"id": "<id>", "name": "<name>"},
     "machine": "<this machine's name>", "cwd": "<the directory it runs in>",
     "head": "<the commit checked out there, 40 hex>" | null}

    {"ok": false, "exit": <the exit code>, "why": "<one of the table's>"}

A success may carry one more key, `not_carried`, a string, checked wherever it is present, on a refusal line too (one that is no string makes the line not whole; on a success, a present string means not carried, `""` included, and only one of `NOT_CARRIED_WORDS` is shown as the reason; one outside `NOT_CARRIED_WORDS`, which a newer VM may know, is read as not carried with no reason shown (the holder's ruling of 2026-11-21 after the second reading)), one of `NOT_CARRIED_WORDS` (§4), where the project the seat was filed in (the engine's own checkout, under `--worktree`) is one this machine's enrollment does not carry; an older Mac ignores it (the holder's ruling of 2026-11-21 after the frontier review). `refilled` is a Boolean; `seat` and `session` are whole by `UUID_RE`; `group`, `alias`, `short`, `status`, `machine`, `cwd` and the project's two are non-empty strings; `head` is null where the directory is no checkout. A key beyond these is ignored, so that a later version may add one.

| `why` | `exit` | Said at |
|---|---|---|
| `not-enrolled` | 1 | step 1 |
| `other-org` | 1 | step 2 |
| `other-repository` | 1 | step 4 |
| `other` | the code `spawn` ended with: 1, 2 or 4 | every other way it ends without `ok` |

What `spawn` says on standard error (a refusal's sentence, a warning that an event could not be appended) is said as today.

**What the line guards against.** The VM is the owner's own machine, reached with the driver's key, and its sminos is trusted: the line is no defence against a hostile VM, and none is built. It guards against confusion: a task's text or a tool's noise that looks like an answer, an answer cut short, a copy that predates the call.

**How the Mac side reads it.** The outcome is known only when all of this holds, and is "not known" (§7, row 29) otherwise:

- exactly one line of standard output opens `sminos-spawn <its nonce> `, and it is the last line;
- the rest of that line is one JSON object of the shape above;
- for `ok` true: `devcloud vm ssh` exited 0, and `alias` is the alias asked for;
- for `ok` false: `why` and `exit` are a row of the table, and `exit` is `devcloud vm ssh`'s exit.

It acts on `why` `not-enrolled` alone (row 25, or the wait of rows 26 and 27) and takes the table's other rows as row 28: a VM of another org, or another repository's checkout, is never waited on. A line outside the shape or the table, a `not-enrolled` beside another exit among them, is "not known" and is never tried again. No exit code by itself is read as an outcome, and no line of devcloud's stands in for one: an exit 2 with no line is said as a copy that may predate the call, a `no VM named` as what devcloud printed, and neither as nothing spawned.

Without `--asked-from`, `spawn` is byte for byte what it was: that is the call an older Mac, or a person, makes over `devcloud vm ssh` today.

### §9. `devcloud vm up --enroll` and `--expect-creator`, and the line that names the host

    devcloud vm up --enroll --expect-creator <short> …

With `--enroll`, `up` requires the host to provision MAWS's endpoint: where `compose.provisions(profile, projects)` is false and the profile's `[desk]` names the provisioning, `compose.MAWS_PROJECT` is appended to the projects (after those named, so the first project's `host.toml` still governs) and `up` says `enroll    the MAWS project is added: its setup installs the endpoint this host enrolls with`.

With `--expect-creator <short>` (eight hex digits, else a usage error), `up` makes nothing unless the creating session it reads itself (`ctx.creator()`, as it records one today) is that one. It is how a caller that already knows who runs it, `sminos spawn --on new`, keeps devcloud from making a host it records no owner for, or another.

Both are checked before the reaper's run and before any call to a provider, under `--dry-run` too:

| Case | Exit | Words (after `devcloud vm: `) |
|---|---|---|
| `--enroll`, a profile whose `[desk]` names no provisioning | 3 | `--enroll: the profile's [desk] names no provisioning (provisioning_secret_v2 with delegation_id), so a host it makes cannot join the org: nothing was made` |
| `--expect-creator`, no creating session read | 1 | `--expect-creator: the caller expects @%(short)s as this host's creator, and devcloud read no creating session here (sminos who --session gave it no address it reads): nothing was made` |
| `--expect-creator`, another session read | 1 | `--expect-creator: the caller expects @%(short)s as this host's creator, and devcloud read @%(read)s: nothing was made` |
| `--enroll`, the boot skipped the provisioning it enrolls with (the holder's ruling of 2026-11-21 after the frontier review) | 1 | `--enroll: the boot of %(name)s skipped the provisioning it enrolls with (maws %(state)s: %(detail)s), so it will not join the org; the VM %(name)s is kept for inspection, with no lease: devcloud vm down %(name)s removes it` (`its lease bounds it` for a leased VM) |
| a boot that failed, or did not finish in 15 minutes, for a kept VM (the holder's ruling of 2026-11-21 after the frontier review) | 1 | `…; the VM %(name)s is kept for inspection, with no lease: devcloud vm down %(name)s removes it`; a leased VM keeps `its lease bounds it` |

**The project a new host is told.** `Context.creator_project()` gives the creating session's project by its id where sminos can say it, and as today (the name in the `Sminos-Session` line) where it cannot. After the `who --session` call that reads the creator, `ctx.thread(<the full calling session id>)` is asked (§4), and the project's id is taken only when all of this holds: the answer's `session` is that same id, so the caller is its thread's current session; `local` is true; `thread` is not empty; `ended` is false; and the id is a value the descriptor takes for the key. Anything else leaves the name: no answer, a sminos that does not know `--thread`, a thread that has gone on in another session, a session the MAWS app launched. It never refuses an `up`, and it never changes the creator, which stays the calling session. The lookup is made once for a run, as the creator's is.

Without either flag `up` is what it was but for that project value. Two of `up`'s lines are read by sminos, and each is pinned by a test in `D/tests/unit` named for that reader: `<name>  ready in <m>m<ss>s`, as the one line of that form in everything a whole `up` prints (the account and caps lines before it, `created`, a `maws      deferred` line, and the five lines of the host's particulars after it); and the opening `no VM named` of `Context.find`'s refusal.

### §11. What the tests are built on

**`T/devcloud_standin.py`** keeps `vm owned-by` exactly as it is and learns two verbs, both set through the same `$HOME/devcloud-standin.json` and logged to `devcloud-standin.calls`:

- `vm up …`: prints the lines its `up.lines` holds (by default a whole `up`'s: the account and caps lines, `created   <up.name> (id 1) from base, slow path`, `<up.name>  ready in 0m01s` and the five lines after it), writes `up.stderr`, and exits `up.exit` (0). `up.gate`, a path, holds its answer back until the file exists, so a test can change something while a VM is being made. With `up.creator` set, it answers `--expect-creator` as devcloud does: exit 1 and devcloud's line when the short it was given is another. `up.said` and `up.hold` (a path touched, then a path waited for) stop it mid-call.
- `vm ssh <name> -- <words>`: for a `<name>` its `ssh_hosts` holds (`hosts` is `vm owned-by`'s), refused with exit 2 when its `env` lacks any of the four, joins the words as `shlex.join` does and runs the line with `/bin/sh -c` under that host's `env` (its `HOME`, `SMINOS_HOME`, `DAEMON_HOST`, `PATH`), standard input passed on, the word `sminos` at the line's head replaced by the launcher `sminos` names, and exits as that line did; `ssh_hosts.<name>.exit`, when set, is answered instead with nothing run (2 for a copy that predates the call, 255 for a host that does not answer), and `ssh_hosts.<name>.stdout`, when set, is printed in place of what the line printed (an outcome line twice, one cut short, one for another alias). For any other name: `devcloud vm: no VM named <name> in any usable account`, exit 1.

**`T/test-on.sh` and `T/test-notice-machines.sh`** are two sminos homes named as `T/rl10-machines.sh` names them (`rl10_as`, `rl10_cut_over`), the second also served by `T/endpoint_standin.py` with the verdict the case sets. A machine is "not enrolled" when its home holds no `daemon/identity.json`, and "of another org" when its identity names one.

**`D/tests/unit/driver_fixtures.py`**: `make_ctx` passes `thread=`, a function from a name to §4's answer, as it passes `creator=`; `FakeRemote` answers the owner program's two modes by rules on `python3 -P - write` and `python3 -P - read`, each through its `fn` where a test changes what a later read finds; the stand-in provider's `behavior` can hold a `get` or a `set-labels` at a gate (a path, as the sminos stand-in's), so a test stops one driver thread between a merge's read and its write while another runs; and the program's own behaviour is tested by running its text.

**`D/tests/fixtures/sminos.py`** plays `say` with the two flags, and, where its state says so, as a copy that does not know them.

**The gates' parts.** The five suite files this child adds (`T/test_notice.py`, `T/test-notice-machines.sh`, `T/test_who_thread.py`, `T/test_on.py`, `T/test-on.sh`) go at the end of `run_suites_c` in `T/run-sminos-tests.sh`, the third of the three parts `run_suites` calls (Constraints). None belongs to the part `channels`, which is the sibling child's.

**(b) What this plan leaves Deferred, or accepts as a known limit.**

- A thread opened from a VM, and on a Mac: the composite's own Deferred item, unchanged.
- MAWS's endpoint on a machine without the MAWS project: it waits on MAWS publishing its `mawsd` pack as a release artifact, which is the owner's decision and has not been asked.
- Carrying the spawner's reach to the VM: `--on` is refused from a spawner whose reach is not the default, since a wrong carry is a privacy fault and a refusal is not.
- `--wait` and `--settings` with `--on`: each reads something of this machine.
- An addressed event that names a session its thread has left is not pushed, for any sender whose view lags, a VM's notice among them: delivery as T1 built it and the holder's ruling. The event stays in the log, counted unread. The window is seconds while both machines are connected and as long as the disconnect otherwise, and a lease warning, sent once thirty minutes before a VM is deleted, can be what lands in it. Closing it is a milestone of its own if the owner asks; TECH-DEBT.
- A notice to a thread whose machine is asleep or not connected is recorded and waits for that machine, and does not go on: nothing publishes presence (the composite's Deferred). A recorded notice is not a timely one.
- A host made before devcloud 0.18.0 sends its notices unmarked and goes on only for an ended thread or no member: a host keeps the boot library it was built with. A notice is a machine's to its reader only where the reader's sminos is this change's too.
- A host built before its send lock (2026-10-28) can send its former owner one notice after a handover has returned: its lease service reads the descriptor before it sends, and nothing there waits for a handover.
- A new host names its owner's project by its id only where sminos answers `who --thread` for the creating session itself; a session that is no thread, a thread that has gone on in another session, or an older sminos leaves the name, and a host made before this keeps what it holds. A name two logs of the VM share is refused by `say` as ambiguous, or read as the first of its tiers.
- A background job that continues no session (one a person started with `claude --bg`) cannot use `--on`: its record is never settled, by the test sminos itself applies before it looks for a predecessor's reach. It spawns from another session. Admitting it means looking for a predecessor among the project's transcripts at each call.
- The driver's lock for a host's labels and its adoption record is one Mac's: two Macs writing one host's labels in the same second can each write back what the other changed. The provider's protocol has no compare-and-set to close it with.
- A host's sminos follows the source its settings declare, which may be pinned: nothing says when a host's copy updates.
- A host built before 2026-10-27 takes a new owner without the project: its parser refuses the key.
- An adopted machine's descriptor holds no project until a handover writes one: `devcloud vm adopt` is not changed here.
- A census older than a handover can let the three-day rule end the thread that just took a VM, for up to an hour (R6: accepted). The VM is not lost, but the thread does not come back by itself when the next census names it: it is reopened by its human, or filled, or the VM is handed on.
- Between the handover's two writes, a retire refuses the thread that gave the VM up and would pass the one taking it; and two handovers at once can leave the two sides holding different threads. Neither is locked against: the verb reads both sides back, says what each holds and what it could not read, and run again it settles.
- A VM made from a session the MAWS app launched is recorded under that session, as `vm up` does today, and nothing guards it: such a session is no thread.
- sminos cannot tell a Mac from another machine, so that refusal is worded as a condition: nothing publishes a machine's kind.
- A thread opened with `--on` is as readable as a default spawn made on the spawner's machine (the whole org reads and messages both), and is owned by the VM's owners, whose words it takes. In an org with more than one owner those may be other people than the owners of the spawner's machine. A known property, not a refusal (MAWS's architect, 2026-11-21).
- `--on new` does not look at uncommitted changes: the VM gets what the pushed branch holds.
- sminos reads two of devcloud's human lines (`<name>  ready in …`, to name the host; `no VM named …`, only to add a note): each is pinned by a test on devcloud's side.
- After the merge `vm up` takes the slow path until an image is built for the new recipe hash: the scheduled reaper does it within a day.
- `sminos spawn --on new` takes minutes and blocks: the skill has a session run it as a background command.
- `sminos spawn --on new` cannot size its VM: it passes `vm up` no type, account or lease, so the VM is what `up` makes from the first project's `host.toml` or the person's defaults; another size is `devcloud vm up --enroll --keep --type …` and then `--on <name>` (TECH-DEBT).
