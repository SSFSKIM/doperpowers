# Prior art: channels, threads, environment pools, and tools for a fleet of agent sessions

> Research for `docs/doperpowers/specs/2026-11-17-sminos-channels-and-threads-design.md`, kept as it was written.
> The spec is the authority. The owner overturned three of this survey's syntheses, and the spec says why: a single
> *home* channel that owns a session's lifecycle and machines (a channel owns nothing), a *resolved* state for threads
> (a thread ends only by a retire or the three-day rule), and member verbs as MCP tools (the CLI stays the one surface).

Survey date: 2026-11-17. Scope: documented evidence (docs' warnings, issue threads, maintainers' notes, papers) bearing on the proposal to replace the repository with declared, cross-repository channels; to make each session a thread; to allow plural channel membership; to give a channel a pool of environments; and to expose member verbs as MCP tools. Claude Projects for Claude Code is excluded (already studied).

Each finding has a source and one line, marked "Implies", on what it means for this design. Quotes are verbatim from pages read in this session unless marked otherwise. A list of what I could not find or verify is at the end.

---

## Synthesis: the findings that most change the design

1. **Plural membership works for reading and subscription. Lifecycle ownership has to stay singular.** Kubernetes let any number of controllers select the same pods by label, the controllers "fought", and it added a persisted single owner (ControllerRef). Buildkite went from agents on several queues to exactly one queue per agent when it introduced clusters. A GitHub runner sits in one group. A Claude Code session has "exactly one team" and a fixed lead. Matrix lets a room sit in many spaces but defines one canonical parent. **Design consequence:** a session may belong to many channels, but has exactly one *home* channel. The home channel owns its lifecycle and environment, and is the default target of anything it posts unaddressed.
2. **Don't route unaddressed messages with an LLM. Make the address explicit and let subscription do the fan-out.** AutoGen's selector silently fell back to "the next speaker in the list" when it could not parse a name. Claude Tag's and Cursor's documented wrong-repository picks are fixed by naming the target. LangChain measured a supervisor that paraphrases ("telephone"), costing tokens and accuracy, and fixed it by forwarding messages verbatim. Leads that implement instead of delegating are a documented failure in Claude Code agent teams and in CrewAI. MetaGPT's answer to broadcast overload is publish-subscribe.
3. **A standing thread is viable only if the thread is not the session.** Claude Tag documents threads that outgrow one session "forever", and old threads stuck on stale configuration; its fix rebinds a fresh session to the same thread. Gas Town states "an agent is not a session." A2A separates a long-lived context from immutable tasks that end. Devin documents degradation in long sessions. **Design consequence:** a thread is an identity plus a log plus a handoff artifact, and sessions behind it are replaceable. Threads need an explicit resolved state (Zulip).
4. **Machines must be owned by something that outlives their creator, with a reaper that does not depend on the creator.** GitLab Runner's docs say idle machines are "typically left to run" when the runner stops, and it added a heartbeat label so external cleanup can tell tracked machines from orphans. Karpenter left 20 instances running after its cluster was deleted. OpenHands left runtime containers behind. E2B kills a sandbox after 5 minutes by default. Codespaces fixes the retention period at creation.
5. **Tools versus CLI is close on raw performance. The decisive differences are identity, permissions and quoting, all of which favor tools for a small verb set.** Zechner's benchmark found "it doesn't matter as much as you'd think." Anthropic's warning that the commonest tool failure is confusing similarly named tools, for example "`notification-send-user` vs. `notification-send-channel`", falls directly on a post/DM verb pair. MCP Agent Mail, the closest prior art, ended up adding macros against "tool overload" and a "robot CLI" for token-sensitive loops.

## 1. Unit and membership

### Exclusive scopes vs plural labels (Kubernetes)
- **Namespaces are exclusive; labels are plural.** "Namespaces cannot be nested inside one another and each Kubernetes resource can only be in one namespace." Also: "For clusters with a few to tens of users, you should not need to create or think about namespaces at all." https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/
  - Implies: an exclusive, hard scope earns its cost at many-team scale. For one owner and about 30 sessions, attribute-like plural grouping is the lighter fit, provided the problems below are handled.
- **Labels give plural, loosely coupled grouping.** "Unlike names and UIDs, labels do not provide uniqueness. In general, we expect many objects to carry the same label(s)." Labels "map their own organizational structures onto system objects in a loosely coupled fashion." https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/
  - Implies: a channel as a selector over session attributes is a real, proven pattern.
- **Overlapping selectors conflict.** "For some API types, such as ReplicaSets, the label selectors of two instances must not overlap within a namespace, or the controller can see that as conflicting instructions and fail to determine how many replicas should be present." (same page). The Deployment docs add that Kubernetes does not stop overlap (from search snippet: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).
  - Implies: two channels that both believe they manage a session's lifecycle (spawn, retire, environment) will conflict. Plural membership must not mean plural management.
- **Kubernetes' fix was a persisted single owner, ControllerRef.** "Main goal of `ControllerReference` effort is to solve a problem of overlapping controllers that fight over some resources (e.g. `ReplicaSets` fighting with `ReplicationControllers` over `Pods`), which cause serious problems such as exploding memory of Controller Manager." Ownership had to be persisted: "we don't want a Controller Manager crash to cause massive changes in object ownership." A controller owns an object only if its selector matches *and* the controller-flagged OwnerReference points to it. Adoption happens only when no controller owner exists. The doc concedes "there are possible races during adoption if multiple controllers can own a given object." https://github.com/kdada/kubernetes/blob/v1.4.5/docs/proposals/controller-ref.md
  - Implies: this is the strongest single precedent. Keep plural membership (selection) and add one persisted owner field per session (its home channel), written once and changed only by an explicit transfer.
- **Owner references cannot cross scopes.** "Cross-namespace owner references are disallowed by design... If it does not [exist in the same namespace], the owner reference is treated as absent, and the dependent is subject to deletion once all owners are verified absent." https://kubernetes.io/docs/concepts/architecture/garbage-collection/
  - Implies: if the owner disappears (a channel is dissolved), the system needs a defined outcome for its sessions and machines: cascade, orphan or adopt. Kubernetes defaults to cascading deletion. For long-lived agent sessions the safer default is probably to orphan them to a fallback home channel (my judgment).

### Pools: from plural to exclusive membership (Buildkite, GitHub Actions)
- **Buildkite went from many queues to one.** "In unclustered environments, a single agent can be assigned to multiple queues. However, with clusters, each agent can only belong to one queue." "Agent tags in clusters are scoped to the specific cluster they belong to, unlike in unclustered environments where tags can be used across multiple queues." The stated rationale is "hard security boundaries", discoverability, and teams self-managing their pools. Unclustered agents are deprecated. https://buildkite.com/docs/pipelines/security/clusters/migrate-from-unclustered-to-clustered-agents
  - Implies: a mature system moved machines from plural to exclusive pool membership for manageability and security. Expect the same pressure on "environment belongs to which channel's pool". Make a machine's pool exclusive and use tags for finer selection inside it.
- **GitHub Actions runner groups.** A runner moves between groups ("can then be moved to another group", choosing one "destination group"), and a group grants access to a list of repositories or to all of them. The docs repeat: "We recommend that you only use self-hosted runners with private repositories" because forks can run code on the machine. https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access
  - Implies: the plural relation goes *group → many repositories* (access), not *machine → many groups*. The same shape fits here: a pool serves a channel spanning many repositories, and each machine sits in one pool.

### Plural membership in messaging (Matrix, Erlang pg, MPI)
- **Matrix spaces are directories, and a room may be in many of them.** A space is a room type, and sending normal messages in it "is discouraged". Clients "might wish to... explicitly ignore notification counts on space-rooms." The relation can be declared from either side. When only `m.space.parent` is set, "the rooms are 'secretly' added to spaces". To prevent false claims, a parent event is ignored unless the space has a matching child event or the sender has power in the space. On multiple parents: "Only one canonical parent should exist, though this is not enforced. To tiebreak, use the lowest room ID." https://spec.matrix.org/v1.11/client-server-api/ (Spaces section)
  - Implies three things. First, separate the grouping object from the conversation: a channel that is both a directory and a busy log is the case Matrix chose to avoid. Second, membership claims need consent from the channel side, so a session cannot just declare itself into a channel. Third, Matrix ended up needing a "canonical" parent anyway, which is the home channel again.
- **Erlang `pg` allows plural membership; groups have no owner and no existence when empty.** "A process may join multiple groups. It may join the same group multiple times." "It is only allowed to join processes running on local node." "If a member terminates, it is automatically removed from the group." "Groups are automatically created when any process joins, and are removed when all processes leave the group." "Process Groups membership view may temporarily diverge." https://www.erlang.org/doc/apps/kernel/pg.html
  - Implies three things. Joining is something a member does for itself, on its own node; nobody joins another process remotely. Death removes membership automatically, so a dead session should leave its channels without a cleanup step. Expect divergent views of a channel across machines during a network partition.
- **Why pg replaced pg2 (OTP 23).** The PR: "Empty groups are not supported: unlike a process, group does not have originating node. So it's possible that during net split one node deletes the group, that still exists for another partition. pg2 will re-create deleted group as soon as net split converges, which is quite unexpected." It also says "no cluster lock required, and no dependency on global". On scopes: "Scopes are completely independent of each other. A process may join any number of groups in any number of scopes." A commenter: "Current pg2 indeed really sucks in production, especially if you cannot guarantee 1ms latency between the cluster." https://github.com/erlang/otp/pull/2524 . Meiklejohn's experiments show pg2 groups "resurrecting themselves during the healing of a partition": https://christophermeiklejohn.com/erlang/2013/06/03/erlang-pg2-failure-semantics.html
  - Implies: with two Macs and VMs, a channel *definition* replicated peer-to-peer will resurrect or diverge. Give channel definitions one authoritative home, a file or one daemon. Keep only *membership* eventually consistent and owned by each member.
- **MPI communicators.** A communicator is a group plus a context. "Contexts partition the communication space. A message sent in one context cannot be received in another context." Libraries duplicate a communicator to get a private context so their traffic cannot collide with the application's. https://www.mpi-forum.org/docs/mpi-3.1/mpi31-report/node144.htm , https://www.netlib.org/utk/papers/intro-mpi/node9.html (read via search snippets only, not opened)
  - Implies: a member of several channels should receive every message tagged with exactly one channel, and a reply should go back to the channel it came from, never to "the member's channel". This is the routing half of plural membership: the address carries the channel.

### Agent systems' grouping units
- **Claude Code agent teams are exclusive and session-scoped.** "One team per session: a session has exactly one team, scoped to that session. You can't create additional named teams or share a team across sessions." "Lead is fixed: the main session is the lead for its lifetime." "No nested teams." https://code.claude.com/docs/en/agent-teams
  - Implies: Anthropic's own multi-session primitive kept membership exclusive and the owner fixed. It is evidence of what they chose to support, not of a failure with plural membership.
- **MCP Agent Mail: the project key is the repository, with a "Product Bus" across repositories.** The unit is `project_key`, by default the repository's absolute path ("a stable, collision-resistant project identity"). Across repositories there are two options. A: "register both sides under the same `project_key`" with disjoint reservation globs. B: "separate projects" linked by contact handshakes, keeping "a shared `thread_id` (e.g., ticket key) across repos". A "Product Bus" groups repositories "for product-wide inbox/search and shared threads". Suggested sibling links "do not automatically authorize cross-project messaging". Agent names are "unique per project", and import "aborts if agent-name conflicts would break uniqueness in the target". https://github.com/Dicklesworthstone/mcp_agent_mail
  - Implies: the closest prior art also hit "the repository is too small a unit". It layered a cross-repository grouping on top of the repository unit rather than replacing it. Aliases were unique per project, so cross-project grouping brought collision handling. If session aliases are unique per repository today, channels need either a qualified name (`alias@repo`) or channel-unique names.
- **Claude Tag, Cursor in Slack: the Slack channel is the unit, with repositories and pools as channel grants.** Claude picks "from the channel's grants" (https://claude.com/docs/claude-tag/users/troubleshooting). Cursor: "Anyone on your Cursor team can give a channel its own pool... `@Cursor` mentions in that channel then run on the channel's pool instead of the team default." Channel settings "override your personal defaults for that channel". https://cursor.com/docs/integrations/slack
  - Implies: the "channel = purpose, with granted repositories and a default pool" model ships in two products. Both make the channel a *configuration* scope (repositories, pool, memory), not a membership roster of long-lived agents.

## 2. Routing and a lead

### LLM routers and auto-selection
- **AutoGen GroupChat misdelivers silently.** "GroupChat select_speaker failed to resolve the next speaker's name." A leading space in " Coder" broke the lookup, and then "Speaker selection will default to the next speaker in the list." https://github.com/microsoft/autogen/issues/663 . Related: #842 (regression of the same), #6890 (names mentioned inside think tags counted toward selection), #7677 (round robin skipping an agent). https://github.com/microsoft/autogen/issues/6890 , https://github.com/microsoft/autogen/issues/7677
  - Implies: router failures land on a plausible but wrong recipient, with no error. If any routing is inferred, a failure must surface as "unaddressed", never as a fallback recipient.
- **AutoGen's own doc points away from heavy LLM selection.** "if you find yourself writing multiple conditions for each agent, it is a sign that you should consider using a custom selection function, or breaking down the task". Messages are "broadcasted to all other participants" and "the conversation context is kept within the team and all participants". https://microsoft.github.io/autogen/stable//user-guide/agentchat-user-guide/selector-group-chat.html
  - Implies: the default group-chat model is broadcast plus a shared context, the token pattern to avoid at 30 members.
- **Repository auto-pick in Slack-hosted agents is a documented wrong-pick source.** Claude Tag: "The request didn't name a repository, so Claude picked one from the channel's grants." Fix: "Start a new thread with the right one named in your first message." https://claude.com/docs/claude-tag/users/troubleshooting . Cursor's resolution order is message content, then recent activity, then keyword routing rules, then channel default, then user default. Options in the message "skip both default pools". https://cursor.com/docs/integrations/slack
  - Implies: both vendors resolve ambiguity with a deterministic precedence chain plus an explicit override, and both document misses. For "open a thread", require an explicit channel and environment, or apply a fixed default chain. Don't let a model pick the environment.
- **Claude Tag over-listens once mentioned.** "Once Claude is mentioned in a thread, it follows the whole conversation there and may reply to messages that weren't addressed to it." Channels have a "respond automatically" default that admins turn off. (same troubleshooting page)
  - Implies: if every member watches the channel log and decides for itself whether to answer, expect unaddressed replies. Default to responding only when addressed.

### Supervisor/lead vs swarm
- **LangChain benchmark (Tau-bench with distractor domains).** "the swarm architecture slightly outperforms supervisor architecture across the board". The supervisor's losses came from "translation... the sub agents cannot respond to the user directly". "supervisor consistently uses more tokens than swarm." The fixes were removing handoff messages from sub-agent state, adding a `forward_message` tool ("reduced errors caused by the supervisor agent paraphrasing the sub agent incorrectly") and tuning handoff tool names, for "a nearly 50% increase in performance". https://blog.langchain.com/benchmarking-multi-agent-architectures/
  - Implies: a lead in the path between threads and the human degrades fidelity. Here each thread reports to the human directly (the message tool), the swarm property LangChain found better. Keep it. If a coordinator exists, it should forward verbatim, not summarize.
- **LangChain now recommends against its own supervisor library.** "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases", for "more control over context engineering". https://github.com/langchain-ai/langgraph-supervisor-py
  - Implies: framework-managed supervision gave way to plain tool calls. A coordinator, if any, is just another member with the same verbs.
- **Leads implement instead of delegating.** Claude Code: "Sometimes the lead starts implementing tasks itself instead of waiting for teammates." "The lead can stop early too, deciding the team is finished before all tasks are actually complete." https://code.claude.com/docs/en/agent-teams . CrewAI: "Manager agents only execute tasks using their own tools and never delegate to other agents, effectively making the hierarchical process behave like a sequential process"; closed by the stale bot with no merged fix. https://github.com/crewAIInc/crewAI/issues/4783 (also #8368, manager delegating to itself)
  - Implies: a designated lead is a documented weak point. In this design a session is meant for a standing responsibility, so a "lead" would be one more standing role, not a router.
- **Anthropic's research system: the lead is a bottleneck.** "our lead agents execute subagents synchronously... creates bottlenecks in the information flow between agents. For instance, the lead agent can't steer subagents". Early failures were "spawning 50 subagents for simple queries... and distracting each other with excessive updates", and vague delegation caused duplicated searches. Cost: "multi-agent systems use about 15× more tokens than chats". Fit: "domains that require all agents to share the same context or involve many dependencies between agents are not a good fit... most coding tasks involve fewer truly parallelizable tasks than research". https://www.anthropic.com/engineering/multi-agent-research-system
  - Implies: "excessive updates" between agents is a named failure. Status posts in a shared channel log should be pull (read on demand), not push.
- **Cognition: agents conversing fail.** "agents today are not quite able to engage in this style of long-context proactive discourse with much more reliability than you would get with a single agent." "running multiple agents in collaboration only results in fragile systems. The decision-making ends up being too dispersed and context isn't able to be shared thoroughly enough." Principles: "Share context, and share full agent traces" and "Actions carry implicit decisions, and conflicting decisions carry bad results". https://cognition.ai/blog/dont-build-multi-agents
  - Implies: this argues against designing channels for agent-to-agent negotiation over shared work. Channels should coordinate sessions with separate responsibilities (low coupling), with full artifacts (commits, specs) as the medium, not chat summaries.
- **MAST (Berkeley): a taxonomy of multi-agent failures.** 14 failure modes in 3 categories, "(i) system design issues, (ii) inter-agent misalignment, and (iii) task verification", from 150 traces, validated on 1600+ traces across 7 frameworks. https://arxiv.org/abs/2503.13657 . The category shares (about 42/37/21%) come from the project site via a search snippet, not verified: https://sites.google.com/berkeley.edu/mast
  - Implies: about a third of failures are inter-agent misalignment (withholding information, ignoring other agents' input, derailment). Coordination primitives should make the important state durable and inspectable (a task ledger, a resolved flag), not rely on agents relaying it.

### Broadcast, overload, and publish-subscribe
- **MetaGPT replaced one-to-one messaging with a shared pool plus subscriptions.** "communicating this information each time in a one-to-one manner... can complicate the communication topology". "Sharing all information with every agent can lead to information overload... agents utilize role-specific interests to extract relevant information." https://arxiv.org/html/2308.00352v6 (Section 3.2, Appendix E.2)
  - Implies: an append-only channel log that members *pull* from, filtered by subscription, is the published remedy for broadcast overload. The current repository group chat already has this shape. Keep it a log, not a push.
- **Claude Code agent teams: no broadcast primitive.** The current docs (2026-11-10 archive and live): "To reach everyone, send one message per recipient." "Token costs scale linearly." https://code.claude.com/docs/en/agent-teams . Third-party guides say an earlier version had a broadcast "used sparingly since costs scale with team size", e.g. https://claudefa.st/blog/guide/agents/agent-teams-best-practices . I could not confirm that an official broadcast existed and was removed.
  - Implies: with 30 sessions, any post that wakes every member costs about 30 context insertions. A channel post should not wake members by default; DMs should.

### Gas Town (one person's fleet, the closest analogue)
- **Roles mix long-lived and ephemeral workers, and coordination is unreliable.** The Mayor is "the main agent you talk to most of the time". Crew have "long-lived identities". Polecats are "ephemeral per-rig workers". A Witness exists "just to watch over them and help them get un-stuck". Failures he names: "Some bugs get fixed 2 or 3 times... Other fixes get lost"; workers "get into a monkey knife fight over rebasing/merging"; "Claude Code is so miserably polite that GUPP doesn't always work in practice... It just sits there waiting for user input"; "Gas Town is also expensive as hell." https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04
  - Implies: in the nearest analogue, idle sessions failing to act on queued work was a primary failure, which needed nudges and patrol agents. If channel posts don't wake sessions, something must make "work addressed to you" actionable: a hook or an inbox poll at turn boundaries.

## 3. What a thread is

- **A2A: a long-lived context, immutable tasks.** "A `contextId`... groups multiple `Task` objects and independent `Message` objects. This gives continuity across a series of interactions." "Once a task reaches a terminal state... it cannot restart. Any subsequent interaction related to that task, such as a refinement, must initiate a new task within the same `contextId`." Rationale: "Clients reliably reference a task and its state", "Clear Unit of Work", and "removes ambiguity... whether to create a new task or restart an existing one." https://a2a-protocol.org/latest/topics/life-of-a-task/
  - Implies: the protocol answer to "standing role vs task" is both, at two levels. A standing thread (context) contains bounded, terminal tasks. Here, tasks map to subagents or to dated segments of the thread.
- **Gas Town: identity is persistent, sessions are cattle.** "In Gas Town, an agent is not a session. Sessions are ephemeral; they are the 'cattle'... an agent *is* a Bead, an identity with a singleton global address", with an inbox and a hook. "As soon as another session starts up for this agent role, it will start working on that step." "The biggest problem with Claude Code is it ends." (same Medium post)
  - Implies: binding one thread to successive sessions is the documented working pattern. The thread holds identity, inbox and pending work; a new session attaches and resumes.
- **Claude Tag: a thread outlives the session's capacity and configuration.** "The thread has grown past what one session can hold, and it stays too long forever; retrying there can't work." Fix: "Start a new thread. You can paste a summary." "A thread keeps the skills, plugins, and custom instructions it started with, so a thread created weeks ago can fall out of step with your organization's current setup". `@Claude !restart` "archives the stuck session and starts a fresh one with your organization's current configuration, and the fresh session still reads the thread." "Restarting abandons whatever the session was midway through, and there's no way to resume it." "The isolated workspace... is recycled after a period of inactivity." "A new thread only queues a second session behind the first." https://claude.com/docs/claude-tag/users/troubleshooting
  - Implies: the main documented failures of thread-as-session are context exhaustion and configuration drift in weeks-old threads. Both are fixed by rebinding a fresh session to the same thread. Make "restart this thread's session" a first-class verb, and make the thread readable by its next session.
- **Slack's agent API: session statuses.** Slack groups agent conversations "into threads" with titles via `agents.sessions.rename`. Status values are `processing`, `suspended` ("needs input from the user") and `active`. "The session status is how Slack knows a message is part of an agent interaction rather than a notification." "Sessions in the processing status time out after one hour." https://docs.slack.dev/ai/developing-agents
  - Implies: a small fixed status vocabulary (working / needs you / idle) with a timeout on "working" is the platform convention. It argues for a structured "set status" verb over free text.
- **Devin: sessions degrade with length.** The January 2025 update: "Keeping sessions under 10 ACUs (Devin's performance degrades in long sessions)". https://cognition.com/blog/jan-25-product-update . Current docs: "if a task would take you three hours or less, Devin can most likely do it. For longer tasks, break them into smaller sessions." "Try to keep sessions focused (XS, S, or M)". https://docs.devin.ai/essential-guidelines/when-to-use-devin
  - Implies: a standing responsibility must not mean a standing context window. The thread lives for weeks; each session behind it is short.
- **Context rot.** "LLMs do not maintain consistent performance across input lengths. Even on tasks as simple as non-lexical retrieval or text replication, we see increasing non-uniformity in performance as input length grows." https://www.trychroma.com/research/context-rot
  - Implies: this is the mechanism behind the previous two findings. Reading a long channel log into context degrades the reader, so `read` should be windowed or summarized by default.
- **Anthropic's long-running harness: handoff through a progress file and git.** "each new session begins with no memory of what came before." Failure modes: trying "to one-shot the app", and a later instance "would look around, see that progress had been made, and declare the job done". The fix was "the claude-progress.txt file alongside the git history". Open question: "it's still unclear whether a single, general-purpose coding agent performs best across contexts, or if better performance can be achieved through a multi-agent architecture." https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
  - Implies: a thread needs a durable, structured state artifact that its next session reads first. Its message history alone is not enough.
- **Zulip: topics end by being resolved.** Resolving a topic "makes it easy to track the status of each question, investigation, or notification". Suggested policy: resolve "When the work described in the topic is complete and any follow-ups have been transcribed". https://zulip.com/help/resolve-a-topic . "when starting a new conversation, you should start a new topic!" https://zulip.com/help/introduction-to-topics
  - Implies: stale threads are handled by an explicit resolved state, filterable in listings, not by deletion. Task threads resolve; standing-role threads don't. The `list` verb should hide resolved threads by default.
- **Claude Code agent teams: status drift and orphans after resume.** "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks." "After resuming a session, the lead may attempt to message teammates that no longer exist." https://code.claude.com/docs/en/agent-teams
  - Implies: self-reported status goes stale. Derive liveness ("does this session exist and when did it last act") from the daemon, and treat agent-set status as a hint.
- **OpenAI Assistants API: server-side threads retired.** The Assistants API (with server-side Threads) shut down on 2026-08-26; per OpenAI's notice as forwarded on a vendor forum, the Responses API plus Conversations reached "feature parity". https://help.zoho.com/portal/hi/community/topic/deprecation-notice-openai-assistants-api-will-be-shut-down-on-august-26-2026 (secondary; I did not read OpenAI's own notice)
  - Implies: weak evidence, noted for completeness. A platform-held thread object was replaced by a conversation object the client controls. It doesn't speak to agent fleets directly.

## 4. Environment pools

### Declaring where work may run
- **Kubernetes: attraction and repulsion are separate.** "Node affinity is a property of Pods that *attracts* them to a set of nodes... *Taints* are the opposite -- they allow a node to repel a set of pods." For dedicated nodes, a taint plus toleration lets the group *use* those nodes, but to make the group use *only* them "you should additionally add a label... and... node affinity". https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/
  - Implies: "a channel's pool" has two halves. Which machines this channel may use is attraction; which machines refuse other channels is repulsion, so a Mac running interactive work isn't picked by another channel. Declaring only the first leaks work onto the wrong machines.
- **Buildkite: one queue per agent; GitHub: one group per runner** (section 1). These are pools as exclusive, named sets with access granted outward to many pipelines or repositories.
- **Cursor: channel default pool, with explicit override and refusal instead of fallback.** Channel pool beats team default, and `pool=<name>` in a message skips both defaults. For a repo-bound pool with no resolved repository, "Slack rejects the mention with an ephemeral reply instead of falling back to managed infrastructure." https://cursor.com/docs/integrations/slack
  - Implies: when no environment in the pool matches, refuse loudly. Don't fall back to an arbitrary machine.
- **Codex cloud: environments are per-repository configuration, cached.** Setup scripts run with internet access; agent-phase internet is off by default. Container state is cached for up to 12 hours and invalidated when the setup script, environment variables or secrets change. https://developers.openai.com/codex/cloud/environments (via search snippet; page now labelled "Legacy")
  - Implies: an "environment" is usually a *recipe* (image plus setup), with machines as cached instances of it. The pool may be better declared as recipes plus capacity than as a list of named machines. The two Macs are the exception: named, persistent and shared.

### Ownership, lifecycle, orphans
- **GitLab Runner documents that machines are orphaned by default.** "When the runner process shuts down, idle machines in the pool are typically left to run. You must clean them up externally". `shutdown_drain` is off by default. `HeartbeatInterval` refreshes "a provider-side liveness label (`runner_manager_heartbeat`) on each tracked machine... so external cleanup can tell tracked machines from orphaned ones" (default disabled). https://docs.gitlab.com/runner/configuration/advanced-configuration/ . A user issue reports orphaned EC2 instances "costing $100s" (only the title was readable): https://gitlab.com/gitlab-org/ci-cd/docker-machine/-/issues/6
  - Implies: the creator-died case is the default outcome unless designed against. Tag every machine with its owner and a heartbeat at creation, and run a reaper that does not depend on the creator.
- **Karpenter: instances outlive the cluster that created them.** "We have and EKS cluster running for 10 days. After that we decided to delete it and found out that 20 ec2 instances are still running." The cause was a race in which the node object was deleted against the wrong instance ID, so "instance2 is running forever". Maintainer: "instances are left behind but the projected node is gone." https://github.com/aws/karpenter-provider-aws/issues/2734
  - Implies: the controller's record and the cloud's reality diverge. Reconcile against the provider's inventory (list by owner tag), not only against your own records.
- **OpenHands leaves runtime containers behind.** Issue #7914 reports runtime containers never cleaned up after normal use; it was closed "not planned" after going stale (search summary). https://github.com/OpenHands/OpenHands/issues/7914 . PR #6470 adds a shutdown listener to stop them: https://github.com/OpenHands/OpenHands/pull/6470
  - Implies: an agent platform hit the same problem with containers. Cleanup on graceful shutdown doesn't cover crashes.
- **GitHub ARC: ephemeral runners turn into zombies.** Stuck `EphemeralRunner`s after node drain, OOMKill or "lost communication" block new jobs. The official incident workaround was to delete the pods manually. https://github.com/actions/actions-runner-controller/issues/4197 , https://github.com/actions/actions-runner-controller/issues/4155 , https://github.com/orgs/community/discussions/204152 (search summaries; not opened)
  - Implies: "ephemeral" doesn't ensure cleanup; the failure paths need their own reaping.
- **E2B: kill by default, pause by opt-in.** "it defaults to **5 minutes** if you do not set one". `onTimeout: 'kill'` (the default) "terminates the sandbox... its state is gone". The maximum continuous runtime is 1 h (Hobby) or 24 h (Pro). "Paused sandboxes have **no time-to-live**" and "E2B never kills a paused sandbox on its own." https://docs.e2b.dev/faq/sandbox-lifetime
  - Implies: agent-sandbox vendors default to short life and automatic death, and make persistence opt-in. The design's "environment is a property of the session" should include a TTL that defaults to expiring. Paused-forever is its own leak (storage).
- **GitHub Codespaces: idle stop, maximum lifetime and retention fixed at creation.** Defaults: 30-minute idle timeout, 12-hour maximum lifetime, 30-day retention after stopping. Retention "is set at creation and does not change". The organization can cap it. https://docs.github.com/en/codespaces/setting-your-user-preferences/configuring-automatic-deletion-of-your-codespaces (via search summary)
  - Implies: lifecycle policy is captured when the machine is created and can't silently drift. Put the expiry on the machine record when it is created.
- **Coder: dormancy and auto-deletion are separate.** A workspace becomes dormant after an inactivity threshold, and auto-deletion acts after a further period. A PR made template edits to these settings ask for confirmation because they "drive the lifecycle executor directly" on existing workspaces. https://coder.com/docs/admin/templates/managing-templates/schedule , https://github.com/coder/coder/pull/30157 (search summaries)
  - Implies: two-stage reclaim (dormant, then deleted) gives the human a window to rescue a machine whose owning session ended.

## 5. Tools vs a CLI for agent-to-agent communication

### Performance and token cost
- **Zechner's benchmark: close; the tool's design dominates.** Over 120 runs, terminalcp as MCP and as CLI both had 100% success, with MCP "23% faster... and 2.5% cheaper". Conclusion: "it doesn't matter as much as you'd think... if you're building a tool from scratch and your users already have a shell tool available, just make a good CLI. It's simpler and more portable." When MCP makes sense: "stateful tools are easier to implement as MCPs than CLIs since MCP servers are stateful by default." "most often the GitHub MCP Server will lead to much worse results than just letting the agent run the command line tool directly." https://mariozechner.at/posts/2025-08-15-mcp-vs-cli/
  - Implies: performance doesn't decide this. A session's identity and its subscription cursor are state, and that's the case where Zechner says MCP fits.
- **Tool schemas cost context, and deferral mostly fixes it.** Anthropic: "58 tools consuming approximately 55K tokens before the conversation even starts". "At Anthropic, we've seen tool definitions consume 134K tokens before optimization." With Tool Search, about 77K fell to about 8.7K tokens, and accuracy rose (Opus 4: 49% to 74%). https://www.anthropic.com/engineering/advanced-tool-use . Claude Code defers MCP tool definitions, loading only names at start (https://code.claude.com/docs/en/mcp, per search summary).
  - Implies: five verbs cost a few hundred tokens of schema and are deferred anyway. The token argument against MCP doesn't apply at this size.
- **The commonest tool failure is confusing similar names.** "The most common failures are wrong tool selection and incorrect parameters, especially when tools have similar names like `notification-send-user` vs. `notification-send-channel`." (same Anthropic page)
  - Implies: this lands directly on "post to channel" vs "message a session". Use one `post` verb whose required target is a channel or a member, or names that differ in more than a suffix.
- **Tool count hurts selection.** RAG-MCP reports baseline tool-selection accuracy of 13.62% with a large MCP tool pool, rising to 43.13% with retrieval. https://arxiv.org/abs/2505.03275 (abstract via search summary)
  - Implies: a small verb set matters more than the transport.
- **Intermediate results pass through context.** "Every intermediate result must pass through the model." Code execution cut one workflow "from 150,000 tokens to 2,000 tokens". https://www.anthropic.com/engineering/code-execution-with-mcp
  - Implies: `read` must not return a whole channel log. Return a window or summary, with cursors, whether it's a tool or a CLI.

### The closest prior art's choices
- **MCP Agent Mail: MCP first, then macros against "tool overload", then a robot CLI.** Python version: clients should "render a narrow tool palette for the current workflow rather than dumping every verb", which "prevents 'tool overload'". For smaller models, "prefer the macro helpers... and hide the granular verbs". `fetch_inbox` takes `unread_only=true`, which "cuts token-burn for polling agents". https://github.com/Dicklesworthstone/mcp_agent_mail . The Rust rewrite has 45 tools and adds a robot CLI "when you need structured snapshots quickly, especially in automated loops and when tokens matter". It names three failure modes of the Python server under load: "Git lock file contention from concurrent writes, SQLite pool exhaustion under sustained load, and cascading failures when many agents hit the server simultaneously". https://github.com/Dicklesworthstone/mcp_agent_mail_rust
  - Implies: a large MCP surface for agent mail needed curation. A single shared server backing many agents hit write contention, so the channel log's storage and concurrency (30 writers, several machines) matter more than the tool-or-CLI question.
- **Gas Town and Beads: CLI-native.** Mail, nudges and work assignment are `gt`/`bd` commands ("`gt nudge` sends a tmux notification to a worker"); the post doesn't mention MCP. https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04 . Beads ships a CLI ("a CLI tool you install once and use everywhere") and a separate `beads-mcp` package. https://github.com/steveyegge/beads
  - Implies: a large, working single-owner fleet ran entirely on CLIs. A CLI is enough for the verbs. Its pains, nudging and politeness, were about waking sessions, not about the transport.
- **Claude Code agent teams: a built-in tool.** Teammates message with `SendMessage`. "Claude Code tells the receiving agent the message came from another Claude session, not from you." Mailboxes are JSON files per agent. https://code.claude.com/docs/en/agent-teams
  - Implies: the harness vendor made messaging a tool with harness-attested sender identity. A CLI can't attest who called it beyond environment variables the agent can rewrite.

### Permissions and shell failure modes
- **Bash permission patterns are fragile.** "Bash permission patterns that try to constrain command arguments are fragile." Variations such as options placed first or variables slip past the patterns. Compound commands need every subcommand allowed. MCP permissions are per tool name: `mcp__<server>__<tool>`. https://code.claude.com/docs/en/permissions
  - Implies: MCP gives a clean allow or deny per verb (for example, `post` allowed and `open_thread` asking). With a CLI, the same policy rests on argument patterns that the docs call fragile.
- **Heredoc-quoted message bodies triggered approval prompts.** "This $() command substitution causes every git commit to require manual user approval, even when the user has auto-accept enabled". Fixed in v2.1.71 as "false-positive permission prompts for compound bash commands containing heredoc commit messages". https://github.com/anthropics/claude-code/issues/31191 . Escaping bugs: backticks and `$` truncating messages (https://github.com/anthropics/claude-code/issues/1081), stray backslashes in quoted heredocs (https://github.com/threeal/.claude/issues/58), and Windows backslash halving (https://github.com/anthropics/claude-code/issues/98622) (search summaries; only #31191 opened).
  - Implies: free-text bodies (posts, DMs) are the worst case for a CLI: Markdown backticks, `$`, quotes, multi-line text. A JSON tool argument removes the whole class.
