1부 · 무엇이 문제였나
01

클로드 세션이 열 개 떠 있는데, 지도가 없었다.

누가 누구를 만들었는지, 지금 뭘 하는지, 어떻게 말을 걸어야 하는지 — 아무 곳에도 한 장의 그림이 없었다.

2026년 8월 말의 실제 상태. 세션은 있지만 조직은 없었다.

더 깊이 · 정확히 무엇이 두 조각으로 갈라져 있었나

이 저장소에는 같은 것을 반씩 설명하는 도구가 둘 있었다. skills/orchestrating-daemons/scripts/는 오래 사는 백그라운드 클로드 세션("데몬")을 띄우고, 이어가고, 추적하고, 은퇴시키는 bash 스크립트 묶음이었고, 데몬 하나당 JSON 하나를 ~/.claude/orchestrating-daemons/에 두었다. 한편 skills/sminos/scripts/sminos는 세션들에게 이름 있는 작업 그룹을 주는 bash CLI였다: 누가 누구를 낳았는지, 별칭에서 메시지 주소로의 매핑, 그리고 공동 게시판.

데몬 레지스트리는 세션의 태스크·워크트리·모델·생존 여부는 알았지만 어느 그룹에서 일하는지는 몰랐다. sminos는 그룹과 스폰 트리는 알았지만 프로세스에 대해서는 아무것도 몰랐다. "내 함대가 지금 뭘 하고 있나"를 물으려면 두 개의 list 명령을 두 가지 어휘로 쳐야 했고, 자기 그룹에 연결된 자식을 스폰하려는 에이전트는 다른 스킬 디렉터리의 스크립트에 환경변수 접두어를 붙여야 했다.

02

sminos는 일주일 사이에 세 번 태어났다.

v1은 파일 인박스, v2는 하네스의 네이티브 메시지, v3는 좌석. 이 글의 주인공은 v3와 그 위에 올린 화면이다.

각 세대는 그 전 세대가 실물과 부딪혀 배운 것으로 만들어졌다.

더 깊이 · 왜 v1을 버리고 v2로, 그리고 v3로 갔나

v1 (8/27)은 자체 배달 장치를 만들었다. 멤버마다 인박스 파일과 커서가 있고, 모든 멤버가 sminos listen을 영구 Monitor로 무장해야 했다. 설계 당시에는 네이티브 SendMessage를 전송 수단으로 쓸 수 없다고 판단했기 때문이다(셸에서 접근 불가, 이중 기록 드리프트). 살아보니 비용이 컸다: 모든 에이전트가 listener 무장을 기억해야 했고, 죽은 listener는 소리 없이 귀를 막았고, 무장된 listener는 세션을 영원히 state=working으로 고정시켜 하네스의 상태 표시가 거짓말을 하게 했다(그래서 --no-wait 규칙이 생겼다).

v2 (8/31)는 라이브 프로브로 뒤집었다. 네이티브 SendMessage는 idle 세션을 새 턴으로 깨우고, busy 세션에는 큐잉하고, 프로세스가 죽은 세션까지 트랜스크립트에서 되살려 배달한다는 것이 확인됐다. 그래서 sminos는 네이티브 도구가 못 하는 것만 남겼다 — 이름 있는 그룹, 스폰 토폴로지, alias→addr 레지스트리, 영구 보드. 두 개의 리뷰 발견은 모두 "업그레이드 경계" 결함이었다: 영구적이고 머신 전역인 상태 루트에서는 새 필드마다 옛 레코드에 대한 read-time 답이 필요하고, CLI 네임스페이스를 벗어나는 식별자(alias → 머신 전역 세션 이름)는 넓은 범위에서 유일성을 다시 검사해야 한다.

v3 (9/02, PR 92)는 남은 반쪽 — 프로세스를 아는 데몬 레지스트리 — 을 sminos 안으로 접어 넣었다. 이제부터가 이 글의 본문이다.

2부 · PR 92 — 좌석(seat)
03

의자는 남고, 사람은 바뀐다.

좌석(seat)은 그룹 안의 이름 있는 자리다. 역할이 있고, 클로드 세션 하나가 앉는다. 세션이 죽어도 좌석은 남는다.

sminos의 단위는 세션이 아니라 좌석이다. 이 한 가지 결정이 나머지 전부를 결정했다.

더 깊이 · 왜 "세션"이 아니라 "좌석"인가, 왜 그 이름인가

v2의 모델은 노드 = 살아 있는 세션이었다. 세션이 죽으면 그것이 속한 조직도 함께 지워지고, "다시 채우기"를 표현할 방법이 없다. 좌석은 조직을 프로세스 수명에서 분리한다. 좌석 하나는 동시에 0개 또는 1개의 세션에 채워지고, 세션을 가로질러 지속된다. 그룹 템플릿(조직을 한 번 정의하고 새 세션들로 인스턴스화)은 자연스러운 후속 과제로 미뤄졌다.

이름 후보와 낙선 이유: node(그래프 어휘, 지속성을 말하지 않음), post(보드의 post와 충돌), member(사람 단어). 좌석에 앉은 세션은 "에이전트"라 부른다. 예약된 정체성 human은 운영자다 — 좌석을 갖지 않지만 어느 보드에든 글을 쓸 수 있다.

좌석의 주소 지정: group/alias, alias가 유일하면 bare alias, 좌석 id(또는 접두어), 현재 세션의 short/full id. 이름은 [A-Za-z0-9._-]{1,64}.

04

좌석은 그룹 안에서 부모를 가리키고, 역할과 한 줄 상태를 지닌다.

그래서 sminos view login 한 번이면 조직도가 나온다 — 노드마다 살아 있음이 붙어서.

부모–자식 간선은 정보이지 규칙이 아니다. "부모와 자식을 우선하되, 필요하면 누구에게든" 이 프로토콜이다.

더 깊이 · 좌석에 붙는 두 종류의 자기 설명, 그리고 "그룹 없는 스폰"
  • now — 에이전트 자신이 sminos status <seat> "…"로 쓰는 한 줄. list/view/chart의 세 번째 줄에 보인다.
  • note — 오케스트레이터가 sminos mark로 쓰는 판단(done, awaiting-human 같은 상태와 함께).
  • 턴이 끝날 때 상태를 갱신하는 Stop 훅 아이디어는 접었다: 훅은 턴 안에서 발화하므로 턴을 요약할 수 없고, 살아 있음은 하네스가 이미 추적한다.

--group 없이 스폰된 좌석은 작업 디렉터리에서 그룹을 유도한다: git 저장소 안이면 git rev-parse --show-toplevel의 basename, 아니면 디렉터리 basename, 그것도 없으면 fleet. 보드 파이프라인 워커들이 디스패처가 그룹을 배우지 않고도 저장소별로 묶이는 이유다. 프리앰블(에이전트 프로토콜 텍스트)은 --group이 명시적일 때만 태스크 앞에 붙는다.

05

레지스트리는 폴더 하나다. 좌석 하나 = JSON 파일 하나.

~/.claude/sminos/. 좌석 id는 첫 세션의 uuid. 옆에 마지막 답장, 그룹 폴더 아래에 게시판.

~/.claude/sminos/                          ($SMINOS_HOME 으로 바꿀 수 있음; $DAEMON_HOME 은 옛 이름)
├── .metalock                             ← 모든 레코드 쓰기가 잡는 공유 flock
├── 47db7f50-ffd9-4002-….json             ← 좌석 하나 (seat id = 첫 세션의 uuid)
├── 47db7f50-ffd9-4002-….reply.txt        ← 그 좌석의 마지막 답장 텍스트
├── 6ca3cc60-e028-4735-….json
├── 6ca3cc60-e028-4735-….reply.txt
├── …                                     ← 이 머신에는 지금 77개 파일
└── groups/
    ├── demo/board.jsonl                  ← 그룹 게시판: 한 줄에 글 하나
    └── dogfood/board.jsonl

v3의 결정: 레코드는 기존 데몬 meta 파일 그대로에 조직 필드 7개(alias, group, parent, addr, role, brief, now)를 더한 것이다.

더 깊이 · 왜 데몬 레이아웃을 정본으로 삼았나, 그리고 read-time 폴백

데몬 meta는 이미 좌석의 모양이었다 — 원래 uuid에 의한 안정된 정체성, current 체이닝, role, ticket, note. 그리고 보드 파이프라인 스크립트 여섯 개가 이 레이아웃을 직접 읽고 쓴다. 이걸 정본으로 삼으면 그 여섯 스크립트는 기본 경로 하나만 바꾸고 계속 동작한다. 반대안(sminos v2의 groups/<g>/nodes/<alias>.json을 정본으로, 파이프라인을 다시 쓰기)은 여섯 writer, 열두 reader, 스무 개 테스트 파일을 다시 쓰는 일이어서 이 계획이 보드 파이프라인 재작성이 되어 버린다.

상태 루트는 영구적이고 머신 전역이다. 어떤 필드가 생기기 전에 쓰인 레코드(pre-seat 데몬 meta, v2 노드)는 alias/group/addr/role 중 아무것도 없다. 그래서 모든 읽기는 load_seat()를 거치고, 거기서 폴백이 적용된다: alias ← name, addr ← alias, group ← "fleet". 미묘한 것 하나: 옛 데몬 레코드에는 current 키 자체가 없고(옛 resume 폴백이 레코드 자신의 uuid를 이어갈 세션으로 썼다), v2에서 변환된 노드는 current가 있지만 비어 있다(진짜 빈 좌석). 그래서 폴백은 값이 비었는지가 아니라 키의 부재에 걸린다.

파일 권한: 이 CLI가 만드는 모든 것은 0700/0600이다(os.umask(0o077)). 모든 에이전트가 같은 OS 사용자로 돌기 때문에 group/other 권한은 필요 없다.

06

옛 레지스트리는 한 번의 rename으로 통째로 옮겨진다.

그리고 옛 자리에 심볼릭 링크를 남긴다. 옛 경로를 쥐고 있는 무엇이든 계속 풀린다.

복사가 아니라 이동인 이유: 두 루트가 있으면 반드시 서로 어긋난다.

더 깊이 · migrate()의 다섯 단계
  1. 옛 루트. 기본 루트를 쓰고 있고 옛 경로가 진짜 디렉터리이면, 기존 ~/.claude/sminos를 옆으로 치우고(.v2-<timestamp>), 옛 루트를 제자리로 rename, 옛 경로에 심볼릭 링크. 치워둔 루트의 groups/는 merge_asides가 다시 합치며 이후 호출마다 실행되므로 컷오버 중 크래시가 스스로 치유된다.
  2. 레코드별 스탬핑. group이 없는 레코드는 자신의 sminos_group 또는 cwd에서 유도한 값으로 스탬프. 레거시 codex-CLI 워커 레코드(engine: codex)는 상태가 이미 종결이거나 pid가 죽었을 때만 은퇴 — 살아 있는 pid를 가진 working/blocked는 건드리지 않는다. 강등은 updated를 절대 건드리지 않는다(파이프라인은 updated가 가장 큰 레코드를 고르므로, 패자를 bump 하면 정본 좌석을 밀어낸다).
  3. v2 레이아웃. groups/<g>/nodes/*.json은 은퇴한 좌석 레코드가 된다.
  4. alias 중복 제거. 같은 (group, alias)를 공유하는 레코드가 여럿이면(옛 기질이 한 이름으로 워커를 재스폰했다), claude 레코드가 codex를 이기고, 그다음 최신 updated가 이긴다. 패자는 <alias>@<short>로 개명되어 은퇴한다. 실제 레지스트리에서는 4개의 역사적 중복이 개명됐다.
  5. 매번. 루트 0700, 레코드/답장/에러 파일 0600 이하, 레거시 경로가 없으면 심볼릭 링크 복구, 중단된 컷오버가 남긴 aside 병합(충돌하는 보드는 id를 다시 매겨 이어 붙임).

설계 리뷰가 바꾼 것: 원래 계획은 sminos 동사에서만 마이그레이션이었다. 리뷰 발견 F2 — 파이프라인은 레지스트리를 직접 스캔하므로 빈 새 루트를 상대로 dedupe 할 수 있다. 그래서 모든 파이프라인 진입점이 preflight 직후 "$SMINOS_CLI" migrate를 실행하고, 직접 레지스트리 읽기 앞에서도 fail-closed로 실행된다.

07

"살아 있다"에는 일곱 가지 뜻이 있다.

화면에 찍히는 기호 하나가 그중 하나다. 레지스트리에는 절대 기록하지 않고, 볼 때마다 하네스에게 묻는다.

●
busy턴을 돌리고 있다
○
idle프로세스와 소켓은 살아 있고, 턴은 끝났다. 메시지가 오면 깨어난다
◐
blocked질문이나 권한 프롬프트에 걸려 있다
■
stopped프로세스가 내려갔다. 트랜스크립트는 있어서 attach 하면 깨어난다
◌
vacant좌석에 세션이 배정된 적이 없다. fill이 필요
✕
gone하네스가 이 세션을 더 이상 모른다
?
unknown하네스 자체를 물을 수 없었다 — 절대 "빈 함대"로 읽지 않는다

채워진 상태(FILLED) = busy · idle · blocked. 다시 채울 수 있는 상태(REFILLABLE) = vacant · stopped · gone.

더 깊이 · live 와 status 는 다른 것이다

live는 읽을 때마다 하네스에서 계산되는 값이고, status는 레코드에 기록된 턴 상태다(working, blocked, idle, error, retired, 그리고 sminos mark로 놓는 판단 상태 done/awaiting-human). 보드 파이프라인이 lane 슬롯을 세고 dedupe 하는 기준이 status라서 미러 의미를 유지했고, sminos sync가 그 미러를 하네스와 맞추는 조정 동사다(옛 daemon-finalize.sh). sync가 찍는 다섯 단어 어휘 — noop, live, absent, idle, error — 는 파이프라인이 switch 하는 값이라 동결됐다.

네이티브 wake가 들어오면서 미러는 더 자주 뒤처진다: SendMessage(또는 sminos send)로 깨어난 좌석은 sminos 동사가 한 번도 끼지 않은 채 턴을 통째로 돌리고 끝내므로, 레코드는 여전히 idle이고 .reply.txt는 이전 턴을 말한다. 그래서 sync와 reply는 기록된 status를 믿지 않고 트랜스크립트를 답장 파일과 비교한다. "이 좌석이 마지막으로 뭐라고 했나"가 필요한 모든 소비자는 그 두 동사를 거쳐야 하고, 파일을 직접 읽으면 안 된다.

더 깊이 · live_state() 가 실제로 어떻게 결정하나, 그리고 두 줄 문제

live_state(seat): current(지금 채운 세션 id)가 비면 vacant. 하네스 목록 자체를 못 얻었으면 unknown. 하네스 행이 있으면 normalize_state로 두 가지 lingering 모양을 접는다 — state=working & status=idle → done, state=blocked & status=idle → done-blocked. working이면 busy, blocked면 blocked, done/done-blocked면 피어 레코드가 살아 있으면 idle 아니면 stopped. 행이 없고 피어만 살아 있으면 피어의 status로 busy/idle. 둘 다 없으면 gone.

두 줄 문제. 같은 id로 claude --bg --resume을 하면 claude agents --json --all에 한 세션 id로 두 행이 남는다 — 멈춘 옛 job과 새 job. 그래서 세션 id만으로 찾으면 모호하다. harness_row(seat)는 좌석에 기록된 short(최근 launch)와 일치하는 행을 우선하고, 다음으로 running 행, 마지막으로 마지막 매치를 고른다. 결과적으로 resume은 busy/blocked뿐 아니라 idle로 lingering 하는 세션도 먼저 claude stop 해야 한다 — 아니면 하네스가 복사본을 시작한다.

이 세 정보원은 프로세스 수명 동안 캐시된다(_AGENTS, _PEERS, _PSTART). claude agents --json이 여기서는 약 1.2초 걸리기 때문이다. 오래 사는 화면은 이 캐시를 타이머로 갈아야 한다 — refresh_caches()가 PR 93에서 그 용도로 추가됐다.

더 깊이 · 스파이크 결과, "저장된 옵션" 규칙, 왜 wake 와 resume 이 둘인가

스파이크 (9/01). permission mode auto의 claude --bg 프로브가 idle 상태였다. Python 한 줄로 /tmp/cc-socks/<pid>.sock에 연결해 {"type":"user","message":{"role":"user","content":"PROBE-1 …"}}를 썼다. 세션은 몇 초 안에 새 턴을 시작했고, 텍스트를 "Another Claude session sent a message: … not typed by your user"로 프레이밍해 보았다 — 발신자 이름은 없었다(프레임이 싣지 않는다). 그래서 sminos send는 첫 줄에 발신자를 넣는다. 발신자 신원은 하네스에서 유도된다: 클로드 세션 안(CLAUDE_CODE_SESSION_ID가 Bash 환경에 있음)에서는 생략된 --from이 내 좌석의 alias로 풀리고 --from human은 거부된다 — 에이전트는 절대 운영자가 아니다. 진짜 터미널만 human이 기본이다.

저장된 옵션 규칙 (M4 라이브 증명이 가르침). claude --bg --resume <id>는 다른 플래그가 하나도 없을 때만 같은 id로 이어간다. 하네스 메시지 그대로: "background session 4d6ccff7 keeps its own saved options, so the flags you passed started a copy as 74fb1903." 첫 fill --resume 시도들은 -n/--permission-mode/모델 플래그를 실어서 매번 복사본을 만들었다(M1의 복사본 가드가 멈추고 exit 1). 옛 데몬 resume은 일부러 fork 했기에 이 규칙을 만난 적이 없었다. 그래서 resume에서 --model/--settings/--effort는 argv 호환을 위해 받지만 무시하고, 바꾸려면 fill(resume 없이)을 쓴다.

왜 동사가 둘인가. 설계 리뷰의 critical 발견: 보드 파이프라인의 후속 경로와 답변 릴레이는 run의 정체성(BOARD_RUN_TOKEN/BOARD_RUN_ID/BOARD_RUN_FENCE)을 resume 호출의 환경변수 접두어로 전달한다. 소켓 프레임은 돌고 있는 프로세스의 환경을 바꿀 수 없다. 즉 "이 좌석을 이어가라"에는 두 가지 뜻이 있다 — 돌고 있는 프로세스에 텍스트를 배달하라, 또는 내 환경에서 새 프로세스를 시작하라. 하나의 동사로 둘을 섬기면 live-socket 분기가 후속 run 정체성을 조용히 떨어뜨린다. 그래서 wake(대화형: 살았으면 소켓, 아니면 resume)와 resume(프로세스 레벨: 항상 새 프로세스, 살아 있는 턴은 먼저 claude stop)이 갈렸다. 파이프라인 호출 지점은 resume --wait를 쓴다.

wake --wait 의 증거 규칙. 대상은 배달 전에도 idle이었으므로 idle까지 폴링하면 이전 답장이 즉시 돌아온다. 그래서 프레임 첫 줄에 메시지 id를 싣고, 그 id가 대상 트랜스크립트에 나타나거나 세션이 busy로 바뀌는 것을 먼저 기다린다(SMINOS_ACK_TIMEOUT, 기본 120초). 증거가 없으면 exit 1, 답장으로 아무것도 찍지 않는다.

더 깊이 · 이 장치들은 어디서 왔나

대부분은 처음 설계가 아니라 세 번의 코드 리뷰 패널 라운드에서 왔다. 라운드 1(29건): 멈춘 좌석 위 스폰은 re-fill, 비밀 마스킹, 크래시-안전 락 마이그레이션, 조건부 finalize 쓰기, live-name+pid+socket 생존. 라운드 2(25건): re-fill 시 레코드 파일명 배너, gen 가드 조건부 finalize, addr 키 락을 wake/retire/remove/sync까지, resume 전 stop-and-wait, resume 시 cwd 거부, 마이그레이션의 alias dedupe와 권한 조이기, attempts/history, 자격증명 필드 거부. 라운드 3(26건): updated 보존 강등, 락 안에서 gen 스냅샷과 답장 쓰기, 락 걸린 unlink, 전임 소켓 거부, running 행 우선, re-fill 시 run/binding 필드 지우기, 세션 유도 발신자 신원, 하네스 실패 → unknown, 살아 있는 pid의 codex는 건드리지 않기, aside 보드 병합, sha1 정렬 락, no-resurrect 쓰기, procStart 검증.

라운드 1의 채택 두 건이 라운드 2에서 뒤집혔다(사라진 cwd에서 HOME으로 경고하고 실행하기; 레거시 codex pid에 시그널 보내기). 그것은 루프가 작동하는 것이지 흔들림이 아니다. 라운드의 발견이 장부 정리 수준으로 떨어졌을 때 루프를 멈췄다.

더 깊이 · 동결된 와이어 포맷, 그리고 손으로 몰지 말라는 규칙

동결된 것: 배너의 [<short> / <seat-id>], sync의 다섯 단어 어휘, 레지스트리 루트 우선순위 규칙 하나(SMINOS_HOME, 그다음 DAEMON_HOME)를 모든 진입점이 두 이름 모두로 export. 장애 스트릭(outage streak)은 history에서 실패한 점유자만 센다. codex-CLI 엔진 분기는 사라졌고, board-answer.sh는 어떤 보드 쓰기 전에도 codex 바인딩을 거부한다.

규칙: 파이프라인 워커를 손으로 몰지 마라. 워커는 티켓을 park 해서 에스컬레이션하고(issue-tracker의 who-unparks 판별식), 사람이 티켓에 답하고, board-answer.sh가 그 답을 sminos resume으로 릴레이한다. 내 답으로 직접 resume 하면 파이프라인이 제거한 판정자를 다시 들여오는 것이다.

기록만 하고 풀지 않은 가정 하나: 워커 부트스트랩은 "환경에 이미 있는 자격증명"을 쓰라고 하지만, v1의 라이브 발견은 하네스 Bash 도구가 claude 프로세스의 환경을 상속하지 않는다는 것이었다. BOARD_RUN_*가 실제로 워커의 도구까지 닿는지는 스텁으로만 주장된 상태다.

더 깊이 · layout() 을 손으로 따라가기

열 너비. 깊이 d의 열은 그 깊이에서 가장 넓은 내용 줄 + 4(테두리와 패딩), [min_w=16, max_w=30]으로 클램프. 열 사이 간격 gap=4. 박스 높이는 box_lines(3) + 2 = 5행이고 박스 사이에 빈 행 하나.

세로 배치는 후위 순회. place(n, d)는 먼저 자식들을 배치한다. 자식이 없으면 y = cursor; cursor += h + 1. 자식이 있으면 y = (첫 자식.y + 마지막 자식.y) // 2. 자식 밴드들은 서로소이고 순서대로라 형제 밴드는 절대 겹치지 않는다.

커넥터. 부모의 중간 행 pm에서 오른쪽 테두리 밖으로 ─ 하나, 그다음 열 bus = xr + 2에 세로 버스. 버스의 각 행은 첫 자식 행이면 ┌(부모 행과 같으면 ┬), 마지막이면 └(┴), 중간 자식 행이면 ├(┼), 자식 없는 행이면 │(부모 행이면 ┤). 자식 행마다 버스에서 자식 박스까지 ─를 채운다. 자식이 하나면 버스 없이 직선.

발견 하나. 부모가 자식들 가운데에 있으므로 부모 stub이 버스와 만나는 지점은 절대 ┬가 아니다: 자식 둘이면 부모가 그 사이(┤), 셋이면 가운데 자식과 만남(┼). ┬/┴는 부모 행이 첫/마지막 자식과 일치할 때만 나오는데, 가운데 규칙은 그런 경우를 만들지 않는다. M1 테스트는 계획이 처음 적었던 ┬ 대신 │─┼──│, ┌──│, └──│를 assert 한다.

접기 카운트. prune(c)가 자식 c를 접으면 부모의 hidden에 1 + count_nodes(c.children) + c.hidden을 더한다 — c 자신, c에 아직 매달린 것들, 그리고 prune이 c 아래에서 이미 접은 것들. 리뷰 전에는 +1만 더해서, 부모가 죽은 서브트리 전체 위에 "+1 retired"라고 말하는 동안 요약은 그 안의 모든 좌석을 셌다.

SMINOS_TUI_REFRESH초(기본 3)마다, 또는 r로 깨우면 즉시, sminos.refresh_caches() 후 take_snapshot()을 돌려 ("snapshot", roots, meta)를 events 큐에 넣는다. 하네스 읽기가 1초 이상 걸리기 때문에 그리기 스레드에서는 절대 돌리지 않는다. 읽기 실패는 flash 메시지가 될 뿐 화면을 죽이지 않는다. 스냅샷이 도착하면 rebuild()가 레이아웃을 다시 만들고, 포커스 좌석이 사라졌으면 포커스를 옮긴다 — 이 동작이 25장의 첫 번째 리뷰 발견의 원인이다.

뷰포트. 새로 놓인 포커스(시작 시, 또는 사라진 좌석에서 옮겨진 뒤)는 세로로 가운데 맞춤. 부모 박스가 자식들 범위 가운데에 놓이므로 키 큰 그룹에서 첫 루트가 차트 위쪽에서 멀리 아래에 있을 수 있고, 최소 스크롤만 하면 시작 시 포커스 박스가 화면 밖에 있게 된다. 방향키 이동은 최소 스크롤만 해서 화면이 차분하다.

더 깊이 · 재실행(enter_tmux) 과 리뷰가 잡은 new-session -A 함정

tmux 밖에서 sminos tui를 실행하면 자기 자신을 tmux 세션 sminos 안에서 다시 실행하고 터미널을 그 세션에 넘긴다(os.execvp, 돌아오지 않음). 원래 계획은 tmux new-session -A -s sminos였다. 리뷰 발견: 세션은 보통 차트보다 오래 산다 — Enter가 연 대화 창들이 세션을 살려 두기 때문이다. 그러면 new-session -A는 그저 attach만 하고 넘긴 명령을 버려서, 운영자는 차트 없이 옛 대화 창에 떨어진다. 지금은 tmux has-session으로 먼저 확인하고, 있으면 new-window -n chart로 새 창을 만든 뒤 attach 한다. 라이브로 검증: 세션을 잡고 있는 남은 창이 있는 상태에서 sminos tui가 창 chart를 열고 거기에 붙었다.

--no-tmux이거나 $TMUX가 없으면 Enter는 "다른 터미널에서 claude attach <short>를 실행하라"고 flash 한다.

attach와 send는 같은 세션 위의 독립된 표면이다: attach 해도 하네스 행, pid, 인박스 소켓은 그대로이고 sminos send는 여전히 배달된다. Ctrl+Z로 분리해도 아무것도 바뀌지 않는다. 그래서 차트는 둘 다 제공할 수 있다.

기각된 대안: 차트 옆 분할 pane(좌→우 레이아웃이 필요로 하는 차트 너비를 반으로 줄임); tmux 없는 in-place exec(의존성은 없지만 위에서 말한 대로 돌아오는 길이 끊김).

리뷰의 가장 나쁜 발견(25장)은 "입력 중에 리프레시가 포커스를 옮긴다"였다. 이것을 테스트하려면 입력 도중 포커스를 움직여야 하는데, 입력 모드는 모든 키를 삼키므로 키맵으로는 불가능하다. 헤드리스 실행은 프로세스 하나라 레지스트리를 중간에 바꿔도 스냅샷이 바뀌지 않는다.

두 개의 시계가 아홉 시간 어긋나 있었다. 그래서 살아 있는 좌석이 전부 "stopped"였다.

화면의 s를 처음 눌렀을 때 "demo/proof-scout is not live (stopped)"가 떴다. 좌석은 분명히 살아 있었다.

고친 것은 same_process() 함수 하나, 여섯 줄: 문자열이 아니라 순간(instant)을 비교하고, 기록된 문자열을 UTC로도 로컬로도 읽어 둘 중 하나가 2초 안에 맞으면 같은 프로세스다.

def same_process(rec):
    live     = _parse_lstart(proc_start(rec.get("pid")))      # ps, LC_ALL=C, 로컬 시각
    recorded = _parse_lstart(rec.get("procStart"))            # 하네스, UTC 시각
    if not live or not recorded:
        return True                                           # 못 읽으면 pid+socket 규칙이 결정
    live_epoch = time.mktime(live)
    return any(abs(reading - live_epoch) <= 2
               for reading in (time.mktime(recorded),        # 로컬로 읽었을 때
                               calendar.timegm(recorded)))   # UTC 로 읽었을 때
더 깊이 · 이 검사는 애초에 왜 있나, 왜 "둘 다 받아들이는" 게 안전한가

pid는 재사용된다. 죽은 세션의 피어 레코드가 남아 있는데 그 pid를 다른 프로세스가 받으면, "pid가 살아 있다"는 거짓 양성이 된다. 그래서 라운드 3 리뷰가 "레코드의 pid가 여전히 레코드가 묘사한 그 프로세스인가"를 시작 시각으로 확인하라고 했다 — 옳은 요구였고, 그 구현이 텍스트 비교였다.

두 읽기를 모두 받아들이면 재사용된 pid가 검사를 통과하려면 정확히 같은 벽시계 초에(또는 정확히 존 오프셋만큼 떨어져서) 시작했어야 한다. 잘못 통과해도 비용은 실패한 소켓 connect 하나다. 어느 쪽이든 파싱이 안 되면 검사를 건너뛰고 pid+socket 규칙이 결정한다.

왜 이 단계에서 고쳤나(다음으로 미루지 않고): 이 단계의 첫 번째 행동은 Enter(attach)이고 두 번째는 s(send)다. 결함이 있는 채로면 s는 모든 좌석에서 거부되어, 주 행동이 절대 동작하지 않는 화면을 출시하게 된다. 수정은 함수 하나의 여섯 줄이고, 테스트에 필요한 "진짜 돌고 있는 프로세스"는 스위트가 이미 갖고 있었다(인박스 소켓 서버).

더 깊이 · 왜 v3 스위트는 애초에 이걸 잡을 수 없었나

v3 스위트의 피어 레코드는 지어낸 것이었고 procStart 필드가 아예 없었다. 어느 한쪽이라도 파싱이 안 되면 검사는 건너뛴다. 그러니 스위트는 하네스가 실제로 쓰는 필드의 모양에 대해 아무 주장도 하지 않았고, 그 모양(존 표기 없는 UTC)이 문제였다. 지금 스위트의 회귀 블록은 자기 자신의 살아 있는 소켓 서버 프로세스 — 시작 시각이 진짜인 — 를 상대로 procStart를 UTC로 써 넣고, 그 좌석이 idle로 읽히고 send가 성공하는지 확인한다.

sminos.proc_start는 처음부터 LC_ALL=C로 ps를 불렀다. 테스트 헬퍼만 안 그랬다. 같은 외부 표면(ps 출력 형식)에 대한 믿음이 두 곳에서 다르게 코드화되어 있었고, 한 곳만 맞았다.

지름길 하나를 기각했다: startedAt은 프로세스 시작 시각이 아니다.

하네스 행에는 epoch 필드 startedAt이 있다. 그걸 쓰면 파싱 문제가 사라진다. 그런데 백그라운드 세션에서는 프로세스가 startedAt보다 2,517초 오래됐다.

그래서 수정은 procStart를 두 가지로 읽는 쪽이었지, epoch 필드로 갈아타는 쪽이 아니었다.

      --group login --parent architect --role IMPL --worktree impl-a

sminos view login                 # 트리: architect [ARCH] · idle  └── impl-a [IMPL] · busy
sminos chart login                # 같은 것을 박스 조직도로
sminos tui login                  # tmux 안에서 화면으로 — ↑↓←→ 이동, Enter 로 대화 열기, s 로 메시지

sminos send impl-a "상태?"        # 살아 있는 좌석의 인박스 소켓으로; idle 이면 깨어난다
sminos reply impl-a               # 마지막 답장 (대기 중인 질문이 있으면 그것)

sminos retire impl-a              # 세션은 멈추고 좌석은 남는다
sminos fill impl-a --resume "계속" # 같은 세션 id 로 이어간다
