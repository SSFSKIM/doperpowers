## Brief

**Purpose.** sminos is about to treat the thread that made a devcloud VM as the VM's owner: such a thread is not retired, and not ended after three days stopped, while the VM exists (the spec's D4). sminos keeps no copy of who owns what; it asks devcloud. That question has to be one whose "none" can be trusted, because a wrong "none" ends the owner of a VM that goes on costing money. Today's `devcloud vm ls` cannot be that question: it skips an account it cannot use and a provider listing that failed, and reports what is left with exit 0 (`Context.usable`, `Context.fleet` in `devcloud/driver/context.py`; `ops.ls` in `devcloud/driver/ops.py`).

**What done looks like** (the spec's DV section and contract X9 bind; read both, and D4's paragraph on ownership):

1. A command of the driver answers, for one or more names of a creator, which VMs they own. A name is a creator tag as descriptors hold it (`@short`, `@alias#short`, `@alias`, `@project/alias`: `_CREATOR` in `devcloud/boot/devcloudlib/descriptor.py`) or a session's short id; a VM matches when its creator tag equals a given tag or carries a given short id.
2. Its answer, in a form a program reads, is exactly one of: the VMs that match (each with what a caller needs to name it to a person: at least its name and provider or account); none, having listed every configured account in full; or unknown, naming each account that could not be used and each provider whose listing failed. A provider failure or an unusable account never yields "none". When some VMs matched and something else could not be listed, the answer carries both: the caller treats a match as owning whatever else is unknown.
3. The three answers are told apart without parsing prose (the exit code, a field, or both: your call, stated in this ledger).
4. On a machine where the driver does not run (a devcloud host, where every `vm` command exits 6 today), nothing changes: the caller does not ask there (X9).
5. Tests cover: a match by tag and by short id; a complete none; an unusable account with no match elsewhere (unknown, not none); a provider whose listing fails (unknown); a match plus an unusable account. The devcloud gates pass through `ci-gate` from this worktree.
6. devcloud's version is bumped in the same change (`scripts/bump-version.sh --plugin devcloud`; `--since origin/main` checks it), and the nested `CLAUDE.md` beside the code says what the command is for.

## Decisions

- **X9, exactly as built (2026-11-17).** This is the contract's content; T1 builds against it.

  `devcloud vm owned-by <name>...`. Each name is a creator tag in one of `descriptor.py`'s `_CREATOR` forms (`@short`, `@alias#short`, `@alias`, `@project/alias`) or a bare short id (`[0-9a-f]+`). Anything else, or no name, is exit 2.

  Matching: a host holds its creator's short id (the provider label `devcloud-creator=<short>`, which is all the driver can read of a VM; an adoption record's `creator`). The host's tag is `@<short>`. A name matches when it equals that tag, equals the bare short id, or ends in `#<short>`. A short id matches whole, never as a prefix. `@alias` and `@project/alias` match nothing devcloud writes today. Every devcloud-labelled server kind is checked; only `vm` carries a creator.

  The answer is one JSON object on stdout, one line, exit 0, whichever answer it is:
  - `answer`: `"owned"` when any host matched, whatever else is unknown; otherwise `"unknown"` when anything could not be listed; otherwise `"none"`, meaning every configured account was listed in full.
  - `vms`: the hosts that matched, each `{name, account, provider, creator}`. An adopted host is `{name, "account": "adopted", "provider": null, creator, "adopted": true}`.
  - `unknown`: what could not be asked, each `{account, provider, failed, reason}`. `failed` is `"account"` when the account could not be used (not registered, no passing copy, a changed copy, a provider that is neither shipped nor in the profile) and `"listing"` when its list failed (the provider's exit or timeout, an answer that is not a list, a credential that could not be read). An adoption record that does not read is `{"account": "adopted", "provider": null, "failed": "listing", reason}`.
  - `listed`: the accounts listed in full.

  The `answer` field is what tells the three apart; the exit code does not. Exit 0 means an answer was printed. Any other exit printed no answer, and the caller treats it as unknown: 1 (an unreadable profile, a crash, no Python 3.11), 2 (usage, or a `driver.toml` that does not load). The one exception is exit 6, which means the driver does not run on this machine (a devcloud host, or no seed key); D4 makes that answer none, and X9 says the caller does not ask there anyway.

  It asks no host over ssh, runs no reaper and changes nothing. It makes one `list` per usable account and reads the local adoption records.

  The three answers (invented values):

  ```
  {"answer": "owned", "vms": [{"name": "dc-a-0001", "account": "main", "provider": "hetzner", "creator": "@abcd1234"}], "unknown": [], "listed": ["main", "spare"]}
  {"answer": "none", "vms": [], "unknown": [], "listed": ["main", "spare"]}
  {"answer": "unknown", "vms": [], "unknown": [{"account": "spare", "provider": "gce", "failed": "account", "reason": "provider gce of account spare has no passing copy yet (run devcloud vm provider test spare)"}], "listed": ["main"]}
  ```

  A match plus something that could not be listed:

  ```
  {"answer": "owned", "vms": [{"name": "dc-a-0001", "account": "main", "provider": "hetzner", "creator": "@abcd1234"}], "unknown": [{"account": "spare", "provider": "gce", "failed": "listing", "reason": "provider gce/spare: list failed (exit 1)"}], "listed": ["main"]}
  ```
- **The name.** `owned-by` keeps it apart from EN's coming `vm owner <vm> <thread>`, the handover, which `owned` would sit one letter from.
- **Adopted hosts count as owned.** An adoption record carries its creator's short id, and its lease notice goes to that creator. A thread that adopted a machine and was then retired would leave that machine with nobody to release it. The records are local files, so they add no new way for the answer to be unknown beyond a record that does not read.
- **The listing is a new `Context.census`, and `fleet` is left alone.** `ls`, `find` and the reaper keep their skip-and-warn listing. `census` tries every configured account and returns the entries, the accounts listed in full, and what failed. It catches every `DriverError` an account raises, not only exit 7, so a provider that is neither shipped nor in the profile (exit 2 from `working_file`) or a credential that cannot be read becomes unknown, not an error for the whole command.
- **The skill is unchanged.** No session runs this verb. It is in `devcloud/CLAUDE.md` and in the README's command section, where it is marked as a program's question.

## Surprises

- The provider label `devcloud-creator` holds only the short id, and the label alphabet `[a-z0-9-]` could not hold a tag. The descriptor's `DEVCLOUD_CREATOR` holds `@short`, but it lives on the VM, where the driver cannot list it. So "the creator tag as descriptors hold it" reduces to `@<short>` for anything the driver can see. That is why names that carry no short id never match.

## Flow-back

- **For T1: what "where the driver does not run" means.** It is exit 6, or `devcloud` not being on PATH. A Mac that made VMs and then lost its seed file also answers exit 6, and D4 makes that a none, which would end the thread that owns those VMs. This was not guarded: it is rare, and a guard would need a record of the seed's past that the driver does not keep. T1 may want its refusal text to name exit 6 for what it is.
- **For T1: PATH.** `devcloud` is on a session's PATH because it lives in the plugin's `bin/`. The sminos daemon, which runs the three-day rule, may not have it on PATH. T1 has to find the CLI itself, as the driver finds `sminos` in `context._sminos`.
- **For T1: the names to pass.** Pass the short id of each session id the thread has had, bare or as `@short`. A name with no short id (`@alias`, `@project/alias`) matches nothing devcloud writes today.
- **For the spec's DV and X9 text.** X9 says "the VMs that name them". As built, that includes adopted machines (see Decisions). Neither the spec nor X9 says otherwise, so the parent's text needs a word if the owner disagrees.
