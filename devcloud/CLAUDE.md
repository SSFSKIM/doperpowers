# devcloud/

A path here is named from `devcloud/` when it is the plugin's own file; `docs/`, `scripts/` and `devcloud/…` paths are the repository's. The secrets guard mod's detail is in `hooks/mods/CLAUDE.md`.

A second plugin in this marketplace (its entry found by name, versioned on its own: `scripts/bump-version.sh --plugin devcloud`), opt-in, design in `docs/doperpowers/specs/2026-10-15-devcloud-design.md`.

The host: `image/` (`setup.sh`, which runs `packages.sh` first; the `Dockerfile`, which runs `packages.sh` as four layers, one per part, keyed on that file alone, then the rest of `setup.sh`) and `boot/` (`devcloud-boot`, steps 1–13 in `devcloudlib/steps.py`, step 12's projects and mirror cache in `devcloudlib/projects.py`, step 11's sminos daemon on an enrolled persistent host in `devcloudlib/sminos_host.py`, step 13's MAWS endpoint provisioning and the departure's certificate retirement in `devcloudlib/maws_host.py`, the tailnet join with the Tailscale OAuth client in step 4; `devcloud` for status and the jobs; `devcloud-services`, the supervisor where PID 1 is not systemd), tested in containers by `devcloud/tests/run.sh` (the `devcloud-*` gates, one part each: `DEVCLOUD_PART`, the integration parts in `tests/integration.py`'s `PARTS`).

`skills/devenv/` writes a repository's `devenv/` from its CI, manifests and README and proves it with `devenv up`.

The VM driver: `driver/` (`devcloud vm`, run by `bin/devcloud`; the shipped providers in `driver/providers/`), design in `docs/doperpowers/specs/2026-10-21-devcloud-vm-driver-design.md`, unit-tested in `tests/unit/test_driver_*.py` and the providers' own tests; `skills/vm/` is what a session reads to use it. One verb is a program's, not a session's, and stays out of the skill: `vm owned-by` (`driver/owned.py`, over `Context.census`), sminos's question before it retires or ends a thread, which hosts name a creator, answered owned, none or unknown and never a none that a skipped account or a failed listing could make wrong (an account whose provider never passed under this profile is the one it may leave unasked, on confirmed absence of any pass artifact: it holds none of the asking threads' hosts) (contract X9 in `docs/doperpowers/specs/2026-11-17-sminos-channels-and-threads-design.md`); its exit 6, which the caller reads as none, comes only from a host, a copy without `driver/` (`boot/devcloud`) or a missing seed key (the driver), never from a driver that fails to import; where no Python 3.11+ is on PATH, `bin/devcloud` makes the same three refusals itself, each only on confirmed evidence, and is otherwise exit 1. A second program's verb, also out of the skill: `vm info [--within <seconds>] <name>...` (`driver/info.py`; EN.G2's plan `docs/doperpowers/plans/2026-11-23-sminos-environments-en-g2.md`, §2), what each named host is for sminos's `channel show` (its creator, `created`, and `spent`/`currency` at the type's list price by `ops.spent`, `vm ls`'s own rule, both null for one host whose amount is no finite number), by name without regard to case, every account walked under `Context.bounded(<within>)` with each account's fate recorded as it is walked (`listing`, `account`, or `time` for a call not started or ended by the budget; a provider that cannot be opened or started, an `OSError`, is that account's failure, never an escape that loses the reply), `unused` as `owned-by` computes it, a type list with a row that is no type's name leaving costs unknown; it asks no host, runs no reaper and writes nothing. Its reply's shape is pinned by `tests/unit/test_driver_info.py` and read by sminos's `sminos/tests/test_vm_info.py`, which builds its replies with `driver/info.py`'s own builders (the `sminos-on-devcloud` gate runs it); change neither side alone. `bin/devcloud`'s own refusals cover `owned-by` alone, so where no Python 3.11+ is on PATH `vm info` is exit 1, which `channel show` reads as no answer.

`vm owner` (`driver/owner.py`; EN.G1's plan `docs/doperpowers/plans/2026-11-21-sminos-environments-en-g1.md`, §5) hands a host to another thread, which sminos names (`sminos who --thread`, `context.sminos_thread`): the host first, through the program the driver sends as root (`driver/owner_host.py`, which loads the host's own library from beside its `devcloud`, so the host's own parser decides; nothing under `boot/` serves it), then the label or the adoption record, then both read back; a thread whose project this machine's enrollment does not carry (the answer's `not_carried`) is handed the host with a warning, and a signal between the writes is said as which side holds what. On a Mac, every merge of a server's labels goes through `Context.merge_labels` and every write of an adoption record after its first through `adopt.update`, each under `Context.host_lock` (one lock file per host name, held for the read and the replace, never across a call to a host); a test holds a merge open with the stand-in provider's `gate`.

`vm up --enroll --expect-creator <short>` (`driver/up.py`'s `asked`, before the reaper's run and any provider call) is what `sminos spawn --on new` runs (EN.G1's §9): the MAWS project added where no named one provisions, and nothing made unless the creating session `ctx.creator()` reads is that short id. A new host's descriptor names its owner's project by id where `sminos who --thread <the calling session>` answers for that very session (`context.creator_project`), else by name. sminos reads some of the driver's human lines (`up`'s `<name>  ready in …`, and where `up` fails its `caps` line, its `created   <name> (id …) from …` and its recount's two lines that say it deleted the VM, said only once `Context.delete` confirmed it; `Context.find`'s `no VM named`): each is pinned by a unit test named for its reader, so change none without sminos's `sminos_on.py`. A failure of `up` after the create says a lease bounds the VM only where it has one (`up.kept`), and `--enroll` whose boot skipped the provisioning that enrolls (the `maws` step neither `ok` nor `deferred`) fails, naming the kept VM, instead of printing `ready`.

A host's notices (the idle notice, `boot/devcloudlib/idle.py`; the lease warning, `lease.py`) go through `notices.deliver`: the chain (the owning thread, its project's live members, its project's log, then the journal and `wall`), then, wherever the host's sminos is found and cut over, one `say --notice devcloud --pools <text>` that records the notice in every channel whose pool holds the host (EN.G2's plan `docs/doperpowers/plans/2026-11-23-sminos-environments-en-g2.md`, Interfaces §5). That call and the exits it reads are frozen on every host built from this library: exit 2 is a sminos without `--pools`, never a reason to send again; the text is the notice's own full text (`CHANNEL_TEXT = "full"`, the owner's answer to EN.G2's O6), repositories with unpushed work included, read by everyone who may read the channel's log; set to `"short"` it is the short one each notice composes (`short=True`), and with no short text given no call is made. A host that has not read its removal from a pool records one more notice there, naming those repositories. Which channels, and that the pool is the host's own copy's, is sminos's (`sminos_channels.record_in_pools`).
