# devcloud/

A path here is named from `devcloud/` when it is the plugin's own file; `docs/`, `scripts/` and `devcloud/…` paths are the repository's. The secrets guard mod's detail is in `hooks/mods/CLAUDE.md`.

A second plugin in this marketplace (its entry found by name, versioned on its own: `scripts/bump-version.sh --plugin devcloud`), opt-in, design in `docs/doperpowers/specs/2026-10-15-devcloud-design.md`.

The host: `image/` (`setup.sh`, which runs `packages.sh` first; the `Dockerfile`, which runs `packages.sh` as four layers, one per part, keyed on that file alone, then the rest of `setup.sh`) and `boot/` (`devcloud-boot`, steps 1–13 in `devcloudlib/steps.py`, step 12's projects and mirror cache in `devcloudlib/projects.py`, step 11's sminos daemon on an enrolled persistent host in `devcloudlib/sminos_host.py`, step 13's MAWS endpoint provisioning and the departure's certificate retirement in `devcloudlib/maws_host.py`, the tailnet join with the Tailscale OAuth client in step 4; `devcloud` for status and the jobs; `devcloud-services`, the supervisor where PID 1 is not systemd), tested in containers by `devcloud/tests/run.sh` (the `devcloud-*` gates, one part each: `DEVCLOUD_PART`, the integration parts in `tests/integration.py`'s `PARTS`).

`skills/devenv/` writes a repository's `devenv/` from its CI, manifests and README and proves it with `devenv up`.

The VM driver: `driver/` (`devcloud vm`, run by `bin/devcloud`; the shipped providers in `driver/providers/`), design in `docs/doperpowers/specs/2026-10-21-devcloud-vm-driver-design.md`, unit-tested in `tests/unit/test_driver_*.py` and the providers' own tests; `skills/vm/` is what a session reads to use it. Two verbs are programs', not a session's, and stay out of the skill:

- `vm owned-by` (`driver/owned.py`; contract X9 in `docs/doperpowers/specs/2026-11-17-sminos-channels-and-threads-design.md`) is sminos's question before it retires or ends a thread. Its caller reads exit 6 as "none", so exit 6 comes only on confirmed evidence (a host, a copy without `driver/`, no seed key), never from a driver that fails to import; `bin/devcloud` makes those refusals itself where no Python 3.11+ is on PATH.
- `vm info` (`driver/info.py`) is what each named host is for sminos's `channel show`. Its reply's shape is pinned by `tests/unit/test_driver_info.py` and read by `sminos/tests/test_vm_info.py`, which builds its replies with `driver/info.py`'s own builders (the `sminos-on-devcloud` gate): change neither side alone.

`vm owner` (`driver/owner.py`) hands a host to another thread: the host first, through the program the driver sends as root (`driver/owner_host.py`, which loads the host's own library, so the host's parser decides), then the label or adoption record. On a Mac, a merge of a server's labels goes through `Context.merge_labels` and a rewrite of an adoption record through `adopt.update`, each under `Context.host_lock`, never held across a call to a host.

`vm up --enroll --expect-creator <short>` (`driver/up.py`'s `asked`) is what `sminos spawn --on new` runs. sminos reads some of the driver's human lines (`up`'s `ready in …`, its `caps` line, its `created …` and deletion lines, `no VM named`): each is pinned by a unit test named for its reader, so change none without sminos's `sminos_on.py`.

A host's notices (`boot/devcloudlib/idle.py`, `lease.py`) go through `notices.deliver`: the chain (the owning thread, its project's live members, its project's log, then the journal and `wall`), then one `say --notice devcloud --pools <text>` that records the notice in every channel whose pool holds the host (which channels is sminos's, `sminos_channels.record_in_pools`). That call and the exits it reads are frozen on every host built from this library, so a change must keep old hosts working: exit 2 is a sminos without `--pools`, never a reason to send again.
