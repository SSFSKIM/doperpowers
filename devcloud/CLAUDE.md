# devcloud/

A path here is named from `devcloud/` when it is the plugin's own file; `docs/`, `scripts/` and `devcloud/…` paths are the repository's. The secrets guard mod's detail is in `hooks/mods/CLAUDE.md`.

A second plugin in this marketplace (its entry found by name, versioned on its own: `scripts/bump-version.sh --plugin devcloud`), opt-in, design in `docs/doperpowers/specs/2026-10-15-devcloud-design.md`.

The host: `image/` (`setup.sh`, which runs `packages.sh` first; the `Dockerfile`, which runs `packages.sh` as four layers, one per part, keyed on that file alone, then the rest of `setup.sh`) and `boot/` (`devcloud-boot`, steps 1–13 in `devcloudlib/steps.py`, step 12's projects and mirror cache in `devcloudlib/projects.py`, step 11's sminos daemon on an enrolled persistent host in `devcloudlib/sminos_host.py`, step 13's MAWS endpoint provisioning and the departure's certificate retirement in `devcloudlib/maws_host.py`, the tailnet join with the Tailscale OAuth client in step 4; `devcloud` for status and the jobs; `devcloud-services`, the supervisor where PID 1 is not systemd), tested in containers by `devcloud/tests/run.sh` (the `devcloud-*` gates, one part each: `DEVCLOUD_PART`, the integration parts in `tests/integration.py`'s `PARTS`).

`skills/devenv/` writes a repository's `devenv/` from its CI, manifests and README and proves it with `devenv up`.

The VM driver: `driver/` (`devcloud vm`, run by `bin/devcloud`; the shipped providers in `driver/providers/`), design in `docs/doperpowers/specs/2026-10-21-devcloud-vm-driver-design.md`, unit-tested in `tests/unit/test_driver_*.py` and the providers' own tests; `skills/vm/` is what a session reads to use it. One verb is a program's, not a session's, and stays out of the skill: `vm owned-by` (`driver/owned.py`, over `Context.census`), sminos's question before it retires or ends a thread, which hosts name a creator, answered owned, none or unknown and never a none that a skipped account or a failed listing could make wrong (contract X9 in `docs/doperpowers/specs/2026-11-17-sminos-channels-and-threads-design.md`); its exit 6, which the caller reads as none, comes only from a host, a copy without `driver/` (`boot/devcloud`) or a missing seed key (the driver), never from a driver that fails to import; where no Python 3.11+ is on PATH, `bin/devcloud` makes the same three refusals itself, each only on confirmed evidence, and is otherwise exit 1.

`vm owner` (`driver/owner.py`; EN.G1's plan `docs/doperpowers/plans/2026-11-21-sminos-environments-en-g1.md`, §5) hands a host to another thread, which sminos names (`sminos who --thread`, `context.sminos_thread`): the host first, through the program the driver sends as root (`driver/owner_host.py`, which loads the host's own library from beside its `devcloud`, so the host's own parser decides; nothing under `boot/` serves it), then the label or the adoption record, then both read back; a thread whose project this machine's enrollment does not carry (the answer's `not_carried`) is handed the host with a warning, and a signal between the writes is said as which side holds what. On a Mac, every merge of a server's labels goes through `Context.merge_labels` and every write of an adoption record after its first through `adopt.update`, each under `Context.host_lock` (one lock file per host name, held for the read and the replace, never across a call to a host); a test holds a merge open with the stand-in provider's `gate`.

`vm up --enroll --expect-creator <short>` (`driver/up.py`'s `asked`, before the reaper's run and any provider call) is what `sminos spawn --on new` runs (EN.G1's §9): the MAWS project added where no named one provisions, and nothing made unless the creating session `ctx.creator()` reads is that short id. A new host's descriptor names its owner's project by id where `sminos who --thread <the calling session>` answers for that very session (`context.creator_project`), else by name. sminos reads some of the driver's human lines (`up`'s `<name>  ready in …`, and where `up` fails its `caps` line, its `created   <name> (id …) from …` and its recount's two lines that say it deleted the VM, said only once `Context.delete` confirmed it; `Context.find`'s `no VM named`): each is pinned by a unit test named for its reader, so change none without sminos's `sminos_on.py`. A failure of `up` after the create says a lease bounds the VM only where it has one (`up.kept`), and `--enroll` whose boot skipped the provisioning that enrolls (the `maws` step neither `ok` nor `deferred`) fails, naming the kept VM, instead of printing `ready`.
