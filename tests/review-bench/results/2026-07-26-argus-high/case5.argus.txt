## Findings

[P0] Set/clear `_inflight` in a finally: a failing factory leaves a permanent hang — cache.py:127-133
  `get_or_compute` publishes `self._inflight[key] = done` before awaiting the factory, but `del self._inflight[key]` and `done.set()` run only on the success path — there is no `try/finally`. Any handler exception (and likewise cancellation of the computing task, or `hold()` raising `asyncio.TimeoutError` after the event was published) leaves a never-set `asyncio.Event` registered under that key permanently, since `invalidate()` clears only `_entries`. The next caller for that key takes the join branch and performs an unbounded `await pending.wait()`, blocking forever; the new `timeout`/`lock_timeout` argument guards only `self._locks.hold(...)`, not the wait. This is reached by the first failure of any job, not an exotic case: `_run_job` retries the same key, so attempt 2 parks the worker, `task_done()` is never called, and `drain()`/`aclose()` never return — one transient handler error permanently removes a worker and poisons the key for all future jobs and for `warm_stale_keys()`. Wrapping the compute in `try/finally` that pops the key and sets the event (letting joiners fall through to the lock branch and recompute) resolves it.

[P0] Do not acquire the per-key lock under the shared guard: it serializes all keys and can deadlock — keylock.py:56-59
  `hold()` now yields while still inside `async with self._guard:` (line 34 opens the guard, the `try/yield/finally` at lines 56-61 are nested in it), so the single process-wide guard is held for the entire caller block rather than just the map mutations. Since the only caller wraps `await factory()` in it (`cache.py:120-130`), every cache miss in the process serializes on one mutex regardless of key: four workers running four jobs on four distinct keys with 1 s handlers now take ~4 s instead of ~1 s, and this affects `warm_stale_keys()` passes too. Two further consequences: the new `timeout` is unreachable, because `lock.acquire()` and `lock.release()` both execute under the guard, so the per-key lock is always free when a task reaches line 47/50 and all real waiting happens on the untimed guard — making `lock_timeout` and `get_or_compute(timeout=...)` silently inert; and a handler whose factory performs another cached lookup deadlocks permanently, since the inner `hold()` awaits a non-reentrant lock its own task already owns (this worked before the change for distinct keys). Restoring the original shape — release the guard after `self._refs[key] += 1`, then acquire the key lock and yield outside the guard, re-taking the guard only for the refcount decrement — fixes all three.

[P1] Check the deadline before sliding it: an expired hot entry is revived and served stale — cache.py:74-80
  `_lookup` slides the deadline before testing it, so any entry that has reached `refresh_after_hits` reads (default 3) can never expire. Because `ttl > 0` is enforced in `__init__`, the assignment `entry.expires_at = now + self._ttl` on line 78 always puts the deadline in the future, making the `if entry.expires_at <= now` test on line 80 unreachable for that entry. With `ttl=30`, a key read three times in its first second and then not read for ten minutes will have the ten-minute-old value returned as a hit on the next read, and each subsequent read re-arms it — the entry is effectively immortal, TTL-based invalidation stops applying, and `cache.get.expired` never fires for warm keys. This contradicts the contract documented in the same change (cache.py:37-40 and the README Expiry section: "once a deadline has passed the entry is gone ... however hot the key was"). The fix is to perform the expiry check first and only slide `expires_at` after the entry is confirmed fresh.

[P1] Counter rename to `cache.get.*` silently zeroes `JobQueue.cache_hit_rate()` — cache.py:102-102
  The counter rename in `cache.py` (`cache.hit`/`cache.hit_after_wait`/`cache.miss` -> `cache.get.*`) was not propagated to the only consumer, `JobQueue.cache_hit_rate()` at jobqueue.py:194-195, which still reads the old names. Since `Counters.get` returns 0 for unknown names, `hits` and `misses` are always 0, `total == 0`, and the method permanently returns the "nothing observed yet" value 1.0. Two consequences on any queue using the default shared `Counters`: `warm_stale_keys()` always short-circuits at `if self.cache_hit_rate() >= PREFETCH_HIT_RATE: return 0`, so warm-up is dead code even during a total hit-rate collapse, and `stats()["cache_hit_rate"]` reports a perfect 1.0 to monitoring while every request misses. Updating the three reads to the `cache.get.*` names fixes it; while there, consider whether the new `cache.get.joined` counter (cache.py:110) should feed into the ratio, since a joined computation currently counts as neither hit nor miss.

[P2] Bound the `_inflight` join wait: `lock_timeout` does not apply to joiners — cache.py:110-111
  The new join path at `cache.py:105-111` runs before the timeout is resolved, so `await pending.wait()` is unbounded and neither the `lock_timeout` constructor argument nor the per-call `timeout` argument has any effect on a joining caller. This matters exactly in the scenario the docstring and README cite as the motivation for the timeout: when the task computing the key is stuck upstream, the joiner is the caller that needs the bound, yet `timeout` only reaches `self._locks.hold(...)` at line 120 — the path taken when nobody is computing. It is aggravated by `del self._inflight[key]` and `done.set()` at lines 132-133 not being in a `finally`: if `factory()` raises, the event is never set and joiners wait forever rather than for the stuck computation's duration. Resolving `timeout` before the join branch and wrapping the wait (e.g. `await asyncio.wait_for(pending.wait(), timeout)`), plus setting/clearing the event in a `finally`, would make the timeout apply where it was intended.

[P3] Seed `_last_warm` so the first warm-up pass is not throttled — jobqueue.py:210-213
  `self._last_warm` is initialised to `0.0` but compared against `time.monotonic()`, whose zero point is system boot on Linux and macOS rather than a fixed epoch. In the narrow case of a process started within `WARM_INTERVAL_SECONDS` of boot (typical for a service launched by the init system), the first ever `warm_stale_keys()` call sees `now - 0.0 < 30.0`, increments `cache.warm_throttled` and returns 0 despite no prior pass having run. Impact is small — warm-up is only deferred until uptime passes 30 s, plus one misleading counter increment — but seeding `self._last_warm = float("-inf")` (or `-WARM_INTERVAL_SECONDS`) in `__init__` makes the "never warmed" sentinel independent of the clock's reference point. Verification: plausible — mechanism real, trigger not constructed.

[P3] Retained JobResults pin exception tracebacks and payloads indefinitely — jobqueue.py:170-172
  On the error path, `_record_result` retains the live exception object, and `exc.__traceback__` keeps every frame of the failed handler alive along with that frame's locals. Since `_results` is bounded by entry count (512) rather than by retained bytes, and eviction only happens when 512 newer results arrive, a low-throughput queue whose handlers hold large locals (a buffered response body, an open session) can keep hundreds of such frame stacks resident for an unbounded time; `aclose()` does not clear the buffer either. Whether this matters depends entirely on handler shape and queue throughput, so it is low severity for small payloads. If callers only need to know what failed, clearing the traceback before retention (`exc.__traceback__ = None`) or storing a formatted string keeps `result()` useful without pinning frames. Verification: plausible — mechanism real, trigger not constructed.

## Verdict

Overall correctness: patch is incorrect
Explanation: Two confirmed P0 defects each break the change's own stated design — the missing `try/finally` around the in-flight computation permanently wedges a key and its worker on the first handler exception, and holding `KeyedLock._guard` across the caller's `yield` collapses the per-key locking into one global mutex while rendering the newly added `lock_timeout` inert. Two confirmed P1 defects compound them: hot entries can never expire because the deadline is slid before it is tested, and `cache_hit_rate()` was left reading the pre-rename counter names, so it returns a constant 1.0 and silently disables warm-up.

`★ Insight ─────────────────────────────────────`
Two of these bugs share a root pattern worth naming: **a deleted comment was the invariant.** The `keylock.py` change removed the line "Guards the two maps above, and nothing else: it is never held across an await that belongs to the caller" *and* the code structure that enforced it, in the same hunk. When a comment states a concurrency invariant, deleting it is a diff signal as strong as deleting an assertion.

The `_inflight` bug is the classic **two-phase state without an unwind path**: the old code kept exclusion state (the key lock) exception-safe via a context manager's `finally`, then this change added a *second* piece of shared state (the join event) alongside it with only a success-path teardown. Any time you register something before an `await` and unregister after it, the `await` is a branch point — exception, cancellation, or timeout all skip the teardown.

The `_lookup` reorder is a reminder that **read-path mutation and read-path validation are order-sensitive**: sliding a TTL before checking it makes the check unreachable, because the slide's own postcondition (`expires_at > now`) is the negation of the check.
