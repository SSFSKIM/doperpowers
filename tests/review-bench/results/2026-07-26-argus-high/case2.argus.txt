## Findings

[P0] Fix quickEstimate: baseRateFor now returns cents but is printed as dollars — rates.ts:50-51

  `quickEstimate` (`api.ts:75`) was not migrated to the new cents convention, so the legacy `GET /estimate` endpoint returns prices 100x too high on every call. `baseRateFor` now returns integer cents, but `quickEstimate` still does `roundDollars(baseRateFor(zone, weightKg)).toFixed(2)`, and `roundDollars` (`Math.round(v*100)/100`) is a no-op on an integer, so `quickEstimate("domestic", 0.5)` yields `"310.00"` rather than `"3.10"`. Since the widget renders the string as-is next to a dollar sign (per the doc comment at `api.ts:68-73`), every marketing estimate is displayed at 100x, and `POST /quote` — which goes through `centsToDollars` — now disagrees with `GET /estimate` by that factor for the same parcel. The fix is `centsToDollars(baseRateFor(zone, weightKg)).toFixed(2)`, after which the `roundDollars` import in `api.ts:3` becomes unused.

[P1] Restore inclusive tier upper bound in tierFor; `<` bumps boundary weights up a tier — rates.ts:42

  `tierFor` changed from `weightKg <= tier.maxKg` to `TIERS.find((tier) => weightKg < tier.maxKg)`, which makes `maxKg` an exclusive bound and prices any parcel landing exactly on a tier boundary in the next tier up. Concretely, a domestic 1.0 kg parcel now costs `400 + 95 = 495` cents instead of `250 + 120 = 370` (a 34% increase), 5 kg goes 875 → 1150 cents and 20 kg goes 2350 → 2500 cents, with the gap multiplied by the zone factor (2.4x for international). Only exact-boundary weights are affected, but those are common round values, and the change is silent — the response is still a 200 with a plausible price. This looks unintended for a commit described as a units refactor: the surviving doc comment at rates.ts:6-9 and the README "Weight tiers" section both still state that `maxKg` is inclusive. Restoring `weightKg <= tier.maxKg` in the predicate fixes it; both `buildBreakdown` (quote.ts:54) and `quickEstimate` (api.ts:75) read through `baseRateFor`.

[P1] Reinstate the 400 error path in handleQuote; non-finite weight now returns 200 with a null price — api.ts:53-58

  This commit drops the `weightKg` range check along with the `try`/`catch` that turned it into a `400`, so `handleQuote` no longer rejects any numeric weight. A body of `{"zone":"domestic","weightKg":-5}` now returns `200` with `total: 0` and a negative subtotal (`baseRateFor` computes `250 + 120 * -5 = -350` cents, and `discountCents` caps the zero discount at the negative subtotal, cancelling it out) — a free shipment rather than a rejection. A body of `{"zone":"domestic","weightKg":1e400}` parses to `Infinity`, falls through `tierFor` to the last tier, and returns `200` with `total`/`subtotal`/`amount` all serializing as `null`, which a consumer will either coerce to 0 or crash on. This contradicts README.md:28-30, which this commit left in place ("`handleQuote` answers `400` — never a price — for ... a weight that is not a positive finite number"). Raising priority from P2 to P1 because the endpoint takes untrusted input and the failure yields a chargeable quote of zero rather than an error. Restoring the `!Number.isFinite(req.weightKg) || req.weightKg <= 0` guard (in `buildBreakdown` or `parseQuoteRequest`) and the `RangeError` → `400` mapping in `handleQuote` would restore the documented behaviour.
