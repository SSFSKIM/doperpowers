## Findings

[P0] Guard `/exports/all` with `admin_only`; `authenticated` leaks every tenant's data — app.py:206-208
  `handle_export_all` is decorated `@authenticated` rather than `@admin_only`, so any caller with a valid token — including a plain member — can call `GET /exports/all?format=csv` and receive the rendered contents of every document of every tenant on the node. The handler never consults `session.tenant`; it iterates `store.list_tenants()`, which returns every tenant directory under the data root, so a member of `acme` gets `globex`'s document contents and revisions in one request. This contradicts the route table added in this same change (`| GET /exports/all | admin only | ... |`) and the Tenancy section's "any route that can see across tenants is an admin route", and the far less sensitive `handle_list_tenants`, which returns only tenant names, is correctly guarded with `@admin_only`. Swapping the decorator to `@admin_only` closes it; no other change is needed since the wrapper signatures are identical.

[P1] Return the new revision from save_document, not the row count — store.py:111-112
  `save_document` now returns `len(rows)` (store.py:112) while it persists `current + 1` as the revision, but the only caller still publishes that value as the document revision and ETag: `Response(200, {"name": name, "revision": revision, "etag": 'W/"%d"' % revision})` (app.py:174). Any client that follows the newly documented conditional-write protocol breaks: a `PUT` of 3 rows to a new document stores revision 1 but replies `revision: 3`, and the follow-up `PUT` with `expected_revision: 3` fails the check at store.py:104 and returns a 409 that re-PUTting cannot resolve (the client must do a full `GET` to learn the real revision). With `{"rows": []}` the response is `revision: 0`, which collides with the "document must not exist yet" sentinel. The ETag is also no longer a version identifier — two different writes of 3 rows both yield `W/"3"`, so cache validators can serve stale content. Either return the written revision (`current + 1`) or have the handler read it back with `load_document` as the new docstring suggests.

[P2] Fix off-by-one in page slice; pages return limit+1 and overlap — app.py:98-103
  The page slice uses an inclusive upper bound on an already-exclusive index, so every page of `GET /documents` returns `limit + 1` names and the last name of one page is repeated as the first name of the next. `last = first + limit` is the index one past the final entry, but the slice is `names[first : last + 1]`. Any tenant with more documents than `limit` is affected: at `limit=50` with 120 documents, page 1 returns 51 names while the body advertises `"limit": 50`, and the name at index 50 appears on both page 1 and page 2, so a client concatenating pages processes it twice. At `limit=200` a page carries 201 entries, exceeding the `MAX_PAGE_SIZE` cap documented in the README. The fix is to slice `names[first : first + limit]` (i.e. use `last` as the exclusive bound).

[P2] Isolate per-document failures in `/exports/all` so one bad document cannot kill the whole export — app.py:216-224
  The new `handle_export_all` loop calls `store.load_document` and `render.render` with no per-document error handling, so a single bad document aborts the export for every tenant. Concretely: `handle_put_document` only checks `isinstance(rows, list)` (app.py:157-159), so any member can persist `{"rows": [1, 2, 3]}`; afterwards every `GET /exports/all?format=csv` reaches `render.columns_of`, whose `for key in row` iterates an `int` and raises `TypeError`, which escapes `handle` instead of returning a `Response` — and it keeps doing so until that file is repaired. The same loop is also unguarded against `store.BadDocumentName`, which `store.load_document` raises for any `*.json` file whose stem fails `NAME_PATTERN` (only reachable via files created outside the API, e.g. a restored backup `Report.json`). Wrapping the per-document load and render in a `try/except` and skipping (or reporting) the offending entry, as the sibling handlers already do for `BadDocumentName`, would confine the failure to one document. Verification: plausible — mechanism real, trigger not constructed.

[P3] Close the check-then-write race in the new conditional write path — store.py:104-111
  The new conditional-write check reads the current revision (store.py:101-107) and then writes with a plain `open(path, "w")` (store.py:109-111), so the compare-and-set is not atomic: if two `PUT`s for the same tenant and document are dispatched concurrently, both can read the same `current`, both pass the guard, and the second write truncates the first — including the `expected_revision: 0` "must not exist yet" case, where both callers receive a 200. This only matters if the deployment dispatches `app.handle` concurrently (nothing in this repo does, so it may be a non-issue for the intended single-threaded use); if concurrent writers are expected, the write needs an exclusive create (`os.O_CREAT | os.O_EXCL`) for the revision-0 case and a lock or atomic temp-file-plus-rename for the general case to back the README's "a mismatch is a 409 and nothing is written" guarantee. Verification: plausible — mechanism real, trigger not constructed.
