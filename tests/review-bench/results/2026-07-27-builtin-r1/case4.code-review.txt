## Review body

The review found nine issues, and two of them break the branch outright. I re-ran the reviewer's claims against the actual scripts and confirmed the important ones by execution rather than by reading, so the severity ordering below is grounded in observed behavior.

**The headline result: this branch turns off archive rotation completely, and turns off the disk-space guard it was written to add.**

`snapshot.sh` now prints four tab-separated fields (label, epoch, bytes, path), and `run-backup.sh` was updated to read four. `prune.sh` was not — it still reads three (`prune.sh:62`). In shell, the final variable in a `read` absorbs everything left on the line, so `path` ends up holding `"345<tab>/archives/nightly-….tar.gz"`. That is never a real file, so every record falls into the "manifest points at a missing archive, skipping" branch and the rotation function is never called. I ran five backups against a scratch directory with the retention limit set to two, and all five archives were still there afterward. The archive directory now grows forever, which is precisely the disk-exhaustion failure the rest of the branch is trying to prevent.

The second one is in the new free-space guard (`lib/common.sh:81`). It decides whether a shortfall is fatal with `[ "$force" ]`, and `snapshot.sh` defaults that variable to the string `"0"`. A single-argument `[` test asks only whether the string is non-empty, and `"0"` is non-empty, so the answer is always yes. Every run without `--force` logs the shortfall and continues. The guard is inert exactly in the situation it exists for, and setting `BACKUP_FORCE=0` behaves the same as setting it to `1`.

`★ Insight ─────────────────────────────────────`
- `read` with a fixed variable list is a silent-corruption hazard when a record format grows a column: the extra field lands inside the last variable instead of raising an error, so the failure surfaces far from the parser. A count check (`read -r a b c d rest` plus a guard, or a version marker in the record) makes the mismatch loud.
- `[ "$x" ]` is a string-emptiness test, not a truth test. Shell has no boolean type, so `"0"`, `"false"`, and `"no"` are all "true" here. Sentinel values like `0`/`1` must be compared by value: `[ "$x" != 0 ]`.
- Both bugs share a shape worth noting: the branch added a *new* consumer contract in one file and left the *existing* consumer unchanged. The README even documents why the label column was added, which makes the missed update in `prune.sh` visible in the diff itself.
`─────────────────────────────────────────────────`

**The remaining seven, in descending order of consequence:**

Even once the field count is fixed, `prune.sh:71` still recovers the label by cutting the filename at the first hyphen (`label="${base%%-*}"`), so a label like `weekly-db` becomes `weekly` and rotation deletes archives belonging to a different label. The new label column exists specifically to prevent this and is never read.

`snapshot.sh:77` dropped the `trap 'rm -rf "$STAGE"' EXIT INT TERM` that used to follow `mktemp -d`. Cleanup now happens only on the success path. I pointed `BACKUP_REMOTE` at an unreachable host, and the run left the staging directory with a complete archive inside it sitting in the temp directory. A nightly job against a broken replica accumulates one full-size archive per night.

The replication helper (`lib/common.sh:97`) has a comment saying it uses `cat` rather than `scp` so a dropped connection cannot leave a partial file under the archive's final name — but the remote command is `cat > '$BACKUP_REMOTE_DIR/$name'`, which writes the final name directly. It does the exact thing the comment says it avoids. It should stream to a temporary remote name and rename after the transfer completes.

The free-space check (`snapshot.sh:75`) measures the archive directory, but `tar` writes the archive into the staging directory under `TMPDIR` first. On a host where `/tmp` is a small partition or a tmpfs, a run that passes the check still fills `/tmp` or eats RAM and dies mid-archive.

Moving `umask 077` into the shared library (`lib/common.sh:14`) changed when it takes effect: it is now active before `mkdir -p "$BACKUP_ARCHIVE_DIR"`, so a first run on a new host creates that directory as `drwx------` rather than `drwxr-xr-x`. I confirmed this. Any separate account that reads archives — a restore user, a monitoring agent — loses access after a fresh provision with no error explaining why.

Two smaller ones. The rewritten listing in `prune.sh:44` uses `find -maxdepth 1 -type f`, which excludes symlinks, where the old `[ -f "$file" ]` followed them; the comment claiming the resulting set is identical to the old glob's is wrong on that point. And `lib/common.sh:98` interpolates the remote directory and archive name into a single-quoted remote command without escaping, so a value containing an apostrophe breaks the quoting — these come from the operator's own config rather than untrusted input, so it reads as a confusing failure rather than a security hole.

I made no code changes; this was a review only. If you want the two blocking bugs fixed, the changes are small and self-contained (one `read` line and one test expression), and I can do both plus the label-column consumer in one pass.
