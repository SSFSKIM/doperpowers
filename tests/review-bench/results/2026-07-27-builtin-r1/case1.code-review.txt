## Review body

The review of `main...bench-change` is done. Four findings reported above, two of which are release-blocking and both reproduced by actually running the code.

The short version: the multi-tenant refactor is sound in shape — per-tenant watermarks, `(tenant, window)` aggregation keys, stricter value parsing all hold up — but two mechanical edits made during the refactor silently break the core semantics. The lateness check in `windows.py` flipped a minus to a plus, which converts the grace period into a requirement that readings arrive *ahead* of the watermark, so an ordinary in-order stream gets thrown away. And `flush()` in `aggregate.py` was rewritten to call the new `snapshot()` helper but lost the `_pending.clear()` that made it a *flush*, so every batch in `summarize_files` re-emits all prior batches' windows.

`★ Insight ─────────────────────────────────────`
Both bugs share a signature worth internalizing: **they are invisible under the default configuration**. The inverted cutoff is a no-op at `allowed_lateness=0` (both `ts < watermark - 0` and `ts < watermark + 0` are the same expression), and the missing `clear()` is a no-op when there is exactly one batch — which is exactly what the preserved `summarize_file` wrapper does. A test suite written around the old single-file API would pass clean on both. The new parameters are where the risk moved, and that is where tests are absent.

The `snapshot()`/`flush()` split is also a small lesson in naming as a load-bearing contract. `snapshot()` legitimately means "read without mutating"; `flush()` means "read and retire." Implementing the second as a bare call to the first drops the only behavior that distinguished them, and the docstring left behind ("Emit and retire every accumulated window") now actively lies about what the function does.
`─────────────────────────────────────────────────`

The fixes are one line each — restore `watermark - self.allowed_lateness` in the cutoff, and make `flush()` do `rows = self.snapshot(); self._pending.clear(); return rows`. I have not applied them, since you asked for a review rather than a change. Say the word and I'll make both edits plus add regression tests covering non-zero lateness and the multi-batch path.
