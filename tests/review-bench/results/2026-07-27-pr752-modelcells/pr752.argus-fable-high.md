  `gradeFingerprintKey`는 이번 변경에서 `grade_system`을 키에 포함하도록 확장됐고(tests/grade-recency.test.ts가 이를 고정), grade-recency.ts의 주석도 "등급제가 정정돼도 지문이 그대로면 옛 계획이 계속 반환된다"를 명시하지만, 유일한 프로덕션 호출부인 `buildInputFingerprint`(line 1038)의 `.map((g) => ({ subject, grade, grade_level, semester }))`가 `grade_system`을 떨어뜨립니다. `getLatestGrades`는 `select('*')`라 행에 값이 있는데도 지문에는 항상 `''`로 들어가므로, 성적 행의 `grade_system`만 바뀌는 경우(예: 지원팀의 provenance 정정, 마이그레이션·배포 시차로 남은 NULL 행의 사후 각인)에는 캐시가 무효화되지 않고 옛 해석으로 만든 계획이 만료 없이 계속 반환됩니다. 진급 자체는 `type=` 토큰이, 이번 배포는 `fpv=2`가 커버해 당장 겉으로 드러나진 않지만, 의도한 방어선이 조용히 무력화된 상태입니다 — map에 `grade_system: g.grade_system`을 추가하면 됩니다.

[P2] 온보딩 학년 변경 차단 가드가 DB 조회 오류 시 조용히 열림 — app/api/students/onboarding/route.ts:80-86
  진급 경로 우회를 막는 `existing` 조회가 `const { data: existing } = await …maybeSingle()`로 `error`를 버립니다. 조회가 일시적 DB 오류로 실패하면 `existing`이 null이 되어 409 가드를 그대로 통과하고, `effectiveType`이 클라이언트가 보낸 `data.type`으로 잡혀 upsert가 type을 덮어씁니다 — 이 커밋이 "진급 라우트의 안전장치가 통째로 무의미해진다"고 주석으로 명시하며 막으려던 바로 그 우회가, 오류 상황에서는 각인·이력·감사 로그 없이 조용히 일어납니다(성적 각인도 잘못된 type 기준으로 됩니다). 같은 커밋의 진급 라우트는 조회 오류를 중단으로 처리(`sErr → 404`)하므로, 여기도 `error`를 받아 500으로 중단(fail-closed)하는 것이 일관됩니다. 발생 조건이 일시적 DB 오류라 빈도는 낮습니다.
