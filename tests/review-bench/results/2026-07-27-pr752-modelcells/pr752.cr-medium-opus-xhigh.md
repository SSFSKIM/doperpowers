## Review body

The review of `main...bench-change` is done: five findings, one medium and four low. No blocking defect — the core of the change holds up.

**What the change does well.** The central mechanism of issue #208 is that changing a student's 학년 is a promotion event, and past grades must keep the 등급제 they were recorded under rather than being reinterpreted under the new one. Three things make that safe, and all three check out: the grade stamping is committed *before* the `students.type` update, the type update is a compare-and-swap, and the stamping is idempotent because it only touches rows where `grade_system` is still null. If the process dies between the two steps, the stamped values are still correct and a retry is harmless. The reverse ordering would have permanently falsified grades, and the code comments say so explicitly.

**The one finding worth acting on before merge** is in `lib/goal-grade.ts:122`. The new rule drops the 목표 대비 격차 number whenever a grade row's 등급제 differs from the student's current one. That sounds narrow but isn't: `stampGradeSystem` stamps every 모의고사 row as 9등급제 regardless of 학년, by design, while a 고1 or 고2 student's current system is 5등급제. So for those students the two systems differ on essentially their whole mock-exam history, and the gap disappears for every subject in the 학원장 counseling and student-detail screens. The fix is available in the same file — `GOAL_TARGET_GRADE` already stores both a 9등급제 and a 5등급제 target per university, and `targetGradeFor` already takes the system as an argument, so the gap can be computed against the row's own system instead of being suppressed.

**The four low findings** are: the self-service rate limit on `/api/students/promotion` can be escaped by including your own `student_id` in the body (the route already has `student.user_id` in hand to decide this properly); the settings card never computes the "revert" case, so undoing a promotion you just made demands a reason the server doesn't require and the card's own help text says you don't need; a successful promotion leaves the surrounding navigation showing the old 학년 until reload; and one now-unused type import in `lib/generate-plan.ts`.

**One operational item, not a code defect.** All three grade write paths now include `grade_system` in their insert payloads and four read paths select the column. `sql/p143_student_type_promotion.sql` has to be applied in Supabase with or before this deploy — otherwise every grade save fails outright with a missing-column error rather than degrading gracefully. That is the exact footgun the project's own database notes warn about.

**Verification caveat:** `node_modules` is not installed in this checkout, so I could not run `npx tsc --noEmit`, `npm test`, or `npm run lint`. Every finding above was confirmed by reading the code in this working tree, but none is backed by a test run.

`★ Insight ─────────────────────────────────────`
- The provenance pattern here is worth noting generally: rather than converting historical values into the current scheme (lossy, and the converted number would be presented as something the student actually received), the code stores the interpretation context alongside each value and resolves it at display time. `lib/grade-provenance.ts` is careful to call reinterpretation "위조" — falsification — not a display bug, which is the right framing for why conversion was rejected.
- The finding in `goal-grade.ts` shows the usual failure mode of that pattern: once you have provenance, it's tempting to treat any mismatch as "incomparable" and suppress output. But mismatch only blocks comparison when the *target* is single-system. Here the target table is already dual-system, so the correct move is to look up the target in the row's system rather than to give up.
- The ordering argument in the promotion route — stamp first, then flip the type — is a good example of using commit order as a safety property when you have no transaction across two statements. The test to apply is: for each possible crash point, is the resulting state merely incomplete, or is it actively wrong? Here one order yields incomplete-and-retryable, the other yields wrong-and-permanent.
