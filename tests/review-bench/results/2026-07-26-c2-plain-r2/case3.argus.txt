`★ Insight ─────────────────────────────────────`
- Two of these three findings are the classic failure mode of **decorator-based authorization**: the security policy becomes a single token on a line above the function, so the difference between "any logged-in user" and "admin" is one word that no type checker and no local test will catch. The README route table is the only place the intended policy is written down, which is why the reviewer cross-checked against it — a good argument for driving the guard from the route table rather than restating it per handler.
- The `save_document` bug shows why **changing a return value's meaning is more dangerous than changing its type**. Both the old `revision` and the new `len(rows)` are plain integers, so the caller keeps compiling, keeps running, and keeps emitting a number that looks like a revision. Bugs that preserve the shape of data while corrupting its meaning slip past every automated boundary and only surface later as spurious 409 conflicts.
- The pagination slice is an off-by-one born from mixing conventions: `first + limit` is an *exclusive* end, but `[first : last + 1]` is the idiom for an *inclusive* one. Naming the variable `last` invited the inclusive reading — `end` would have made the mismatch visible at the point of use.
`─────────────────────────────────────────────────`

Want me to apply the three fixes? The export-route guard and the pagination slice are mechanical. The `save_document` one needs a call: return the new revision from the store (keeps the handler and its ETag semantics untouched, which I'd recommend), or leave the row count and have the handler re-read the revision.
