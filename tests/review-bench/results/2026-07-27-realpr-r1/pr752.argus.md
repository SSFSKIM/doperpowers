## Findings

[P3] Self rate-limit bucket selectable by client via optional student_id — app/api/students/promotion/route.ts:204-207
  The tighter self bucket (5/h) applies only when the request body omits `student_id`, but a student can trivially include their own `student_id` (visible throughout the app's API responses), pass `assertStudentAccess` as self, and land in the operator bucket (60/h) — defeating the stated intent of "학생 본인 경로만 좁게 잡는다". Severity is low because the limiter is per-instance in-memory and 60/h is still bounded, but since the route already loads the student row, classifying by actor identity (`student.user_id === user.id`, as `resolveActorRole` later does) instead of request shape would make the tiering non-bypassable. Note the student row is fetched after the limit check, so this needs either an early ownership lookup or moving the gate.

[P3] Revert flow in UI misclassified as correction, forcing an unnecessary reason — components/settings/GradePromotionCard.tsx:68-70
  The card calls `classifyTransition(current, target)` without the `isRevertOfLatest` flag, so when a user follows the card's own hint ("잘못 바꿨다면 위에서 이전 학년을 다시 선택하면 되돌릴 수 있어요") to undo the latest transition, the confirm box shows "학년 정정" and blocks submission until a reason is entered — while the server (which computes `isRevertOfLatest` from history) classifies the same request as `revert` and requires no reason. The GET endpoint even returns a `revertable` payload built for this purpose that the card never reads. Impact is UX friction and a mislabeled confirmation only (the server records `kind: 'revert'` correctly), triggered whenever a user reverts their most recent change.
